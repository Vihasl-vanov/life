## JPA

**JPA (Java Persistence API)** — это стандартный интерфейс для управления объектно-реляционным отображением (ORM) в Java-приложениях. Он предоставляет удобные и простые в использовании средства для взаимодействия с базой данных через java-объекты.

JPA позволяет разработчикам работать с данными в базе данных, используя объекты Java, вместо написания прямых SQL-запросов. Он обеспечивает сопоставление объектов Java с таблицами в базе данных, автоматическую генерацию SQL-запросов, управление транзакциями и другие функции, связанные с доступом к данным.

Основные преимущества JPA включают:

• Упрощение разработки — мы пишем меньше кода;

• Улучшенную поддержку объектно-ориентированного программирования — наш код чистый и понятный;

• Повышение производительности за счёт оптимальности запросов.

Он также способствует уменьшению зависимости от конкретной реализации базы данных, поскольку JPA работает с различными поставщиками, которые могут быть адаптированы под разные базы данных.

Таким образом, JPA позволяет разработчикам более эффективно работать с данными в базе данных, используя объектно-ориентированный подход и предоставляя стандартные средства доступа к данным в Java.

## Hibernate

**Hibernate** является одним из наиболее популярных и широко используемых поставщиков JPA. Он предоставляет реализацию JPA и расширенный функционал для работы с базами данных с использованием ORM.

**Hibernate** обеспечивает сопоставление объектно-ориентированных классов с таблицами базы данных, управление жизненным циклом объектов, автоматическую генерацию SQL-запросов, кэширование данных, управление транзакциями и другие возможности, необходимые для работы с данными.

**Hibernate** соответствует спецификации JPA, но также расширяет её, предоставляя дополнительные функции и возможности, которые не являются стандартными для JPA. Эти дополнительные функции могут быть полезными в некоторых сценариях разработки.

**Hibernate** обладает своими уникальными функциями и возможностями, которые не включены в стандарт JPA. Это включает возможности каскадирования операций, расширенные стратегии загрузки, кэширование, управление сессиями и другие характерные для **Hibernate** функции.

Таким образом, использование Hibernate в качестве поставщика JPA позволяет использовать преимущества обеих платформ.

## JPA Mapping

 Мы описываем, как маппить java-объект в таблицу базы данных.
Просто Java-класс:

```java
public class User {

    private Long id;
    private String username;
    private String email;
```

Java-класс, который представляет сущность в базе данных:

```java
@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "username", length = 64, nullable = false, unique = true)
    private String username;

    @Column(name = "email", length = 64, nullable = false, unique = true)
    private String email;
```

Так, одной из ключевых особенностей JPA Mapping является использование аннотаций для отображения Java-классов на таблицы базы данных. Эти аннотации позволяют нам явно указывать соответствие между полями класса и столбцами таблицы, а также определять связи между различными классами.

Некоторые их наиболее распространенных аннотаций маппинга в JPA:

1. `@Entity` — эта аннотация используется для пометки класса как сущности, которая будет отображена на таблицу базы данных. То есть, мы говорим, что класс, который мы описали в нашем приложении, описывает определённую сущность в базе данных.

2. `@Table` — с помощью этой аннотации можно указать имя таблицы, которую описывает сущность.

3. `@Column` — аннотация применяется к полям класса и определяет соответствующий столбец таблицы, в котором будет храниться значение поля.

4. `@Id` — с помощью этой аннотации указывается, что поле является первичным ключом таблицы.

5. `@GeneratedValue` — данная аннотация указывает способ генерации значений для первичного ключа, например, автоматическая генерация или использование последовательности зависит от выбранной стратегии. Наиболее распространенные стратегии:

- `GenerationType.IDENTITY` — стратегия, при которой база данных автоматически генерирует значения идентификаторов. Обычно используется автоинкрементное поле в базе данных;
    
- `GenerationType.SEQUENCE` — значения идентификаторов генерируются с использованием базовой последовательности, которая управляется базой данных, например, в PostgreSQL это будет SERIAL;
    
- `GenerationType.TABLE` — значения идентификаторов генерируются с помощью отдельной таблицы в базе данных, которая содержит счётчики для каждой сущности. При сохранении новой сущности, значение идентификатора извлекается из таблицы и увеличивается на единицу;
    
- `GenerationType.AUTO` — это стратегия, при которой JPA самостоятельно выбирает подходящую стратегию генерации идентификаторов, в зависимости от используемой базы данных и настроек.
    

6. `@OneToMany`, `@ManyToOne`, `@ManyToMany` — эти аннотации определяют отношения между различными сущностями, такие как One-to-Many, Many-to-One и Many-to-Many соответственно.

7. `@Transient` — используется для пометки поля в сущности, которая не должна быть сохранена в базе данных. Поле, помеченное аннотацией `@Transient`, игнорируется при операциях сохранения, обновления и загрузки сущности.

8. `@Enumerated` — используется для указания, как значение перечисления enum должно быть сохранено в базе данных. При работе с перечислениями в JPA есть два варианта хранения их значений:

- `@Enumerated(EnumType.ORDINAL)` — при использовании этого варианта, JPA сохраняет в базе данных порядковое значение, то есть его индекс. Нумерация начинается с 0. Например, перечисление “A, B, C,” будет сохранено как: 0, 1, 2 — соответственно;
    
- `@Enumerated(EnumType.STRING)` — при использовании этого варианта, JPA сохраняет в базе данных строковое представление перечисления. То есть, значения сохраняются как строки с соответствующими именами. В примере выше, значения “A, B, C” будут сохранены в базе данных именно так, как они перечислены — без изменений.
    

9. `@Embeddable` — используется в JPA для пометки класса как встраиваемого (embeddable) компонента. Встраиваемые компоненты позволяют включать в сущности другие объекты в качестве составных частей без необходимости создания отдельных таблиц в базе данных. Когда класс помечается аннотацией `@Embeddable`, он становится доступным для включения в другие сущности. Объекты данного класса могут быть включены непосредственно в таблицу сущности, содержащей его, или в отдельную таблицу, связанную с основной таблицей сущности.

## Cascade

Аннотация `CascadeType` используется в JPA (Java Persistence API) для определения, какие операции должны каскадироваться от одной сущности к другой при выполнении операций сохранения, обновления или удаления. В контексте JPA, каскадирование (cascade) означает, что определённые операции, примененные к одной сущности (называемой главной сущностью), также будут автоматически применены к связанным сущностям.

`CascadeType` предоставляет несколько вариантов для указания типов операций, которые должны быть каскадированы:

1. `CascadeType.ALL` — все операции (сохранение, обновление и удаление) должны быть каскадированы. Это наиболее полный вариант и включает все другие типы каскадирования.
    
2. `CascadeType.PERSIST` — операция сохранения (`persist`) должна быть каскадирована. Когда вы сохраняете главную сущность, все связанные новые или ещё не сохранённые сущности также будут автоматически сохранены.
    
3. `CascadeType.MERGE` — операция обновления (`merge`) должна быть каскадирована. Когда вы обновляете главную сущность, все связанные сущности также будут автоматически обновлены. Это означает, что при выполнении операции слияния (merge) для корневой сущности, JPA также будет пытаться объединить изменения во всех связанных сущностях. Если связанная сущность уже существует в базе данных, она будет обновлена. Если она не существует, она будет сохранена. Это полезно, например, когда у нас есть граф сущностей и мы хотим сохранить изменения во всех частях графа. CascadeType.MERGE применяется для сохранения изменений из памяти в базу данных.
    
4. `CascadeType.REMOVE` — операция удаления (`remove`) должна быть каскадирована. Когда вы удаляете главную сущность, все связанные сущности также будут автоматически удалены.
    
5. `CascadeType.REFRESH` — операция обновления (`refresh`) должна быть каскадирована. Когда вы обновляете главную сущность, все связанные сущности также будут автоматически обновлены. Это означает, что при выполнении операции обновления (refresh) для корневой сущности, JPA попытается обновить состояние этой сущности и всех связанных сущностей из базы данных. Если данные в базе изменились с момента загрузки сущности в память, они будут обновлены в памяти. Это полезно, например, когда мы хотим обновить состояние объектов сущностей в памяти так, чтобы они точно соответствовали данным в базе. CascadeType.REFRESH применяется для обновления данных из базы данных в память.
    
6. `CascadeType.DETACH` — операция отсоединения (`detach`) должна быть каскадирована. Когда главная сущность отсоединяется от контекста хранения, все связанные сущности также будут автоматически отсоединены.
    
7. `CascadeType.ALL` и `CascadeType.DELETE_ORPHAN` — все операции каскадирования и удаления сирот должны быть каскадированы. Этот тип используется в Hibernate для поддержки удаления "сирот" (связанных сущностей, которые больше не имеют ссылок на главную сущность).

## Сессия в Hibernate
`EntityManager` — это ключевой интерфейс в JPA, через который мы можем взаимодействовать с БД и получать/сохранять данные, которые автоматом конвертируются из простой записи в базе в Java-объекты (сущности) и наоборот.

`EntityManager` выполняет ряд функций:

1. **Управление жизненным циклом сущностей.** С помощью `EntityManager` можно создавать, сохранять, обновлять и удалять сущности в базе данных. Он отслеживает состояние сущностей и синхронизирует их состояние с базой данных.
    
2. **Выполнение запросов.** `EntityManager` предоставляет методы для выполнения запросов к базе данных, как на языке JPQL (Java Persistence Query Language), так и на нативном SQL.
    
3. **Управление транзакциями.** `EntityManager` позволяет управлять транзакциями при взаимодействии с базой данных. Вы можете начинать, фиксировать (commit) или откатывать (rollback) транзакции вручную.
    
4. **Кэширование.** `EntityManager` поддерживает механизмы кэширования, которые позволяют улучшить производительность приложения путём уменьшения количества обращений к базе данных.
    
5. **Управление соединениями.** `EntityManager` управляет соединениями с базой данных, что обеспечивает эффективное использование ресурсов и минимизирует нагрузку на базу данных.
    

Spring Data под капотом использует Hibernate, получает из Persistence контекста `EntityManager` и с помощью AOP оборачивает наши запросы в базу в транзакции.

Сессия в Hibernate — это основная точка взаимодействия между приложением и базой данных. Она представляет собой хранилище для объектов, которые соответствуют записям в базе данных. `Session` — это мост между Java-приложением и Hibernate. Она обеспечивает ORM-механизм для сохранения, получения и обновления данных в базе данных с использованием объектов Java (ORM - Object-Relational Mapping - преобразование записи в БД в объект Java и наоборот). Объект `Session` **получают из экземпляра `SessionFactory`, который в свою очередь должен быть единственным (singleton) **объектом в приложении.

`Session` — это реализация хибернейтом абстракции `EntityManager` (относится к JPA), пример с которым мы смотрели выше (на самом деле `Session` — это тоже интерфейс, а уже конкретная реализация — это, например класс, `SessionImpl`). То есть, когда мы используем `EntityManager`, это значит, что мы используем `SessionImpl` хибернейта. Hibernate — это не единственная реализация JPA, есть много других, например, EclipseLink, поэтому у нас есть такой дополнительный слой абстракции в виде `EntityManager`, чтобы не зависеть от конкретного фреймворка, который можем использовать в программе.

Для каждой операции взаимодействия с базой данных, вам нужно открыть сессию. Обычно сессия открывается в начале транзакции или операции чтения/записи данных.

## Кэширование в Hibernate

Кэширование в Hibernate — это механизм, который позволяет улучшить производительность и снизить нагрузку на базу данных, храня часто используемые данные в памяти. Hibernate поддерживает различные уровни кэширования, которые можно настроить для оптимизации работы с базой данных. Рассмотрим основные принципы и кейсы использования кэширования в Hibernate.

1. Уровни кэширования в Hibernate:

- Кэширование первого уровня (First-Level Cache). Это кэш, который хранит сущности и их состояния в рамках сессии (`Session`). Он автоматически активируется при использовании `Session`, и его срок жизни ограничен временем жизни сессии. Каждая сессия имеет свой собственный кэш первого уровня;
    
- Кэширование второго уровня (Second-Level Cache). Это кэш, который хранит сущности и их состояния в рамках фабрики сессий (`SessionFactory`). Кэш второго уровня является общим для всех сессий и позволяет совместно использовать данные между различными сессиями;
    
- Уровень запросов (Query Cache). Это кэш, который хранит результаты выполненных запросов. Он позволяет кэшировать результаты запросов и повторно использовать их при последующих выполнениях того же запроса.
    

2. Принципы кэширования в Hibernate:

- Идентификация и ключи. Кэширование в Hibernate основано на идентификации сущностей. Каждая сущность имеет уникальный идентификатор (первичный ключ), который используется в качестве ключа для доступа к кэшированным данным;
    
- Инвалидация. Кэш должен быть умным и способен инвалидировать устаревшие данные. Если данные в базе данных были изменены или удалены, то кэш должен быть обновлён или очищен.
    

3. Кейсы использования кэширования в Hibernate:

- **Кэширование сущностей (Entity Caching)**. Кэширование сущностей позволяет избежать частых обращений к базе данных при повторном запросе одних и тех же сущностей. Это особенно полезно для часто используемых данных;
    
- **Кэширование запросов (Query Caching)**. Кэширование запросов позволяет избежать повторного выполнения сложных запросов к базе данных, если они уже были выполнены и их результаты кэшированы;
    
- **Кэширование коллекций (Collection Caching)**. Кэширование коллекций позволяет улучшить производительность при доступе к связанным объектам, таким как списки или множества;
    
- **Кэширование прокси (Proxy Caching)**. Hibernate использует прокси для ленивой загрузки связанных объектов. Кэширование прокси может помочь избежать множественных запросов к базе данных при доступе к связанным объектам;
    
- **Кэширование метаданных (Metadata Caching)**. Hibernate также поддерживает кэширование метаданных, таких как маппинг классов и таблиц, что улучшает производительность при создании сессий.
    

Важно заметить, что кэширование должно быть использовано с осторожностью, и не все данные подходят для кэширования. Некорректное или неадекватное использование кэширования может привести к проблемам согласованности данных и ухудшению производительности приложения. Поэтому перед включением кэширования важно провести тестирование и оценку его эффективности для конкретного приложения.

## Кэширование первого уровня (First-Level Cache)

Кэш первого уровня в Hibernate есть по умолчанию и активируется автоматически при использовании `Session`. Кэш первого уровня представляет собой внутренний кэш, который хранит сущности и их состояния в рамках текущей сессии. Это означает, что каждая открытая сессия имеет свой собственный кэш первого уровня.

Когда вы получаете сущность по её идентификатору с помощью метода `session.get()` или `session.load()`, Hibernate сначала проверяет кэш первого уровня на наличие запрошенной сущности. Если сущность уже есть в кэше первого уровня, она будет возвращена из кэша, и запрос к базе данных не будет выполнен. Если же сущность отсутствует в кэше первого уровня, Hibernate выполнит запрос к базе данных для получения сущности и добавит её в кэш.

Кэш первого уровня является внутренним механизмом Hibernate и работает без необходимости дополнительной конфигурации. Вы можете использовать его просто при работе с `Session` в Hibernate.

**Преимущества кэша первого уровня:**

- Улучшение производительности. Кэш первого уровня позволяет избежать частых запросов к базе данных при повторном доступе к одним и тем же сущностям в рамках одной сессии, что значительно улучшает производительность приложения;
    
- Минимизация нагрузки на базу данных. Благодаря кэшу первого уровня, сущности, которые уже были загружены в рамках текущей сессии, не будут загружены повторно при повторном доступе к ним.
    

Однако, кэш первого уровня ограничен своей локальностью и не предоставляет совместного использования данных между различными сессиями. Если вам требуется общее кэширование данных между сессиями, рекомендуется использовать кэш второго уровня (Second-Level Cache) в Hibernate.

## Кэширование второго уровня (Second-Level Cache)

Кэширование второго уровня (Second-Level Cache) в Hibernate представляет собой общий кэш, который хранит сущности и их состояния между различными сессиями (`Session`). В отличие от кэша первого уровня, который ограничен областью видимости текущей сессии, кэш второго уровня доступен для всех сессий, использующих одну и ту же фабрику сессий (`SessionFactory`). Это позволяет совместно использовать данные между различными сессиями и улучшить производительность приложения.

**Принципы работы кэша второго уровня:**

1. **Общий доступ**. Кэш второго уровня является общим для всех сессий, использующих одну и ту же фабрику сессий (`SessionFactory`). Это позволяет совместно использовать данные между различными сессиями и избежать повторной загрузки уже загруженных сущностей.
    
2. **Конфигурирование**. Кэш второго уровня должен быть явно настроен и включен для использования. Вы можете выбрать различные поставщики кэша (например, Ehcache, Infinispan, Hazelcast) и настроить его параметры для оптимальной производительности.
    
3. **Идентификация и ключи**. Кэш второго уровня также основан на идентификаторах сущностей (первичных ключах). При загрузке или получении сущности по её идентификатору, Hibernate сначала проверяет кэш второго уровня на наличие запрошенной сущности.
    
4. **Обновление и синхронизация**. Кэш второго уровня автоматически обновляется при изменении состояния сущностей в рамках различных сессий. Hibernate следит за изменениями и автоматически синхронизирует кэш второго уровня с базой данных при необходимости.
    
5. Сущности не хранятся в кэше второго уровня как экземпляры Java, а скорее в их разобранном (гидрированном) состоянии:  
    Идентификатор (первичный ключ) не сохраняется (он сохраняется как часть ключа кэша);  
    Transient-свойства не сохраняются;  
    Коллекции не сохраняются, на них нужно явно указать при помощи аннотации, что коллекция должна быть кэширована. В каждой записи кэша коллекции хранятся только идентификаторы (id) сущностей, содержащихся в этой коллекции. Если хотим хранить другие поля, то они должны быть отмечены аннотацией `@Cachable`.
    

**Кейсы использования кэша второго уровня**

1. Общее кэширование данных. Кэш второго уровня позволяет совместно использовать часто используемые данные между различными сессиями, что улучшает производительность и снижает нагрузку на базу данных.
    
2. Улучшение масштабируемости. Кэш второго уровня помогает улучшить масштабируемость приложения, так как позволяет распределить нагрузку между различными сессиями и избежать излишнего доступа к базе данных.
    
3. Оптимизация запросов. Кэш второго уровня позволяет кэшировать результаты выполненных запросов, что уменьшает количество запросов к базе данных и улучшает производительность приложения.

Для примера, рассмотрим, как подключить кэш второго уровня с использованием провайдера Ehcache. Для включения кэша второго уровня в Spring Boot приложении, потребуется выполнить несколько шагов:

1. **Добавить зависимости в проект:**

```java
//gradle
implementation 'org.ehcache:ehcache'
```

2. В файле `application.yml` добавьте соответствующие настройки для кэш-провайдера:

```java
hibernate.cache.use_second_level_cache: true
hibernate.cache.region.factory_class: org.hibernate.cache.ehcache.EhCacheRegionFactory
```

3. **Конфигурации кэша**

Можно также создать файл конфигурации с различными настройками **ehcache.xml:**

```java
<ehcache xmlns:xsi="<http://www.w3.org/2001/XMLSchema-instance>"
         xsi:noNamespaceSchemaLocation="<http://www.ehcache.org/ehcache.xsd>"
         updateCheck="false">

    <cache name="myEntityCache"
           maxEntriesLocalHeap="1000"
           eternal="false"
           timeToLiveSeconds="300"
           timeToIdleSeconds="60"
           memoryStoreEvictionPolicy="LRU"/>

</ehcache>
```

В этом примере мы определяем кэш с именем "myEntityCache" с максимальным количеством элементов `maxEntriesLocalHeap` равным 1000. Элементы в кэше не являются "вечными" (`eternal="false"`), и они будут удалены через 300 секунд (`timeToLiveSeconds="300"`) после последнего доступа к ним или через 60 секунд (`timeToIdleSeconds="60"`) после последнего обновления, используя алгоритм вытеснения наименее недавно используемых элементов `memoryStoreEvictionPolicy="LRU"`.

Путь к файлу `ehcache.xml` нужно указать в `application.yml`:

```java
spring.cache.jcache.config: classpath:ehcache.xml
```

4. **Настройка сущностей для кэширования**. Чтобы кэшировать сущности второго уровня, укажите соответствующую аннотацию `@Cache` на классах сущностей, которые вы хотите кэшировать. Например:

```java
@Entity
@Cache
public class MyEntity {
    // Поля и методы класса
}
```

5. **Cache Concurrency Strategy**

Hibernate предоставляет несколько встроенных стратегий, с помощью которых можно контролировать, какие данные будут кэшированы и как они будут обновляться или исключаться из кэша при выполнении операций чтения и записи.

- **Read-Only**. Эта стратегия предполагает, что данные в базе данных не изменяются и могут быть кэшированы только для чтения. Все запросы на запись приводят к сбросу данных из кэша. Это подходящая стратегия для данных, которые редко меняются и требуют высокой производительности при чтении;
    
- **Read-Write**. Эта стратегия позволяет кэшировать данные как для чтения, так и для записи. При изменении данных в базе данных, кэш будет автоматически обновлён для отражения изменений. Подходит для данных, которые часто изменяются, но требуют быстрого доступа при чтении;
    
- **Nonstrict Read-Write**. Эта стратегия позволяет кэшировать данные для чтения, и когда данные изменяются, они сначала обновляются в базе данных, а затем сбрасываются из кэша. Это предпочтительно для данных, которые не часто изменяются, но требуют более гибкого подхода к обновлению кэша;
    
- **Transactional**. Эта стратегия предполагает, что данные будут кэшироваться только в рамках транзакции. Когда транзакция завершается, данные сбрасываются из кэша. Подходит для данных, которые часто изменяются и требуют точного контроля над обновлением кэша.
    

Стратегию можно установить с помощью аннотации `@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)` на классе или на поле.

6. **CacheMode** — определяет, какие данные будут кэшироваться во втором уровне кэша и каким образом они будут использоваться в процессе выполнения сессий. В Hibernate есть несколько режимов работы кэша второго уровня:

- `NORMAL`. Это режим по умолчанию. В этом режиме Hibernate использует кэш второго уровня для кэширования сущностей и коллекций, которые были явно помечены аннотациями `@Cacheable` или настройками XML. Также кэшируются результаты запросов (Query Cache) и другие данные, которые могут быть сконфигурированы для кэширования;
    
- `GET`. В этом режиме Hibernate использует кэш второго уровня только для кэширования данных, которые были получены через метод `Session.get()` или `Session.load()`. Это позволяет избежать кэширования данных, полученных через другие методы, например, `Session.createQuery()`;
    
- `PUT`. В этом режиме Hibernate использует кэш второго уровня только для кэширования данных, которые были сохранены через метод `Session.save()` или `Session.update()`. Это позволяет избежать кэширования данных, полученных из базы данных, но не сохранённых в кэше;
    
- `REFRESH`. В этом режиме Hibernate всегда обновляет данные из базы данных, несмотря на наличие данных в кэше. Это полезно, когда вы хотите, чтобы данные всегда были актуальными и не кэшировались;
    
- `IGNORE`. Полезен в ситуациях, когда вы хотите отключить полностью кэширование второго уровня для определённых сущностей или запросов, например, когда вы знаете, что данные часто меняются и кэширование не приведет к значительному улучшению производительности.
    

Пример установки CacheMode:

```java
Session session = sessionFactory.openSession();
session.setCacheMode(CacheMode.IGNORE);

// Выполнение операций с базой данных, которые не будут кэшироваться
...
```

### **Query Cache**

Это часть кэша второго уровня в Hibernate, которая позволяет кэшировать результаты запросов к базе данных. Он предназначен для кэширования метаданных запросов и соответствующих результатов запросов для повторного использования при выполнении одинаковых запросов.

```java
spring.jpa.properties.hibernate.cache.use_query_cache: true
```

Если хотим кэшировать результаты запросов, то нужно указать это явно используя `QueryHint:`

```java
entityManager.createQuery("select f from Foo f")
  .setHint("org.hibernate.cacheable", true)
  .getResultList();
```

Либо делать это с помощью аннотаций, добавив `@QueryHints` к методам репозитория с атрибутом `@QueryHint` для настройки кэширования.

```java
@Repository
public interface MyEntityRepository extends JpaRepository<MyEntity, Long> {

    @QueryHints(@QueryHint(name = org.hibernate.annotations.QueryHints.CACHEABLE, value = "true"))
    @Query("SELECT e FROM MyEntity e WHERE e.status = :status")
    List<MyEntity> findByStatus(@Param("status") String status);
}
```

Это может улучшить производительность, если запрос выполняется часто с одними и теми же параметрами.

## Lazy fetch & Eager fetch

Lazy fetch или Ленивая загрузка — это шаблон проектирования, который мы используем для отсрочки инициализации объекта до тех пор, пока этот объект реально не потребуется приложению для работы. Противоположность ему - Eager fetch - тоже шаблон проектирования, в котором инициализация данных происходит на месте, т.е. сразу.

### Lazy fetch (по умолчанию стоит в `@OneToMany` и `@ManyToMany`)

Преимущества:

- Эффективность загрузки: Ленивое извлечение позволяет загружать связанные данные только в том случае, если они действительно понадобятся. Это может значительно улучшить производительность запросов.
    
- Экономия ресурсов: Если часть связанных данных редко используется, ленивое извлечение позволяет избежать ненужной загрузки и потребления памяти.
    

Недостатки:

- Дополнительные запросы: Ленивое извлечение может потребовать дополнительных запросов к базе данных, когда связанные данные фактически понадобятся.
    
- Проблемы с исключениями: При использовании ленивого извлечения, если попытаться получить доступ к связанным данным за пределами транзакции, возникнет исключение `LazyInitializationException`.

### Eager fetch (по умолчанию стоит в `@OneToOne` и `@ManyToOne`)

Преимущества:

- Отсутствие влияния на производительность, связанного с задержкой инициализации
    
- Простота использования: В режиме жадного извлечения, все связанные сущности загружаются сразу, что упрощает доступ к данным внутри транзакции.
    
- Минимизация проблем с `LazyInitializationException`: Жадное извлечение помогает избежать исключений, связанных с ленивой инициализацией (например, `LazyInitializationException`), так как все данные уже загружены.
    

Недостатки:

- Избыточная загрузка: Если нам не всегда требуются все связанные данные, то использование жадного извлечения может привести к избыточной загрузке данных и снижению производительности запросов.
    
- Неэффективность: Если большинство времени связанные данные не будут использованы, режим жадного извлечения может привести к ненужному расходу ресурсов.

### LazyInitializationException

LazyInitializationException — считается одной из самых распространённых исключений при работе с `Hibernate`. Возникает она при попытке извлечь зависимые данные (при стратегии `FetchType.LAZY`) вне сессии, с которой была подгружена родительская сущность.

Использование `FetchType.EAGER` избавит вас от этой проблемы, но это не лучшее решение, т.к. нам не всегда нужны все зависимые объекты.

## N+1 problem
Проблема N+1 — это распространённая проблема производительности, которая может возникнуть при использовании Hibernate, других ORM-фреймворков и даже при прямом использовании SQL. Она проявляется, когда в вашем приложении выполняется N+1 запросов к базе данных вместо одного оптимального запроса. И чем больше значение N, тем больше запросов будет выполнено, и тем больше будет накладных расходов на производительность.

 Оптимизация (JOIN FETCH)
  `JOIN FETCH` vs `JOIN`:

Если бы запрос был с обычным `join`:

```
SELECT p FROM Post p JOIN p.comments
```

Мы вернули бы `hibernate` только посты, имеющие связь хоть с одним комментарием.

В случае `JOIN FETCH`, возвращаются посты и все связанные с ними комментарии одним запросом. Это особенно полезно, если есть уверенность, что все связанные комментарии нам понадобятся, иначе это излишний расход ресурсов.

💡 Если вы не используете `join fetch`, но связанные комментарии продолжают возвращаться, значит в ассоциации сущностей стоит стратегия извлечения — `EAGER`

## Batch fetching

Batch fetching — это техника, используемая в запросах к базе данных для повышения производительности и уменьшения количества отдельных запросов, выполняемых приложением. Она особенно полезна в ситуациях, когда приложению необходимо получить большое количество связанных объектов из базы данных.

Суть этого подхода заключается в том, что когда вы запрашиваете Hibernate загрузить эти сущности, он "собирает" несколько таких запросов в один. Hibernate, вместо множества запросов на каждую сущность, делает один запрос для всех сразу, `select * FROM table where id IN (?, ?, ?, …., ?)`, где размер блока IN — как раз и есть batch size.

 💡 Некоторые базы данных имеют ограничение на количество элементов, которые можно включить в `IN` блок. Внимательно читайте документацию используемой базы данных перед использованием данного подхода.

Существует несколько способов реализовать batch fetching, первая и самая популярная из них — аннотация `@BatchSize` над зависимыми сущностями. Единственный параметр — `size`, где мы и выставляем размер батча.

`@EntityGraph` — это механизм в Hibernate/JPA для **динамического управления жадной (EAGER) загрузкой связей** на уровне конкретного запроса. Он решает проблему N+1, позволяя в одном SQL-запросе загрузить корневую сущность и все её связанные коллекции или поля (через `JOIN FETCH`), вместо того чтобы делать дополнительные запросы для каждой связи.

**Ключевая цель:** Заменить несколько `SELECT`'ов одним оптимальным запросом с `JOIN`, избегая N+1.

## Entity lifecycle
**1. Transient (Временное состояние)**

- Объект создан через `new`, но не ассоциирован с сессией Hibernate
    
- Не имеет идентификатора (ID)
    
- Не отслеживается Hibernate
    
- Изменения не сохраняются в БД
    

**2. Managed (Персистентное/управляемое состояние)**

- Объект ассоциирован с сессией через `save()`, `persist()` или загрузку
    
- Имеет идентификатор
    
- Отслеживается Hibernate - изменения автоматически синхронизируются с БД
    
- Находится в кэше первого уровня
    

**3. Detached (Отсоединенное состояние)**

- Ранее управляемый объект после закрытия сессии
    
- Имеет идентификатор
    
- Не отслеживается Hibernate
    
- Изменения не сохраняются автоматически
    
- Можно повторно прикрепить через `merge()` или `update()`
    

**4. Removed (Удаляемое состояние)**

- Объект помечен на удаление через `delete()` или `remove()`
    
- Будет удален из БД при коммите транзакции
    
- После коммита переходит в transient состояние
    

**Ключевой момент:** Hibernate автоматически управляет синхронизацией только для managed-объектов.
