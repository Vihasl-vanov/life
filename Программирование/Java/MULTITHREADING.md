## Поток vs Процесс
- **Процесс — это отдельное приложение.** У него своя собственная память, и он не может просто так "залезть" в данные другого приложения.
    
- **Поток — это "поток выполнения" внутри приложения.** Все потоки одного приложения работают с общими данными, поэтому им нужно аккуратно договариваться, кто и в какой момент эти данные меняет.

## Запуск задачи в отдельном потоке в Java

 Поток — это сущность на уровне операционной системы, которая умеет помещать задачу на отдельное ядро процессора или в пул задач для параллельного выполнения.


 Наследование от класса Thread. Класс `Thread` содержит логику взаимодействия с ОС для запуска потоков.
```java
class MyThread extends Thread {
    public void run() {
        // Логика выполнения задачи
        System.out.println("Выполняется в отдельном потоке");
    }
}

// Запуск
MyThread thread = new MyThread();
thread.start();  // Важно использовать start(), а не run()
```

Реализовать интерфейс Runnable
```java
class MyRunnable implements Runnable {
    public void run() {
        // Логика выполнения задачи
        System.out.println("Выполняется в отдельном потоке");
    }
}

// Запуск
Thread thread = new Thread(new MyRunnable());
thread.start();
```

Использование ExecutorService - это предпочтительный способ
```java
ExecutorService executor = Executors.newSingleThreadExecutor();
executor.submit(() -> {
    // Логика выполнения задачи
    System.out.println("Выполняется в отдельном потоке");
});

// Не забываем закрыть ExecutorService когда он больше не нужен
executor.shutdown();
```

Через CompletableFuture
```java
CompletableFuture.runAsync(() -> {
    // Логика выполнения задачи
    System.out.println("Выполняется асинхронно");
});
```

- Всегда предпочтительнее использовать Runnable или Callable, чем наследование от Thread
- Executor Framework предоставляет более гибкое управление потоками и пулами потоков
- Для возврата результата из потока можно использовать Callable вместо Runnable
- В production-коде лучше использовать пулы потоков (ThreadPoolExecutor), а не создавать потоки напрямую

## Отличия между Thread и Runnable в Java
**Основные отличия**

1. **Способ реализации**:
    - `Thread` - это класс, от которого нужно наследоваться
    - `Runnable` - это интерфейс, который нужно реализовать
2. **Инкапсуляция**:
    - `Runnable` лучше соответствует принципу инкапсуляции, так как разделяет логику выполнения (метод `run()`) от механизма выполнения (поток)
    - `Thread` объединяет и то, и другое в одном классе
3. **Наследование**:
    - При использовании `Thread` вы теряете возможность наследовать от другого класса (Java не поддерживает множественное наследование)
    - `Runnable` не ограничивает иерархию наследования
4. **Повторное использование**:
    - `Runnable` можно передавать в разные экземпляры `Thread`
    - `Thread` менее гибок для повторного использования
5. **Ресурсы**:
    - Создание нового `Thread` каждый раз дороже, чем использование одного потока с разными `Runnable`

### Практические рекомендации
1. **Когда использовать Runnable**:
    - Когда нужно разделить логику задачи от механизма выполнения
    - Когда задача должна быть выполнена в пуле потоков
    - Когда нужна большая гибкость архитектуры
2. **Когда использовать Thread**:
    - Когда нужно переопределить поведение потока (например, приоритет)
    - В простых приложениях с минимальными требованиями к архитектуре

"В современной Java разработке предпочтение отдается `Runnable` (или `Callable` для возврата результатов), так как это:

- Более гибкий подход
- Лучше соответствует принципам ООП
- Позволяет использовать пулы потоков
- Не занимает место в иерархии наследования

Класс `Thread` следует использовать только когда вам действительно нужно модифицировать поведение самого потока, что требуется довольно редко."

## Отличие между Thread.run() and Thread.start()
**`Thread.start()`**:
- Создает новый поток выполнения (выделяется новый call stack)
- JVM вызывает метод `run()` в контексте этого нового потока
- Выполнение происходит асинхронно (параллельно основному потоку)

**`Thread.run()`**:
- Просто вызывает метод `run()` как обычный метод
- Выполняется в том же потоке, где был вызван (синхронно)
- Не создает новый поток

```java
public class Example {
    public static void main(String[] args) {
        Thread thread = new Thread(() -> {
            System.out.println("Выполняется в: " + Thread.currentThread().getName());
        });
        
        thread.run();   // Выполнится в main
        thread.start(); // Выполнится в Thread-0
    }
}
```

Только метод `start()` запускает поток, то есть дает команду JVM создать новый поток и передать его в работу процессору. С этого момента созданный нами поток выполняется параллельно с основным, или лежит в пуле, если прямо сейчас нет свободного ядра, чтобы обработать его


## Volatile
Ключевое слово `volatile` используется для переменных, которые читаются множеством нитей, а пишутся одной. Когда переменная помечена как `volatile`, каждое чтение и запись будет производиться напрямую из памяти, а не из кэша потока. `Volatile` не гарантирует атомарность.

Единственная гарантия — это то, что мы не ходим в кэш, и это обеспечивает нам безопасную и консистентную запись/чтение/=. От изменения же мы не защищаемся.

## Immutable classes

**Неизменяемый класс (immutable class)** — это класс, экземпляры которого не могут быть изменены после создания. Все его поля должны быть объявлены как final и инициализированы в конструкторе.

Использование неизменяемых классов в многопоточном приложении помогает обеспечить безопасность потоков, так как они гарантируют, что их состояние не будет изменено другим потоком, что может привести к состоянию гонки (race condition) и другим проблемам синхронизации.
## ExecutorService
**интерфейс** (набор правил и методов), который описывает, как управлять выполнением задач в отдельных потоках

Основная идея **ExecutorService** — отделить **подачу задачи** от **механизма ее выполнения** . Вы просто говорите: "Вот задача, выполни ее, пожалуйста", а **ExecutorService** сам решает, как это сделать наилучшим образом, используя доступные потоки из своего пула потоков.

 **ExecutorService** предоставляет унифицированный способ запуска и контроля асинхронных операций.

**ExecutorService** работает с **пулом потоков** (thread pool). Это заранее созданный набор потоков, готовых к работе.

**1. FixedThreadPool (newFixedThreadPool(n))**

- **Фиксированное количество** потоков (n).
    
- **Использование:** Постоянная нагрузка. Оптимально для числа ядер процессора. Контроль ресурсов.

##  Synchronized
`synchronized` - это ключевое слово в Java, обеспечивающее синхронизацию потоков при доступе к общим ресурсам. Оно гарантирует, что только один поток в данный момент может выполнять синхронизированный блок кода или метод.

**Атомарная операция** — это операция, которая выполняется целиком и без переключения процессора во время ее выполнения на другие потоки с той же операцией. Это означает, что если два или более потоков одновременно выполняют одну и ту же атомарную операцию, то результат будет таким же, как если бы эти операции выполнялись последовательно одна за другой.

Процессор не сможет переключиться на выполнение другого потока где-то в середине синхронизованного кода

Lock — это интерфейс, представляющий блокировку. По сути, это просто объект, который отвечает за недоступность блока кода, в то время пока он выполняется каким-то потоком. Замком может быть любой объект ссылочного типа,

### Синхронизированные блоки vs методы

- **Синхронизированные методы**:
    - Проще в реализации
    - Весь метод блокируется
    - Может привести к излишней блокировке
- **Синхронизированные блоки**:
    - Более гибкие (можно указать конкретный монитор)
    - Можно синхронизировать только часть метода
    - Лучшая производительность за счет меньшей области блокировки

### Монитор и его привязка

Монитор может быть привязан к:

**Объекту** - когда используется синхронизированный метод экземпляра или блок с указанием объекта
```java
public synchronized void method() {} // монитор - this (текущий объект)
```

```java
synchronized(this) { /* блок кода */ }
```

**Классу** - когда используется синхронизированный статический метод или блок с классом
```java
public static synchronized void staticMethod() {} // монитор - Class object
```

```java
synchronized(MyClass.class) { /* блок кода */ }
```
### Поведение при многопоточном доступе
Когда несколько потоков пытаются вызвать синхронизированный метод:
1. Первый поток захватывает монитор (объекта или класса)
2. Другие потоки блокируются до освобождения монитора
3. После выхода из метода (или блока) монитор освобождается
4. Один из ожидающих потоков получает монитор и продолжает выполнение

```java
public class Counter {
    private int count = 0;
    
    public synchronized void increment() {
        count++; // операция атомарна благодаря synchronized
    }
}
```


## **`wait()` и `notify()` 

**`wait()`** и **`notify()`** — методы класса `Object`, низкоуровневый механизм синхронизации для многопоточной синхронизации.
- **`wait()`** — приостанавливает текущий поток и освобождает монитор.
- **`notify()`** — пробуждает **один** случайный поток, ожидающий на этом мониторе.
- **`notifyAll()`** — пробуждает **все** потоки, ожидающие на этом мониторе.

Вызываются **только на объекте-мониторе**, который удерживается текущим потоком:
```java
synchronized (lock) {
    lock.wait();     // Ожидание на lock
    lock.notify();   // Пробуждение ожидающего потока
}
```

**`wait()` и `notify()` требуют `synchronized` из-за:**
1. **Атомарности**
    - Без синхронизации возможна **гонка состояний** между проверкой условия и вызовом `wait()`.
2. **Удержания монитора**
    - `wait()` **освобождает** монитор, но для этого он должен быть сначала захвачен (`synchronized`).
3. **Избежание `IllegalMonitorStateException`**
    - Вызов `wait()`/`notify()` без синхронизации приведёт к исключению.

### **Шаблон использования (Producer-Consumer)**

```java
private final Queue<String> queue = new LinkedList<>();
private final Object lock = new Object();

// Producer
public void produce(String data) throws InterruptedException {
    synchronized (lock) {
        while (queue.size() >= 10) {
            lock.wait();  // Ждём, пока Consumer не освободит место
        }
        queue.offer(data);
        lock.notifyAll();  // Сообщаем Consumer, что данные готовы
    }
}

// Consumer
public String consume() throws InterruptedException {
    synchronized (lock) {
        while (queue.isEmpty()) {
            lock.wait();  // Ждём, пока Producer не добавит данные
        }
        String data = queue.poll();
        lock.notifyAll();  // Сообщаем Producer, что место освободилось
        return data;
    }
}
```

### Важные нюансы
✔ **Всегда используйте `while` вместо `if`**
- Из-за **ложных пробуждений** (`spurious wakeups`) условие может не выполняться после `wait()`.

✔ **Предпочитайте `notifyAll()`**
- `notify()` будит только один поток (может привести к deadlock, если разбудит не тот поток).

✔ **Не вызывайте `wait()` без условия**
- Это может привести к бесконечной блокировке.

### **Альтернативы в современном Java**
 **`Lock` + `Condition`** (из `java.util.concurrent.locks`)
 ```java
Lock lock = new ReentrantLock();
Condition notEmpty = lock.newCondition();
notEmpty.await();  // Аналог wait()
notEmpty.signal(); // Аналог notify()
```

**Блокирующие очереди** (`BlockingQueue`, `LinkedBlockingQueue`)

Итого
**Правила:**
1. Только в `synchronized`.
2. Всегда с проверкой условия в цикле (`while`).
3. Лучше использовать `notifyAll()`.
4. В новых проектах предпочитать `java.util.concurrent.*`.

## Что такое volatile?
Волотайл запрещает помещать поле в кэш процессора и мы всегда читаем из main memory. Он обеспечивает видимость изменений среди разных потоков, которые обращаются к одному значению. Не гарантирует атомарность.  В отличие от `synchronized`, volatile не вызывает блокировок потоков. Volatile переменные работают медленнее обычных, но быстрее, чем синхронизированный доступ.

## Что такое ThreadLocal?
`ThreadLocal` - это класс в Java, который позволяет создавать переменные, доступные только конкретному потоку. Каждый поток имеет свою собственную независимую копию переменной ThreadLocal.

Основные случаи применения ThreadLocal:

1. **Хранение контекста потока** - например, в веб-приложениях для хранения информации о пользовательской сессии
2. **Избегание синхронизации** - когда нужно, чтобы каждый поток работал со своей копией объекта
3. **Передача параметров** - через методы без явной передачи в аргументах
4. **Потокобезопасность** - так как каждый поток работает со своим экземпляром

**ключевые особенности**
1. **Изоляция данных** - каждый поток видит только свою версию переменной
2. **Автоматическая очистка** - при завершении потока его ThreadLocal-переменные могут быть собраны GC
3. **Память** - может вызывать утечки памяти, если не очищать (особенно в пулах потоков)

**важные методы**
- `get()` - возвращает значение для текущего потока
- `set(T value)` - устанавливает значение для текущего потока
- `remove()` - удаляет значение для текущего потока
- `initialValue()` - определяет начальное значение (можно переопределить)

ThreadLocal часто используется в:

- Веб-фреймворках (Spring, Servlet API)
- Логировании (MDC в Log4j/SLF4J)
- Транзакциях (Hibernate, JDBC)

## Atomic classes and CAS
это набор классов, которые предоставляют атомарные операции над переменными.
CAS - это операция, которая выполняет три действия **атомарно** (как одно целое):
1. **Сравнивает** текущее значение в памяти с ожидаемым значением
2. **Если значения совпадают** - записывает новое значение
3. **Если не совпадают** - ничего не делает

Возвращает `true`, если замена произошла, и `false` - если нет.

```java
import java.util.concurrent.atomic.AtomicInteger;

public class CasExample {
    public static void main(String[] args) {
        AtomicInteger counter = new AtomicInteger(0);
        
        // Поток 1 пытается изменить 0 → 1
        boolean success1 = counter.compareAndSet(0, 1);
        System.out.println("Попытка 1: " + success1); // true
        
        // Поток 2 пытается изменить 0 → 2 (но значение уже 1)
        boolean success2 = counter.compareAndSet(0, 2);
        System.out.println("Попытка 2: " + success2); // false
        
        System.out.println("Итоговое значение: " + counter.get()); // 1
    }
}
```


## ThreadPool концепция и реализация

ThreadPool (пул потоков) — это механизм для управления множеством потоков, который позволяет:
- **Переиспользовать потоки** вместо создания новых для каждой задачи
- **Ограничивать количество одновременно работающих потоков**
- **Эффективно управлять ресурсами системы**

Почему нельзя создавать потоки на каждую операцию? Потому что это очень дорогостоящая и долгая операция.

**Основные компоненты ThreadPool:**

- **Рабочие потоки (Worker Threads):** Потоки, которые постоянно находятся в ожидании задач и выполняют их по мере поступления.
- **Очередь задач (Task Queue):** Структура данных, в которую помещаются задачи для последующего выполнения рабочими потоками.
- **Менеджер пула (Pool Manager):** Компонент, отвечающий за управление количеством потоков, распределение задач и обработку ошибок.

**Варианты реализации**
 **ThreadPoolExecutor (базовый вариант)**
 ```java
 ThreadPoolExecutor executor = new ThreadPoolExecutor(
    5, // corePoolSize
    10, // maximumPoolSize
    60, // keepAliveTime
    TimeUnit.SECONDS, // единицы измерения времени
    new LinkedBlockingQueue<>() // очередь задач
);
```
**FixedThreadPool** — фиксированное количество потоков:
```java
ExecutorService executor = Executors.newFixedThreadPool(4);
executor.submit(() -> {
    // Ваша задача
});
executor.shutdown();
```
**CachedThreadPool** — создает потоки по мере необходимости:
```java
ExecutorService cachedPool = Executors.newCachedThreadPool();
```
**SingleThreadExecutor** — один поток (очередь задач):
```java
ExecutorService singleThread = Executors.newSingleThreadExecutor();
```
**ScheduledThreadPool** — пул для отложенных задач:
```java
ScheduledExecutorService scheduled = Executors.newScheduledThreadPool(2);
scheduled.schedule(() -> System.out.println("Done"), 1, TimeUnit.SECONDS);
```
 
 **Очереди задач**
- **SynchronousQueue** — передача задачи прямо в поток
- **LinkedBlockingQueue** — неограниченная очередь (риск OOM)
- **ArrayBlockingQueue** — очередь с ограниченным размером

 **Политики отказа**
 Когда очередь заполнена и все потоки заняты:
- **AbortPolicy** — бросает RejectedExecutionException
- **CallerRunsPolicy** — выполняет задачу в вызывающем потоке
- **DiscardPolicy** — молча отбрасывает задачу
- **DiscardOldestPolicy** — удаляет самую старую задачу

## ForkJoinPool
ForkJoinPool — это специальный ExecutorService, предназначенный для эффективного выполнения задач, которые можно рекурсивно разбивать на подзадачи (fork), а затем объединять результаты (join). Используется в  parallel stream

Основные особенности и назначение:
1. **Оптимизация для рекурсивного параллелизма**:
    - Идеально подходит для "разделяй и властвуй" алгоритмов
    - Эффективен для задач, которые можно разбивать на независимые подзадачи
2. **Work-stealing алгоритм**:
    - Каждый поток имеет свою очередь задач (deque)
    - Если у потока заканчиваются задачи, он "ворует" задачи из хвоста очереди другого потока
    - Минимизирует простои потоков
3. **Отличия от ThreadPoolExecutor**:
    - В обычном пуле потоки ждут в голове общей очереди
    - В ForkJoinPool потоки активно ищут работу, когда их очередь пуста

 Основные компоненты:
1. **ForkJoinTask** — базовая абстракция задачи (обычно используют его подклассы):
    - `RecursiveAction` — для задач без возвращаемого результата
    - `RecursiveTask` — для задач с возвращаемым результатом
2. **ForkJoinWorkerThread** — специальные потоки пула

 Типичные use cases:
1. Параллельная обработка деревьев/графов
2. Рекурсивные алгоритмы (быстрая сортировка, merge sort)
3. Параллельные вычисления (MapReduce-подобные задачи)
4. Обработка больших массивов данных

**Почему не использовать обычный ThreadPool?**

1. **Эффективность**:
    - Work-stealing лучше балансирует нагрузку
    - Меньше contention (конкуренции) за общие ресурсы
2. **Удобство для рекурсивных задач**:
    - Автоматическое разделение и объединение результатов
    - Оптимальное планирование родительских/дочерних задач
3. **Меньшие накладные расходы**:
    - Локальные очереди уменьшают синхронизацию
    - Лучше использует процессорные ядра

## Что такое `Semaphore`?
Семафор — это счетчик, ограничивающий количество потоков, которые могут одновременно получить доступ к ресурсу.

**Как работает?**

- Имеет **количество "разрешений" (permits)**
- `acquire()` — блокирует, если разрешений нет
- `release()` — освобождает разрешение

```java
Semaphore semaphore = new Semaphore(3); // максимум 3 потока

void accessResource() {
    semaphore.acquire();  // ждём разрешения
    try {
        // работа с ресурсом (не более 3 потоков одновременно)
    } finally {
        semaphore.release();  // освобождаем
    }
}
```
## Race condition

**Race Condition** — это ошибка в многопоточном программировании, когда результат выполнения программы зависит от порядка выполнения потоков, что может приводить к недетерминированному поведению и некорректным данным.

Race Condition возникает, когда **два или более потока** одновременно обращаются к **общему ресурсу** (переменной, файлу, структуре данных), и хотя бы один из потоков **изменяет** этот ресурс.

Как предотвратить?
- **Синхронизация (`synchronized`)**
- **Атомарные классы (`AtomicInteger`, `AtomicReference`)**
- **Lock-механизмы (`ReentrantLock`)**
- **Потокобезопасные коллекции (`ConcurrentHashMap`, `CopyOnWriteArrayList`)**

## Java Memory Model
Это набор правил, определяющий, как потоки в Java взаимодействуют с памятью, гарантируя **видимость изменений** и **порядок операций** в многопоточной среде.
#### **Основные концепции:**

1. **Happens-Before**  
    — гарантирует, что если операция A _«предшествует»_ операции B, то результат A виден для B.  
    _Пример:_ `synchronized`, `volatile`, `Thread.start()`.
    
2. **Visibility (Видимость)**  
    — изменения переменной в одном потоке могут быть не видны другому без синхронизации.  
    _Решение:_ `volatile`, `final`, атомарные классы (`AtomicInteger`).
    
3. **Reordering (Переупорядочивание)**  
    — JVM/процессор может оптимизировать код, меняя порядок инструкций, если это не нарушает _happens-before_.
	Решение:_ `volatile`

## ReentrantLock

`ReentrantLock` — это реализация интерфейса `Lock`. Это так называемая **повторно входимая (reentrant)** блокировка.

**Ключевые особенности:**

1. **Повторный вход (Reentrancy):** Это самое важное свойство. Поток, который уже владеет блокировкой, может безопасно захватить её снова без риска взаимной блокировки (deadlock) самого себя. Счётчик владений увеличивается при каждом `lock()` и уменьшается при каждом `unlock()`. Блокировка освобождается только когда счётчик достигает нуля.
    
    - _Пример:_ Рекурсивный вызов метода, синхронизированного одним и тем же lock.
        
2. **Честность (Fairness):** Конструктор `ReentrantLock` принимает параметр `fairness` (честность).
    
    - **Нечестный режим (по умолчанию):** `new ReentrantLock(false)`. При освобождении блокировки её получит случайный ждущий поток. Это даёт производительность, но может привести к "голоданию" (starvation) некоторых потоков.
        
    - **Честный режим:** `new ReentrantLock(true)`. Блокировка будет предоставляться потокам строго в порядке очереди (FIFO). Производительность ниже, но справедливость гарантирована.
        
3. **Возможность попытаться захватить lock:** В отличие от `synchronized`, `ReentrantLock` предоставляет более гибкие методы:
    
    - `tryLock()`: Пытается захватить блокировку _немедленно_. Возвращает `true`, если удалось, `false` — если нет. Поток не блокируется навсегда.
        
    - `tryLock(long timeout, TimeUnit unit)`: Пытается захватить блокировку в течение заданного времени. Идеально для избежания deadlock.
        
    - `lockInterruptibly()`: Позволяет прервать поток, который ждёт захвата блокировки.
        
4. **Условные переменные (Condition):** Позволяет создавать несколько очередей ожидания для одной блокировки с помощью `newCondition()`. Это более гибкая альтернатива `wait()/notify()`. Например, можно иметь отдельные условия "очередь пуста" и "очередь полна" в bounded buffer.

## ReadWriteLock / ReentrantReadWriteLock

Это не отдельный lock, а пара блокировок: одна на чтение, другая — на запись.

- **Идея:** Разделить доступ к ресурсу по операциям "чтение" и "запись".
    
- **Принцип:**
    
    - **Многие читатели:** Если никто не пишет, множество потоков могут одновременно читать данные.
        
    - **Один писатель:** Если один поток пишет, другие потоки (как читатели, так и писатели) блокируются.
        
- `ReentrantReadWriteLock` — основная реализация. Она также повторно входима и может быть честной/нечестной.
    

**Применение:** Идеально для структур данных (например, кэшей), где операции чтения сильно преобладают над операциями записи. Это даёт значительный прирост производительности по сравнению с исключительной блокировкой.

```java
ReadWriteLock rwLock = new ReentrantReadWriteLock();

// Для чтения
public Data readData() {
    rwLock.readLock().lock();
    try {
        // Много потоков могут читать здесь одновременно
        return data;
    } finally {
        rwLock.readLock().unlock();
    }
}

// Для записи
public void writeData(Data newData) {
    rwLock.writeLock().lock();
    try {
        // Только один поток может писать здесь
        data = newData;
    } finally {
        rwLock.writeLock().unlock();
    }
}
```

## StampedLock (появился в Java 8)

Это более современная и производительная альтернатива `ReentrantReadWriteLock`.

**Ключевые особенности:**

1. **Оптимистичная блокировка чтения:** Основная "фишка". Поток при чтении получает **штамп (stamp)** — своего рода номер версии. После выполнения операций поток проверяет, не изменились ли данные пока он работал (не была ли захвачена блокировка на запись). Если нет — результат корректен. Если да — только тогда переходит на пессимистичную блокировку. Это позволяет избежать ненужных блокировок.
    
2. **Неповторяемость:** `StampedLock` **не является повторно входимым**. Попытка взвать блокировку в одном потоке дважды приведёт к deadlock.
    
3. **Поддерживает три режима:**
    
    - **Write (эксклюзивная запись):** Аналогична `writeLock` в `ReadWriteLock`.
        
    - **Read (пессимистичное чтение):** Аналогична `readLock` в `ReadWriteLock`.
        
    - **Optimistic Read (оптимистичное чтение):** Не блокирует других писателей.

## Пессимистичная блокировка

**Принцип:** "Заблокирую сначала - потом работаю"

- **Стратегия:** Предполагает конфликт данных по умолчанию
    
- **Механизм:** Полная эксклюзивная блокировка ресурса
    
- **Аналогия:** Забрать книгу в отдельную комнату и запереться
    
- **В Java:** `synchronized`, `ReentrantLock`, `ReadWriteLock.readLock()`
    
- **Гарантии:** Полная консистентность данных
    
- **Цена:** Более низкая производительность при частом чтении
    

## Оптимистичная блокировка

**Принцип:** "Работаю сначала - проверяю конфликт потом"

- **Стратегия:** Предполагает отсутствие конфликтов по умолчанию
    
- **Механизм:** Версионирование + проверка после работы
    
- **Аналогия:** Сделать копию книги, потом проверить не меняли ли оригинал
    
- **В Java:** `StampedLock.tryOptimisticRead()`, atomic-классы (CAS)
    
- **Гарантии:** Актуальность данных не гарантирована, нужна проверка
    
- **Цена:** Возможность переделывать работу при конфликте
    

### Ключевые различия

|Критерий|Пессимистичная|Оптимистичная|
|---|---|---|
|**Подход**|Блокировка на время работы|Работа + последующая проверка|
|**Производительность**|Ниже при частом чтении|Выше (читатели не блокируются)|
|**Гарантии**|Полная консистентность|Требует проверки актуальности|
|**Идеальный случай**|Частые изменения данных|Read-heavy workload, редкие конфликты|

###
Что говорить на собеседовании

"В Java есть два подхода к синхронизации. **Пессимистичный** - через явные locks (`ReentrantLock`), где мы гарантируем целостность данных полной блокировкой. И **оптимистичный** - через `StampedLock` или CAS-операции, где мы работаем без блокировки, но проверяем после работы, не изменились ли данные. Выбор зависит от сценария: при частых записях лучше пессимистичный подход, при редких изменениях - оптимистичный даёт выигрыш в производительности."

**Use cases:**
- Пессимистичная: банковские транзакции, частые обновления
    
- Оптимистичная: кэширование, статистика, read-heavy системы

## LongAdder
**Принцип разделения:** Вместо одной общей переменной (как в `AtomicLong`) использует **массив ячеек** (cells).

- **Низкая конкуренция:** Работает как `AtomicLong` (базовое значение `base`)
    
- **Высокая конкуренция:** Конфликтующие потоки начинают писать в свои ячейки массива
    
- **Итоговое значение:** `sum() = base + sum(cells[])`
    

 Ключевые преимущества

1. **Высокая пропускная способность** при записи в многопоточной среде
    
2. **Снижение contention** (конкуренции) за счет разделения переменной
    
3. **Лучшая масштабируемость** по сравнению с `AtomicLong`
    

Недостатки

1. **Большее потребление памяти** (из-за массива ячеек)
    
2. **Медленнее чтение** (`sum()`) - нужно просуммировать все ячейки![[Снимок экрана 2025-08-28 в 16.05.44.png]]
LongAdder использует технику динамического разделения переменной на несколько ячеек для уменьшения конкуренции при записи. Это дает выигрыш в производительности в высококонкурентных сценариях ценой большего расхода памяти и более медленного чтения итогового значения

## Асинхронность vs Параллелизм
**Параллелизм** позволяет разбить большую задачу на меньшие подзадачи, которые могут выполняться одновременно в отдельных потоках.
![[Снимок экрана 2025-08-31 в 09.48.59.png]]
Это позволяет сократить время выполнения общей задачи и увеличить производительность системы в целом. При этом, общий результат становится доступен только после полного завершения всех подзадач. При использовании параллелизма важно следить за синхронизацией потоков, чтобы избежать ошибок, связанных с изменением общих данных несколькими потоками одновременно.

**Асинхронность**, с другой стороны, позволяет выполнить несколько независимых друг от друга или частично зависимых задач. Каждая асинхронная задача выполняется в своем потоке и не знает о других асинхронных задачах.
![[Снимок экрана 2025-08-31 в 09.49.25.png]]
Однако, в некоторых случаях, задачи могут быть зависимыми, и результат одной задачи может быть необходим для выполнения другой задачи. В этих случаях может происходить блокирование, когда результаты той задачи, от которой зависит другая задача, ещё не доступны.

## Future
`Future` представляет собой объект, который обещает вернуть результат выполнения асинхронной операции в будущем. `Future` даёт возможность получить результат асинхронной операции в будущем, не блокируя текущий поток до завершения операции.

Можно создать несколько `Future`-объектов для каждой отдельной операции, и использовать метод `Future.get()` для получения результатов каждой из них. Чтобы проверить, готов ли уже результат, можно вызвать метод `isDone()`, и если результат ещё не готов, то основной поток может, пока что, делать что-то другое.

`Future` — `generic`, он содержит в себе тип того результата, который однажды в нем появится.

Для возвращения какого-либо значения из задачи в другом потоке используется интерфейс `Callable`, на основе которого создается лямбда. Этот интерфейс определяет метод `call()`, который должен быть реализован классом, который его реализует.

## CompletableFuture
 CompletableFuture представляет собой более продвинутую версию `Future`, которая позволяет задавать цепочки операций, которые будут выполняться после завершения асинхронной задачи.

Одним из основных преимуществ `CompletableFuture` является возможность задавать колбэки, которые будут вызваны при завершении операции. Например, метод `thenApply()` позволяет применить функцию к результату выполненной операции, в то время как метод `thenAccept()` позволяет выполнить определенное действие, не возвращая никакого значения.
```java
CompletableFuture<List<Integer>> futureNumbers = getNumbers();

futureNumbers.thenApply(numbers -> numbers.stream()
        .map(num -> num * 2)        // умножаем каждое число на 2
        .collect(Collectors.toList()))
    .thenApply(numbers -> numbers.stream()
        .filter(num -> num >= 10)   // оставляем только числа, которые больше или равны 10
        .collect(Collectors.toList()))
    .thenApply(numbers -> numbers.stream()
        .reduce(0, Integer::sum))   // суммируем оставшиеся числа
    .thenAccept(sum -> System.out.println("Сумма оставшихся чисел: " + sum));
```
Класс `CompletableFuture` также предоставляет возможность объединения нескольких асинхронных операций в одну последовательность. Для этого можно использовать методы `thenCompose()` и `thenCombine()`. Метод `thenCompose()` позволяет запускать новую асинхронную операцию на основе результата предыдущей, в то время как метод `thenCombine()` позволяет комбинировать результаты двух асинхронных операций.

- `thenRun()` — выполняет заданное действие после завершения операции и не возвращает результат;
    
- `exceptionally()` — обрабатывает исключение, которое может возникнуть в результате выполнения операции;
    
- `handle()` — обрабатывает результат или исключение, которые могут возникнуть в результате выполнения операции;
    
- `join()` — блокирует текущий поток до тех пор, пока `CompletableFuture` не завершится и возвращает результат операции;
    
- `allOf()` — выполняет несколько асинхронных операций параллельно и возвращает `CompletableFuture`, который завершится, когда все операции будут завершены;
    
- `anyOf()` — выполняет несколько асинхронных операций параллельно и возвращает `CompletableFuture`, который завершится, когда любая из операций завершится;
    
- `complete()` — завершает `CompletableFuture` с заданным результатом;
    
- `completeExceptionally()` — завершает `CompletableFuture` с заданным исключением;
    
- `get()` — блокирует текущий поток до тех пор, пока операция, связанная с `CompletableFuture`, не будет завершена, и возвращает результат этой операции.
    


## Проблемы синхронизации

1. **Deadlock (Взаимная блокировка)** — это ситуация, когда два или более потоков блокируют друг друга, ожидая, когда другой поток освободит заблокированный ресурс. Ни один из потоков не может продвинуться в своей работе, что приводит к застою в работе приложения.
    
2. **Livelock (Активная блокировка)** — это ситуация, когда два или более потоков активно меняют свое состояние в ответ на действия друг друга, но не продвигаются в работе. В отличие от deadlock, потоки в livelock не блокируют друг друга, но они не могут закончить свою работу, так как постоянно ожидают, что другой поток выполнит свою часть работы.
    
3. **Starvation (Голодание)** — это ситуация, когда один или несколько потоков не могут получить доступ к общим ресурсам из-за постоянной занятости другими потоками. В результате потоки, которые ждут доступа к ресурсам, не могут продвигаться в своей работе, что приводит к замедлению работы приложения.
    
4. **Lock contention (Борьба за блокировку)** — это ситуация, когда несколько потоков конкурируют за доступ к одному и тому же заблокированному ресурсу. Это может привести к замедлению работы приложения и увеличению времени ожидания доступа к ресурсу.

**Диагностика deadlock в Java:**

1. **Профилировщики** (JProfiler, VisualVM) — отслеживают блокировки в реальном времени.
    
2. **Утилита jstack** — выводит дамп стеков потоков. Команда: `jstack <pid>`. В выводе ищется информация о заблокированных потоках и удерживаемых ими ресурсах.
    
3. **Отладчик (debugger)** — пошаговое выполнение с брейкпоинтами для анализа состояния потоков.

## CountDownLatch

`CountDownLatch` — это класс, предназначенный для синхронизации потоков, которые ждут, пока определённое количество операций завершится. Он позволяет одному или нескольким потокам ждать, пока не завершится определённое количество операций, и только после этого продолжить свою работу;

## CyclicBarrier

`CyclicBarrier` — это класс, предназначенный для синхронизации нескольких потоков, которые ждут друг друга до определенного момента. Он позволяет синхронизировать несколько потоков, чтобы они ждали друг друга до того, как продолжить свою работу;

## ForkJoinPool

`ForkJoinPool` — реализация `ExecutorService`, предназначенная для решения задач, связанных с параллельными вычислениями. Этот класс использует пул потоков и позволяет делать форки и джойны задач. Stream API использует `ForkJoinPool` для выполнения параллельных операций. Когда вызывается метод `parallelStream()` для коллекции, Stream API автоматически создаёт экземпляр `ForkJoinPool` и использует его для распределения работы между несколькими потоками.
