## Запуск задачи в отдельном потоке в Java

 Поток — это сущность на уровне операционной системы, которая умеет помещать задачу на отдельное ядро процессора или в пул задач для параллельного выполнения.


 Наследование от класса Thread. Класс `Thread` содержит логику взаимодействия с ОС для запуска потоков.
```java
class MyThread extends Thread {
    public void run() {
        // Логика выполнения задачи
        System.out.println("Выполняется в отдельном потоке");
    }
}

// Запуск
MyThread thread = new MyThread();
thread.start();  // Важно использовать start(), а не run()
```

Реализовать интерфейс Runnable
```java
class MyRunnable implements Runnable {
    public void run() {
        // Логика выполнения задачи
        System.out.println("Выполняется в отдельном потоке");
    }
}

// Запуск
Thread thread = new Thread(new MyRunnable());
thread.start();
```

Использование ExecutorService - это предпочтительный способо
```java
ExecutorService executor = Executors.newSingleThreadExecutor();
executor.submit(() -> {
    // Логика выполнения задачи
    System.out.println("Выполняется в отдельном потоке");
});

// Не забываем закрыть ExecutorService когда он больше не нужен
executor.shutdown();
```

Через CompletableFuture
```java
CompletableFuture.runAsync(() -> {
    // Логика выполнения задачи
    System.out.println("Выполняется асинхронно");
});
```

- Всегда предпочтительнее использовать Runnable или Callable, чем наследование от Thread
- Executor Framework предоставляет более гибкое управление потоками и пулами потоков
- Для возврата результата из потока можно использовать Callable вместо Runnable
- В production-коде лучше использовать пулы потоков (ThreadPoolExecutor), а не создавать потоки напрямую

## Отличия между Thread и Runnable в Java
**Основные отличия**

1. **Способ реализации**:
    - `Thread` - это класс, от которого нужно наследоваться
    - `Runnable` - это интерфейс, который нужно реализовать
2. **Инкапсуляция**:
    - `Runnable` лучше соответствует принципу инкапсуляции, так как разделяет логику выполнения (метод `run()`) от механизма выполнения (поток)
    - `Thread` объединяет и то, и другое в одном классе
3. **Наследование**:
    - При использовании `Thread` вы теряете возможность наследовать от другого класса (Java не поддерживает множественное наследование)
    - `Runnable` не ограничивает иерархию наследования
4. **Повторное использование**:
    - `Runnable` можно передавать в разные экземпляры `Thread`
    - `Thread` менее гибок для повторного использования
5. **Ресурсы**:
    - Создание нового `Thread` каждый раз дороже, чем использование одного потока с разными `Runnable`

### Практические рекомендации
1. **Когда использовать Runnable**:
    - Когда нужно разделить логику задачи от механизма выполнения
    - Когда задача должна быть выполнена в пуле потоков
    - Когда нужна большая гибкость архитектуры
2. **Когда использовать Thread**:
    - Когда нужно переопределить поведение потока (например, приоритет)
    - В простых приложениях с минимальными требованиями к архитектуре

"В современной Java разработке предпочтение отдается `Runnable` (или `Callable` для возврата результатов), так как это:

- Более гибкий подход
- Лучше соответствует принципам ООП
- Позволяет использовать пулы потоков
- Не занимает место в иерархии наследования

Класс `Thread` следует использовать только когда вам действительно нужно модифицировать поведение самого потока, что требуется довольно редко."

## Отличие между Thread.run() and Thread.start()
**`Thread.start()`**:
- Создает новый поток выполнения (выделяется новый call stack)
- JVM вызывает метод `run()` в контексте этого нового потока
- Выполнение происходит асинхронно (параллельно основному потоку)

**`Thread.run()`**:
- Просто вызывает метод `run()` как обычный метод
- Выполняется в том же потоке, где был вызван (синхронно)
- Не создает новый поток

```java
public class Example {
    public static void main(String[] args) {
        Thread thread = new Thread(() -> {
            System.out.println("Выполняется в: " + Thread.currentThread().getName());
        });
        
        thread.run();   // Выполнится в main
        thread.start(); // Выполнится в Thread-0
    }
}
```

Только метод `start()` запускает поток, то есть дает команду JVM создать новый поток и передать его в работу процессору. С этого момента созданный нами поток выполняется параллельно с основным, или лежит в пуле, если прямо сейчас нет свободного ядра, чтобы обработать его


##  Synchronized
`synchronized` - это ключевое слово в Java, обеспечивающее синхронизацию потоков при доступе к общим ресурсам. Оно гарантирует, что только один поток в данный момент может выполнять синхронизированный блок кода или метод.

**Атомарная операция** — это операция, которая выполняется целиком и без переключения процессора во время ее выполнения на другие потоки с той же операцией. Это означает, что если два или более потоков одновременно выполняют одну и ту же атомарную операцию, то результат будет таким же, как если бы эти операции выполнялись последовательно одна за другой.

Процессор не сможет переключиться на выполнение другого потока где-то в середине синхронизованного кода

Lock — это интерфейс, представляющий блокировку. По сути, это просто объект, который отвечает за недоступность блока кода, в то время пока он выполняется каким-то потоком. Замком может быть любой объект ссылочного типа,

### Синхронизированные блоки vs методы

- **Синхронизированные методы**:
    - Проще в реализации
    - Весь метод блокируется
    - Может привести к излишней блокировке
- **Синхронизированные блоки**:
    - Более гибкие (можно указать конкретный монитор)
    - Можно синхронизировать только часть метода
    - Лучшая производительность за счет меньшей области блокировки

### Монитор и его привязка

Монитор может быть привязан к:

**Объекту** - когда используется синхронизированный метод экземпляра или блок с указанием объекта
```java
public synchronized void method() {} // монитор - this (текущий объект)
```

```java
synchronized(this) { /* блок кода */ }
```

**Классу** - когда используется синхронизированный статический метод или блок с классом
```java
public static synchronized void staticMethod() {} // монитор - Class object
```

```java
synchronized(MyClass.class) { /* блок кода */ }
```
### Поведение при многопоточном доступе
Когда несколько потоков пытаются вызвать синхронизированный метод:
1. Первый поток захватывает монитор (объекта или класса)
2. Другие потоки блокируются до освобождения монитора
3. После выхода из метода (или блока) монитор освобождается
4. Один из ожидающих потоков получает монитор и продолжает выполнение

```java
public class Counter {
    private int count = 0;
    
    public synchronized void increment() {
        count++; // операция атомарна благодаря synchronized
    }
}
```


## **`wait()` и `notify()` 

**`wait()`** и **`notify()`** — методы класса `Object`, низкоуровневый механизм синхронизации для многопоточной синхронизации.
- **`wait()`** — приостанавливает текущий поток и освобождает монитор.
- **`notify()`** — пробуждает **один** случайный поток, ожидающий на этом мониторе.
- **`notifyAll()`** — пробуждает **все** потоки, ожидающие на этом мониторе.

Вызываются **только на объекте-мониторе**, который удерживается текущим потоком:
```java
synchronized (lock) {
    lock.wait();     // Ожидание на lock
    lock.notify();   // Пробуждение ожидающего потока
}
```

**`wait()` и `notify()` требуют `synchronized` из-за:**
1. **Атомарности**
    - Без синхронизации возможна **гонка состояний** между проверкой условия и вызовом `wait()`.
2. **Удержания монитора**
    - `wait()` **освобождает** монитор, но для этого он должен быть сначала захвачен (`synchronized`).
3. **Избежание `IllegalMonitorStateException`**
    - Вызов `wait()`/`notify()` без синхронизации приведёт к исключению.

### **Шаблон использования (Producer-Consumer)**

```java
private final Queue<String> queue = new LinkedList<>();
private final Object lock = new Object();

// Producer
public void produce(String data) throws InterruptedException {
    synchronized (lock) {
        while (queue.size() >= 10) {
            lock.wait();  // Ждём, пока Consumer не освободит место
        }
        queue.offer(data);
        lock.notifyAll();  // Сообщаем Consumer, что данные готовы
    }
}

// Consumer
public String consume() throws InterruptedException {
    synchronized (lock) {
        while (queue.isEmpty()) {
            lock.wait();  // Ждём, пока Producer не добавит данные
        }
        String data = queue.poll();
        lock.notifyAll();  // Сообщаем Producer, что место освободилось
        return data;
    }
}
```

### Важные нюансы
✔ **Всегда используйте `while` вместо `if`**
- Из-за **ложных пробуждений** (`spurious wakeups`) условие может не выполняться после `wait()`.

✔ **Предпочитайте `notifyAll()`**
- `notify()` будит только один поток (может привести к deadlock, если разбудит не тот поток).

✔ **Не вызывайте `wait()` без условия**
- Это может привести к бесконечной блокировке.

### **Альтернативы в современном Java**
 **`Lock` + `Condition`** (из `java.util.concurrent.locks`)
 ```java
Lock lock = new ReentrantLock();
Condition notEmpty = lock.newCondition();
notEmpty.await();  // Аналог wait()
notEmpty.signal(); // Аналог notify()
```

**Блокирующие очереди** (`BlockingQueue`, `LinkedBlockingQueue`)

Итого
**Правила:**
1. Только в `synchronized`.
2. Всегда с проверкой условия в цикле (`while`).
3. Лучше использовать `notifyAll()`.
4. В новых проектах предпочитать `java.util.concurrent.*`.

## Что такое volatile?
Волотайл запрещает помещать поле в кэш процессора и мы всегда читаем из main memory. Он обеспечивает видимость изменений среди разных потоков, которые обращаются к одному значению. Не гарантирует атомарность.  В отличие от `synchronized`, volatile не вызывает блокировок потоков. Volatile переменные работают медленнее обычных, но быстрее, чем синхронизированный доступ.

## Что такое ThreadLocal?
`ThreadLocal` - это класс в Java, который позволяет создавать переменные, доступные только конкретному потоку. Каждый поток имеет свою собственную независимую копию переменной ThreadLocal.

Основные случаи применения ThreadLocal:

1. **Хранение контекста потока** - например, в веб-приложениях для хранения информации о пользовательской сессии
2. **Избегание синхронизации** - когда нужно, чтобы каждый поток работал со своей копией объекта
3. **Передача параметров** - через методы без явной передачи в аргументах
4. **Потокобезопасность** - так как каждый поток работает со своим экземпляром

**ключевые особенности**
1. **Изоляция данных** - каждый поток видит только свою версию переменной
2. **Автоматическая очистка** - при завершении потока его ThreadLocal-переменные могут быть собраны GC
3. **Память** - может вызывать утечки памяти, если не очищать (особенно в пулах потоков)

**важные методы**
- `get()` - возвращает значение для текущего потока
- `set(T value)` - устанавливает значение для текущего потока
- `remove()` - удаляет значение для текущего потока
- `initialValue()` - определяет начальное значение (можно переопределить)

ThreadLocal часто используется в:

- Веб-фреймворках (Spring, Servlet API)
- Логировании (MDC в Log4j/SLF4J)
- Транзакциях (Hibernate, JDBC)

## Atomic classes and CAS
это набор классов, которые предоставляют атомарные операции над переменными.
CAS - это операция, которая выполняет три действия **атомарно** (как одно целое):
1. **Сравнивает** текущее значение в памяти с ожидаемым значением
2. **Если значения совпадают** - записывает новое значение
3. **Если не совпадают** - ничего не делает

Возвращает `true`, если замена произошла, и `false` - если нет.

```java
import java.util.concurrent.atomic.AtomicInteger;

public class CasExample {
    public static void main(String[] args) {
        AtomicInteger counter = new AtomicInteger(0);
        
        // Поток 1 пытается изменить 0 → 1
        boolean success1 = counter.compareAndSet(0, 1);
        System.out.println("Попытка 1: " + success1); // true
        
        // Поток 2 пытается изменить 0 → 2 (но значение уже 1)
        boolean success2 = counter.compareAndSet(0, 2);
        System.out.println("Попытка 2: " + success2); // false
        
        System.out.println("Итоговое значение: " + counter.get()); // 1
    }
}
```

## ThreadPool концепция и реализация

ThreadPool (пул потоков) — это механизм для управления множеством потоков, который позволяет:
- **Переиспользовать потоки** вместо создания новых для каждой задачи
- **Ограничивать количество одновременно работающих потоков**
- **Эффективно управлять ресурсами системы**

Почему нельзя создавать потоки на каждую операцию? Потому что это очень дорогостоящая и долгая операция.

**Основные компоненты ThreadPool:**

- **Рабочие потоки (Worker Threads):** Потоки, которые постоянно находятся в ожидании задач и выполняют их по мере поступления.
- **Очередь задач (Task Queue):** Структура данных, в которую помещаются задачи для последующего выполнения рабочими потоками.
- **Менеджер пула (Pool Manager):** Компонент, отвечающий за управление количеством потоков, распределение задач и обработку ошибок.

**Варианты реализации**
 **ThreadPoolExecutor (базовый вариант)**
 ```java
 ThreadPoolExecutor executor = new ThreadPoolExecutor(
    5, // corePoolSize
    10, // maximumPoolSize
    60, // keepAliveTime
    TimeUnit.SECONDS, // единицы измерения времени
    new LinkedBlockingQueue<>() // очередь задач
);
```
**FixedThreadPool** — фиксированное количество потоков:
```java
ExecutorService executor = Executors.newFixedThreadPool(4);
executor.submit(() -> {
    // Ваша задача
});
executor.shutdown();
```
**CachedThreadPool** — создает потоки по мере необходимости:
```java
ExecutorService cachedPool = Executors.newCachedThreadPool();
```
**SingleThreadExecutor** — один поток (очередь задач):
```java
ExecutorService singleThread = Executors.newSingleThreadExecutor();
```
**ScheduledThreadPool** — пул для отложенных задач:
```java
ScheduledExecutorService scheduled = Executors.newScheduledThreadPool(2);
scheduled.schedule(() -> System.out.println("Done"), 1, TimeUnit.SECONDS);
```
 
 **Очереди задач**
- **SynchronousQueue** — передача задачи прямо в поток
- **LinkedBlockingQueue** — неограниченная очередь (риск OOM)
- **ArrayBlockingQueue** — очередь с ограниченным размером

 **Политики отказа**
 Когда очередь заполнена и все потоки заняты:
- **AbortPolicy** — бросает RejectedExecutionException
- **CallerRunsPolicy** — выполняет задачу в вызывающем потоке
- **DiscardPolicy** — молча отбрасывает задачу
- **DiscardOldestPolicy** — удаляет самую старую задачу

## ForkJoinPool
ForkJoinPool — это специальный ExecutorService, предназначенный для эффективного выполнения задач, которые можно рекурсивно разбивать на подзадачи (fork), а затем объединять результаты (join). Используется в  parallel stream

Основные особенности и назначение:
1. **Оптимизация для рекурсивного параллелизма**:
    - Идеально подходит для "разделяй и властвуй" алгоритмов
    - Эффективен для задач, которые можно разбивать на независимые подзадачи
2. **Work-stealing алгоритм**:
    - Каждый поток имеет свою очередь задач (deque)
    - Если у потока заканчиваются задачи, он "ворует" задачи из хвоста очереди другого потока
    - Минимизирует простои потоков
3. **Отличия от ThreadPoolExecutor**:
    - В обычном пуле потоки ждут в голове общей очереди
    - В ForkJoinPool потоки активно ищут работу, когда их очередь пуста

 Основные компоненты:
1. **ForkJoinTask** — базовая абстракция задачи (обычно используют его подклассы):
    - `RecursiveAction` — для задач без возвращаемого результата
    - `RecursiveTask` — для задач с возвращаемым результатом
2. **ForkJoinWorkerThread** — специальные потоки пула

 Типичные use cases:
1. Параллельная обработка деревьев/графов
2. Рекурсивные алгоритмы (быстрая сортировка, merge sort)
3. Параллельные вычисления (MapReduce-подобные задачи)
4. Обработка больших массивов данных

**Почему не использовать обычный ThreadPool?**

1. **Эффективность**:
    - Work-stealing лучше балансирует нагрузку
    - Меньше contention (конкуренции) за общие ресурсы
2. **Удобство для рекурсивных задач**:
    - Автоматическое разделение и объединение результатов
    - Оптимальное планирование родительских/дочерних задач
3. **Меньшие накладные расходы**:
    - Локальные очереди уменьшают синхронизацию
    - Лучше использует процессорные ядра

## Что такое `Semaphore`?
Семафор — это счетчик, ограничивающий количество потоков, которые могут одновременно получить доступ к ресурсу.

**Как работает?**

- Имеет **количество "разрешений" (permits)**
- `acquire()` — блокирует, если разрешений нет
- `release()` — освобождает разрешение

```java
Semaphore semaphore = new Semaphore(3); // максимум 3 потока

void accessResource() {
    semaphore.acquire();  // ждём разрешения
    try {
        // работа с ресурсом (не более 3 потоков одновременно)
    } finally {
        semaphore.release();  // освобождаем
    }
}
```
## Race condition

**Race Condition** — это ошибка в многопоточном программировании, когда результат выполнения программы зависит от порядка выполнения потоков, что может приводить к недетерминированному поведению и некорректным данным.

Race Condition возникает, когда **два или более потока** одновременно обращаются к **общему ресурсу** (переменной, файлу, структуре данных), и хотя бы один из потоков **изменяет** этот ресурс.

Как предотвратить?
- **Синхронизация (`synchronized`)**
- **Атомарные классы (`AtomicInteger`, `AtomicReference`)**
- **Lock-механизмы (`ReentrantLock`)**
- **Потокобезопасные коллекции (`ConcurrentHashMap`, `CopyOnWriteArrayList`)**
## Deadlock
**Deadlock** — это ситуация в многопоточной среде, при которой два или более потока бесконечно блокируют друг друга, ожидая освобождения ресурсов, которые удерживаются самими этими потоками.

Для возникновения взаимной блокировки должны выполняться **4 условия** (условия Коффмана):
1. **Взаимное исключение (Mutual Exclusion)**
    - Ресурс может использоваться только одним потоком в данный момент (например, `synchronized` блокирует доступ другим потокам).
2. **Удержание и ожидание (Hold and Wait)**
    - Поток удерживает один ресурс и ожидает освобождения другого.
3. **Отсутствие вытеснения (No Preemption)**
    - Ресурс нельзя принудительно забрать у потока, он освобождается только добровольно.
4. **Циклическое ожидание (Circular Wait)**
    - Существует замкнутый цикл потоков, где каждый ждёт ресурс, удерживаемый следующим.

### Пример Deadlock

```java
public class DeadlockExample {
    private static final Object lock1 = new Object();
    private static final Object lock2 = new Object();

    public static void main(String[] args) {
        Thread thread1 = new Thread(() -> {
            synchronized (lock1) {
                System.out.println("Thread 1: Holding lock1...");
                try { Thread.sleep(100); } 
                catch (InterruptedException e) {}
                System.out.println("Thread 1: Waiting for lock2...");
                synchronized (lock2) {  // Блокируется, так как lock2 у thread2
                    System.out.println("Thread 1: Acquired both locks!");
                }
            }
        });

        Thread thread2 = new Thread(() -> {
            synchronized (lock2) {
                System.out.println("Thread 2: Holding lock2...");
                try { Thread.sleep(100); } 
                catch (InterruptedException e) {}
                System.out.println("Thread 2: Waiting for lock1...");
                synchronized (lock1) {  // Блокируется, так как lock1 у thread1
                    System.out.println("Thread 2: Acquired both locks!");
                }
            }
        });

        thread1.start();
        thread2.start();
    }
}
```

1. **Thread1** захватывает `lock1` и ждёт `lock2`.
2. **Thread2** захватывает `lock2` и ждёт `lock1`.
3. Оба потока **бесконечно заблокированы**, программа **не завершается**.

### **Как избежать Deadlock?**

1. **Упорядоченное получение блокировок** (всегда брать `lock1` → `lock2`).
2. **Использование `tryLock()`** (из `ReentrantLock`) с таймаутом.
3. **Уменьшение времени удержания блокировок**.
4. **Использование высокоуровневых API** (`ConcurrentHashMap`, `ExecutorService`).
