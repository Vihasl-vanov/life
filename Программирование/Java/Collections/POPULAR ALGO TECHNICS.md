## Big O
Чаще все оценку алгоритмов делают двух видов: оценка сложности по количеству операций (временная сложность) и оценка сложности по памяти
 **Примечание**: Хотя оценка худшего случая часто используется для определения верхнего предела производительности алгоритма, на практике средний случай может дать более реалистичное представление о том, как алгоритм будет вести себя в большинстве реальных ситуаций
### Временная сложность:

**O(1)** — константная сложность. Считается самой быстрой. Сложность получения элемента из хэш-мапы, например, считается константой, потому что элементы ищутся по уникальному хэшкоду, что позволяет мгновенно обращаться к нужной ячейке памяти без необходимости просматривать все элементы.

**O(log n)** — логарифмическая сложность или просто логарифм. Это тоже очень быстрые алгоритмы. Чаще всего в эту категорию попадают алгоритмы, где на каждом шагу из алгоритма “отпадает” по половине элементов. Пример: бинарный поиск.

**O(n)** — линейная сложность. Тоже считается быстрым алгоритмом. Это такие алгоритмы, где каждый элемент обрабатывается фиксированные число раз. Например — поиск элемента по неотсортированному массиву, где мы вынуждены идти от первого элемента до последнего и сверять с искомым.

**O(nlogn)** — линейно-логарифмическая сложность. Она уже не считается быстрой, но все равно намного лучше, чем следующие по списку. Обычно такой сложностью оценивают быстрые алгоритмы сортировки (это, кстати, значит, что алгоритмы, которые мы рассматривали в начале урока — не очень эффективные).

**O(n^2), O(n^3)** и т.д. — квадратичная, кубическая и так далее сложности. Эти алгоритмы очень быстро замедляются при увеличении количества элементов и не являются эффективными. Это сложность неэффективных алгоритмов сортировок, таких как пузырьковая.

**O(n!)** — исключительно долгий алгоритм. Оставим без комментариев: что-то из области задач комбинаторики, когда проще подождать столетие, чем найти оптимальное решение.![[Снимок экрана 2025-04-15 в 09.51.36.png]]
### Сложность по памяти

Чаще всего встречаются две оценки:

**O(1)** — во время работы алгоритма выделяется память на несколько переменных, число которых не зависит от входных данных. То есть здесь неважно, насколько большой объем входных данных обрабатывает алгоритм, потому что в памяти будет создаваться всегда фиксированное количество переменных.

**O(n)** — выделяется массив или несколько массивов длиной равной количеству входных данных.

💡 **Примечание**: Не всегда оценка сложности зависит от одного параметра. Например временная сложность алгоритма на основе подсчетов рассчитывается как O(N+K), где N — количество элементов, а K — разница между минимальным и максимальным элементов.



## Хранение дополнительной информации (Prefix Sum)
При работе с исходным массивом иногда бывает очень полезно создать второй массив для хранения промежуточных результатов.

 Для этого существует техника префиксной суммы, которая позволяет эффективно вычислять сумму элементов массива в каком-либо диапазоне. Эта техника особенно полезна, когда нам нужно многократно получать сумму элементов.

Мы можем построить новый массив `prefixSum:`

- Создаем новый массив `prefixSum` той же длины, что и исходный массив.
    
- `prefixSum[0]` устанавливаем равным `arr[0]`.
    
- Проходим по остальным элементам массива, начиная с индекса 1.
    
- Для каждого элемента `arr[i]` вычисляем 
    
- `prefixSum[i] = prefixSum[i-1] + arr[i]`.

### Вычисление суммы в диапазоне `[left, right]`
Используя массив префиксных сумм, можно быстро вычислить сумму элементов от индекса `left` до индекса `right` следующей формулой:
Для **0-based** индексации

```java
sum(left, right) = prefixSum[right] - (left > 0 ? prefixSum[left - 1] : 0)
```

Для **1-based** индексации:

```java
sum(left, right) = prefixSum[right] - prefixSum[left - 1]
```

- **0-based индексация:** Если `left` равно `0`, то сумма равна `prefixSum[right]`. В противном случае вычитаем `prefixSum[left - 1]` из `prefixSum[right]`.
- **1-based индексация:** Всегда вычитаем `prefixSum[left - 1]` из `prefixSum[right]`.

### Применение префиксных сумм

1. **Обработка запросов на суммы подмассива:** Часто встречается в задачах на массивы и строки.
2. **Решение задач на подсчет количества элементов с определенными свойствами.**
3. **Работа с матрицами:** Префиксные суммы могут быть расширены для двухмерных массивов для быстрого вычисления сумм подматриц.


## Sliding Window

**Sliding window** — это техника для решения задач, основная идея которой заключается в том, чтобы поддерживать фиксированный размер "окна", которое "скользит" по массиву или структуре данных, изменяя свое положение. Указатели начала и конца “окна” двигаются, пока не выполнится определенное в задаче условие.

В контексте массивов, “окно” - это какой-то подмассив основого массива. **Важно, что это непрерывная последовательность от начального индекса подмассива, до конечного индекса.**

Каждый раз, когда в задаче требуется работать с подмассивом, подумайте, можете ли вы использовать sliding window для эффективного решения задачи. Однако, если задача не связана с массивами, идею **sliding window** все равно можно использовать и с другими структурами данных. Например, при работе со строками и подстроками, а еще в деревьях скользящее окно используют для анализа поддеревьев или уровней, а при анализе графов можно использовать скользящее окно для обработки последовательности вершин. В каждом случае ключевой идеей остается то, что мы анализируем подмножества данных с фиксированным размером, последовательно смещая окно по структуре данных.
## Fast and Slow pointers
Основная идея заключается в использовании двух указателей, один из которых движется быстрее, чем другой. Если в привычном **two pointers** указатели движутся с двух сторон, то fast and slow указатели обычно движутся в одном направлении, но с разной скоростью.
