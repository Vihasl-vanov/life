## Базовые определения

Масштабируемость - способность системы увеличивать пропускную способность и/или объём данных без потери заданного уровня качества (SLO по p95/p99, ошибкам, доступности).

Вертикальное масштабирование (scale-up) - усиление одного узла: больше CPU/памяти/IOPS/сети. Горизонтальное масштабирование (scale-out) - увеличение количества узлов и распределение нагрузки между ними.

Эластичность - способность автоматически менять мощность (вверх/вниз) под актуальный трафик.

Практическая оценка нагрузки. Используйте закон Литтла: `Конкурентность ≈ RPS × Средняя задержка`. Пример: 200 RPS × 0.2 c = 40 одновременных запросов → столько "рабочих мест" должно быть в сумме у ваших воркеров/нитей, чтобы не накапливались очереди.

## Вертикальное масштабирование (Scale-Up)

### Когда уместно

- Узкое место - один компонент, который сложно реплицировать (часто - write-master БД, OLTP-узел, stateful кэш).
    
- Требуется минимальная латентность (меньше хопов, отсутствие сетевых RPC между "кусочками" логики).
    
- Простой SLA/эксплуатация важнее гибкости (меньше движущихся частей).
    

### Сильные стороны

- Простота: минимум архитектурных изменений, быстрый путь к приросту производительности.
    
- Меньше накладных расходов: нет межузловой координации/репликации, меньше сетевых задержек.
    
- Хорошо для stateful-нагрузок: интенсивные записи/транзакции проще на "большом железе".
    

### Ограничения и риски

- Потолок железа: масштаб вверх конечен (часто упираетесь в NUMA/память/шину/IO).
    
- Нелинейность: закон Амдала - ускорение ограничено непараллелимой долей.
    
- Дороговизна: "большие" узлы растут в цене не линейно.
    
- Blast radius: падение "монстра" = сильный инцидент.
    

## Горизонтальное масштабирование (Scale-Out)

### Когда уместно

- Нужна линейная пропускная способность по мере роста трафика.
    
- Компоненты можно сделать бесстейт или вынести состояние (сессии, кэш, файлы) во внешние хранилища.
    
- Приоритет - высокая доступность и "мелкий" blast radius.
    

### Сильные стороны

- Линейный рост: добавили узлы - получили пропускную способность (почти линейно при хорошем балансировании).
    
- Надёжность: отказ одного узла переносится без даунтайма.
    
- Стоимость: commodity-железо, "тонкие" узлы, гибкость закупки/аренды.
    

### Сложности и компромиссы

- Сетевые накладные: RPC, сериализация, ретраи, таймауты, кворумы.
    
- Данные: консистентность (репликация, шардинг, распределённые транзакции), hot-keys.
    
- Сессии: нужна sticky-сессия или внешний session store.
    
- Оперирование: service discovery, health-checks, автоскейлинг, canary/blue-green, observability.
    

## Типовые шаблоны масштабирования

### Приложения (API/бизнес-логика)

- Вертикально: увеличить vCPU/RAM, профилировать, убирать lock-contention, оптимизировать GC.
    
- Горизонтально: статлесс-слой за L7-балансировщиком; сессии в Redis; rate limiters; очереди для выравнивания пиков.
    

### Базы данных

- Вертикально: увеличить класс инстанса, тюнинг буферов/индексов/IO.
    
- Горизонтально:
    
    - Read replicas для чтений.
        
    - Шардирование (hash/range/geo); продумать ключ, rebalancing, "двухфазное" перешардирование.
        
    - CQRS: write-модель отделить от read-модели.
        
    - Outbox/CDC для событий и asynch-согласованности.
        

### Кэш/файлы/очереди

- Кэш - кластер (Redis Cluster), реплики; near-cache на клиентах.
    
- Объектное хранилище - S3/MinIO c CDN.
    
- Очереди/стриминг - scale-out по партициям (Kafka/RabbitMQ).
    

## Экономика и методология

- Стройте кривые "производительность-стоимость" для вариантов (scale-up vs scale-out).
    
- Микроскопируйте SLO: p95/p99 по ключевым операциям; headroom 20–40% под всплески.
    
- Benchmark-план: ступенчатая нагрузка, открытая модель (генератор не ограничивает коннекты), гистограммы задержек, flamegraphs.
    
- Автоскейлинг:
    
    - HPA по CPU/RAM/критериям слоя (RPS, queue length, consumer lag).
        
    - VPA - корректировка ресурсов под профиль.
        
    - Предиктивный скейлинг по расписаниям/истории.

## Быстрый чек-лист выбора

- Нагрузка растёт, но один узел далеко от предела → Scale-Up сейчас, параллельно готовьте stateless-слой.
    
- Нагрузка "пилит" и нужны быстрые фичи → Scale-Out фронта (stateless) + кэш, БД ещё вертикально.
    
- Чтения >> записи → реплики чтения, CDN, кэш → затем шардинг.
    
- Записи упираются в один мастер → денормализация, partition-by-key, очереди, шардинг.
    
- Высокая стоимость простоя → scale-out + избыточность; cell-based архитектура (изоляция blast radius).
    

## Типичные ошибки

- Ранний "тотальный" микросервисинг (создание большого количетсва микросервисов) без нужды → рост сложности без выигрыша.
    
- Горизонтальный скейл без stateless → липкая боль со сессиями.
    
- Шардирование без ключа домена → "горячие" шарды и перекос нагрузки.
    
- Автоскейлинг по CPU только → игнорирование очередей/lag → флапы/неустойчивость.
