## REST
Это стиль Api, который описывает то, как клиент взаимодействует с сервером.

**Ключевые принципы (ограничения) REST:**

1. **Единообразие интерфейса (Uniform Interface):** Это фундаментальный принцип REST. Он включает в себя несколько аспектов:
    
    - **Идентификация ресурсов:** Каждый ресурс (объект, сущность) в системе однозначно идентифицируется URI (Uniform Resource Identifier). Например, `/api/users/123`.
        
    - **Манипуляция ресурсами через представления:** Клиент работает с ресурсом через его представление (например, JSON или XML). Изменив представление на своей стороне и отправив его обратно серверу, клиент может изменить ресурс.
        
    - **Самодостаточные сообщения:** Каждое сообщение от сервера к клиенту содержит всю необходимую информацию для его понимания и обработки (например, заголовки `Content-Type`, `Cache-Control`).
        
    - **Hypermedia as the Engine of Application State (HATEOAS):** Ответы сервера должны содержать не только данные, но и ссылки (гипермедиа) на возможные следующие действия. Это делает API discoverable (познаваемым).
        
2. **Отсутствие состояния (Stateless):** Каждый запрос от клиента к серверу должен содержать всю информацию, необходимую для его понимания и выполнения. Сервер не хранит состояние сессии клиента между запросами. Это улучшает масштабируемость и надежность.
    
3. **Кэшируемость (Cacheable):** Ответы сервера должны явно указывать, можно ли кэшировать данные и как долго. Это значительно снижает нагрузку на сервер и улучшает производительность.
    
4. **Клиент-серверная архитектура (Client-Server):** Четкое разделение ответственности. Клиент отвечает за UI и пользовательский опыт, сервер — за хранение данных, бизнес-логику и безопасность. Они развиваются независимо друг от друга.
    
5. **Многоуровневая система (Layered System):** Архитектура может состоять из нескольких уровней (прокси, кэши, шлюзы). Клиент не знает и не должен заботиться о том, с каким именно уровнем он взаимодействует.
    
6. **Код по требованию (Code on demand, опционально):** Сервер может временно расширять функциональность клиента, передавая ему исполняемый код (например, JavaScript). На практике используется редко.

### HTTP
 это протокол, который используется для передачи данных между веб-сервером и веб-клиентом. HTTP является основным протоколом, используемым в Интернете для передачи данных между серверами и клиентами.

**HTTPS (HTTP Secure)** является расширением протокола HTTP, которое добавляет безопасность с помощью шифрования данных, передаваемых между сервером и клиентом, с использованием SSL (Secure Sockets Layer) или его современного эквивалента TLS (Transport Layer Security). HTTPS обеспечивает защищенную передачу данных через Интернет и используется для безопасной передачи конфиденциальной информации, такой как данные банковских карт или логин/пароль.

Когда клиент отправляет запрос на сервер, запрос должен быть сформирован в соответствии со схемой HTTP-запросов. Эта схема состоит из нескольких основных блоков: HTTP-метод запроса (GET, POST и так далее), хедеры (в том числе содержит запрашиваемый адрес) и непосредственно тело запроса. В хедерах содержатся метаданные или метаинформация, которая описывает запрос, клиента и передаваемые данные. Заголовки могут включать информацию, такую как тип содержимого (Content-Type), длину содержимого (Content-Length), куки (Cookies), заголовки авторизации (Authorization) и другие данные. Заголовки запроса используются для передачи дополнительной информации о запросе, которая не может быть передана через строку запроса. Также вы можете создавать и передавать собственные заголовки.

Тело запроса — это просто какая-то информация. Это может быть просто текст, JSON, XML, бинарный формат и другие форматы данных. Формат тела запроса может зависеть от типа запроса, метода HTTP-запроса и настроек сервера. Здесь может быть любая информация, которой клиент обменивается с сервером.

Когда сервер получил и обработал запрос клиента, он формирует HTTP-ответ. Основная структура содержит статус-код, заголовки и тело.

Ресурсы и методы HTTP

- **Ресурсы** — это ключевая абстракция в REST. Любая сущность (пользователь, заказ, товар) является ресурсом. Доступ к ним осуществляется через **URI**.
    
    - Пример: `/api/books`, `/api/books/45`, `/api/users/12/orders`
        
- **HTTP-методы** (глаголы) определяют операцию, которую мы хотим выполнить над ресурсом. Они соответствуют CRUD-операциям (Create, Read, Update, Delete).
    

| HTTP Метод | CRUD   | Описание                                                                     | Идемпотентность* | Безопасность** |
| ---------- | ------ | ---------------------------------------------------------------------------- | ---------------- | -------------- |
| **GET**    | Read   | Получить представление ресурса или коллекции ресурсов.                       | Да               | Да             |
| **POST**   | Create | Создать новый ресурс. URI определяет коллекцию, в которую он будет добавлен. | Нет              | Нет            |
| **PUT**    | Update | Полностью обновить ресурс по указанному URI. Если не существует — создать.   | Да               | Нет            |
| **PATCH**  | Update | Частично обновить ресурс.                                                    | Нет***           | Нет            |
| **DELETE** | Delete | Удалить ресурс по указанному URI.                                            | Да               | Нет            |

_Идемпотентность_: Повторный идентичный запрос имеет тот же эффект, что и однократный. Клиент может безопасно повторить такой запрос при ошибке сети.  
_Безопасность_: Метод не меняет состояние ресурса на сервере.  
***PATCH не всегда идемпотентен, но его следует проектировать таким образом, насколько это возможно.

Коды состояния
- 2хх успех
- 3хх редирект
- 4хх ошибка клиета
- 5хх ошибка сервера

## GRPC

- **Использует HTTP/2:** Это фундаментальное отличие от REST и основа его преимуществ.
    
- **Использует Protocol Buffers (protobuf):** Это язык-независимый и платформонезависимый механизм сериализации структурированных данных по умолчанию. Можно использовать и другие форматы (например, JSON), но protobuf — это "сердце" gRPC.
    
- **Идемпотентный и потоковый:** Позволяет легко реализовать сложные сценарии взаимодействия, которые сложно или неэффективно делать на HTTP/1.1.

### Ключевые Компоненты и Принцип Работы

**1. Protocol Buffers (protobuf)**  
Это не просто формат данных, а язык для описания схемы данных (_структуры_) и сервисов (_контрактов_).

- **Языково-независимый:** Вы описываете контракт в `.proto`-файле.
    
- **Кодогенерация:** Компилятор `protoc` генерирует код клиента и сервера на поддерживаемых языках (Go, Python, Java, C#, C++, JS, Ruby, PHP и др.). Этот код включает:
    
    - **Сериализацию/десериализацию:** Невероятно быструю и эффективную по размеру (бинарный формат).
        
    - **Базовые классы клиента и сервера:** На их основе вы строите свою логику.
        
- **Пример `.proto` файла:**

```protobuf
// Определение сообщения
message Person {
  string name = 1;
  int32 id = 2;
  string email = 3;
}

// Определение сервиса
service PersonService {
  rpc GetPerson (GetPersonRequest) returns (Person); // Простой RPC
}

message GetPersonRequest {
  int32 person_id = 1;
}
```

**HTTP/2**  
gRPC построен поверх HTTP/2, а не HTTP/1.1. Это дает решающие преимущества:

- **Бинарный протокол:** Более эффективная парсинговая производительность по сравнению с текстовым HTTP/1.1.
    
- **Мультиплексирование:** Множество запросов и ответов могут передаваться **одновременно по одному TCP-соединению**, устраняя проблему "head-of-line blocking" HTTP/1.1. Это drastically снижает задержку и эффективно использует сеть.
    
- **Двунаправленная потоковая передача:** Клиент и сервер могут независимо и асинхронно отправлять потоки данных друг другу.
    
- **Сжатие заголовков (HPACK):** Уменьшает накладные расходы.

**Типы gRPC методов**

- **Unary RPC:** Классический запрос-ответ. Клиент отправляет один запрос и получает один ответ.  
    `rpc Method(RequestType) returns (ResponseType);`
    
- **Server streaming RPC:** Клиент отправляет один запрос и получает поток ответов от сервера. Идеально для отправки уведомлений, chunked-данных.  
    `rpc Method(RequestType) returns (stream ResponseType);`
    
- **Client streaming RPC:** Клиент отправляет поток запросов, а сервер возвращает один ответ. Идеально для загрузки больших данных.  
    `rpc Method(stream RequestType) returns (ResponseType);`
    
- **Bidirectional streaming RPC:** Обе стороны обмениваются потоками сообщений асинхронно и независимо. Идеально для чатов, онлайн-игр, real-time систем.  
    `rpc Method(stream RequestType) returns (stream ResponseType);`

### Преимущества и Недостатки (Когда использовать и когда не использовать)

**Преимущества gRPC (Сильные стороны):**

1. **Высочайшая производительность и низкая задержка (Low Latency):** Благодаря HTTP/2, бинарному protobuf и эффективному коду.
    
2. **Строгая типизация и контракты:** `.proto` файл — это единственный источник истины. Это исключает ошибки из-за несоответствия типов данных между клиентом и сервером.
    
3. **Встроенная генерация кода:** Генерирует клиентские и серверные stubs, что ускоряет разработку и обеспечивает согласованность.
    
4. **Поддержка потоковой передачи (Streaming):** Нативные возможности для сложных сценариев взаимодействия.
    
5. **Встроенные функции:** Поддержка аутентификации, deadlines (таймауты), отмены вызовов, load balancing и interceptors (middleware) из коробки.
    
6. **Идеален для сервис-ориентированной (SOA) и микросервисной архитектуры:** Там, где сервисы интенсивно общаются друг с другом внутри кластера.
    

**Недостатки gRPC (Слабые стороны):**

1. **Отсутствие удобочитаемости (читаем человеком):** Бинарный формат protobuf не читается глазами, в отличие от JSON. Для отладки нужны дополнительные инструменты (например, grpcurl, Wireshark).
    
2. **Неполная поддержка в браузерах:** Нативная поддержка gRPC в браузерах ограничена (требуется gRPC-Web, который часто требует прокси). **gRPC не предназначен для прямого взаимодействия с браузерным JavaScript-кодом.**
    
3. **Сложнее в освоении:** По сравнению с простым JSON-over-HTTP нужно понимать концепцию protobuf, кодогенерацию, работу с потоками.
    
4. **Не кэшируется на промежуточных узлах:** В отличие от HTTP-запросов с их методами и кэширующими прокси, gRPC-запросы сложнее кэшировать стандартными методами.

### Сравнение с REST API (Обязательный вопрос на собеседовании)

|Критерий|gRPC|REST|
|---|---|---|
|**Протокол**|HTTP/2|HTTP/1.1 / HTTP/2|
|**Формат данных**|**Binary (Protocol Buffers)**|**Text (JSON/XML)**|
|**Контракты**|**Строгие, обязательные** (.proto)|Слабые, опциональные (OpenAPI/Swagger)|
|**Парсинг**|Быстрый (бинарный)|Медленный (текстовый)|
|**Размер payload**|**Очень компактный**|Больше (текст + избыточность)|
|**Потоковая передача**|**Полная нативная поддержка**|Частичная (SSE, WebSockets — не являются частью стандарта)|
|**Кодогенерация**|**Встроенная, первоклассная поддержка**|Существует (например, через OpenAPI), но часто сторонняя|
|**Идеальный сценарий**|**Внутренняя коммуникация микросервисов** (high-performance, low-latency)|**Публичные API**, взаимодействие с браузерами (human-readable, cacheable)|
### глубина

- **gRPC-Gateway:** Инструмент, который генерирует reverse-proxy сервер, который транслирует RESTful JSON HTTP-запросы в gRPC. Позволяет иметь как gRPC, так и REST API из одного `.proto`-файла. Идеально для постепенного перехода или предоставления публичного REST API поверх внутренних gRPC-сервисов.
    
- **gRPC-Web:** Позволяет клиентам в браузере общаться с gRPC-сервером через специальный прокси.
    
- **Deadlines/Timeouts:** Важная встроенная функция gRPC, которая позволяет клиенту указать, как долго он готов ждать ответа. Сервер может проверить этот дедлайн и прервать работу, если он истек, экономя ресурсы.
    
- **Interceptors:** Аналог middleware. Позволяют реализовать сквозную функциональность: логирование, аутентификацию, метрики.

## WEBSOCKETS
### Определение и Основная концепция

**WebSocket** — это коммуникационный протокол, предоставляющий двунаправленный канал связи между клиентом (чаще всего браузером) и сервером поверх единственного TCP-соединения.

**Ключевая идея:** Решить фундаментальные ограничения HTTP для интерактивных приложений.

- **HTTP — это однонаправленный запрос-ответ.** Клиент всегда инициирует соединение, сервер отвечает и закрывает его. Для постоянного обновления данных клиент вынужден постоянно опрашивать сервер (Polling), что неэффективно.
    
- **WebSocket — это двунаправленное постоянное соединение.** После установки соединения и сервер, и клиент могут **асинхронно и независимо** отправлять данные друг другу в реальном времени без необходимости постоянно переподключаться.
    

**Простая аналогия:**

- **HTTP** — как отправка писем через почту. Для каждого сообщения нужен новый конверт, адрес, марка.
    
- **WebSocket** — как телефонный звонок. Вы звоните один раз (устанавливаете соединение), и после этого можете говорить (отправлять данные) и слушать (получать данные) одновременно.


Процесс установления соединения — это «апгрейд» HTTP-соединения до WebSocket.

**Ping/Pong:** Протокол использует контрольные фреймы Ping (от сервера) и Pong (в ответ от клиента) для проверки живости соединения (heartbeat).

### Преимущества и Недостатки

**Преимущества WebSockets:**

1. **Низкая задержка (Low Latency):** Данные доставляются практически мгновенно, так как нет накладных расходов на повторное установление соединения.
    
2. **Эффективность:** Минимальный overhead по сравнению с HTTP-заголовками каждого запроса.
    
3. **Двунаправленная связь:  Сервер может отправлять данные в любой момент без запроса от клиента.
    
4. **Одно постоянное соединение:** Экономит ресурсы клиента, сервера и сети по сравнению с постоянным polling.
    

**Недостатки и сложности:**

1. **Отсутствие встроенного механизма повторного соединения:** Если соединение разорвалось, клиентское приложение должно самостоятельно реализовать логику переподключения.
    
2. **Масштабируемость на сервере:** Сервер должен поддерживать множество долгоживущих соединений одновременно. Это требует иной архитектуры, чем классический HTTP-сервер (часто используют асинхронные frameworks или кластеризацию).
    
3. **Проблемы с балансировкой нагрузки:** «Липкие» сессии (sticky sessions) часто необходимы, так как состояние соединения привязано к конкретному worker-процессу на сервере.
    
4. **Сложнее кэшировать и индексировать:** Промежуточные прокси (CDN) традиционно плохо работают с WebSockets (хотя современные прокси, like Cloudflare, уже поддерживают их).
    
5. **Не все брандмауэры и прокси дружелюбны:** Могут обрывать «долгие» соединения.

### Сравнение с альтернативами (когда что использовать)

|Технология|Паттерн|Плюсы|Минусы|Идеальный кейс|
|---|---|---|---|---|
|**WebSocket**|**Двунаправ., постоянное**|Низкая задержка, эффективность|Сложность масштабирования|**Чат, онлайн-игры, реальные времени данные (биржевые тикеры), коллаборативные инструменты**|
|**HTTP Long-Polling**|Запрос-ответ с задержкой|Проще реализовать, работает везде|Высокий overhead, задержка|Уведомления, простой реальный время|
|**Server-Sent Events (SSE)**|**Однонаправ. от сервера**|Простой протокол, встроенный reconnect|Только сервер -> клиент|**Лента новостей, уведомления, мониторинг**|
|**gRPC-Streaming**|Двунаправ., потоковый|Высокая производит., типизация|Сложность, не для браузера|**Микросервисы, внутренняя коммуникация**|
## GRAPHQL
**GraphQL** — это язык запросов для  API и среда выполнения для их обработки. Это  а **спецификация** (стиль апи). Его ключевая идея — позволить клиенту точно определить, какие данные ему нужны, и получить их в одном запросе, избегая проблем недополучения (under-fetching) или переполучения (over-fetching) данных, характерных для REST.

### Ключевые особенности и преимущества

1. **Точность данных (Precise Data Fetching)**:
    
    - **Over-fetching**: Клиент получает больше данных, чем нужно (например, весь объект пользователя, когда требуется только его имя).
        
    - **Under-fetching**: Одного HTTP-запроса недостаточно, чтобы получить все нужные данные (например, нужно сделать запрос к `/users/1`, а потом к `/users/1/posts`).
        
    - **GraphQL решает это**: Клиент в одном запросе точно описывает, какие поля и связанные сущности ему нужны. Сервер возвращает ровно такой же по структуре JSON-объект.
        
2. **Единственная конечная точка (Single Endpoint)**:
    
    - В отличие от REST, где множество endpoint'ов (`/users`, `/posts`, `/comments`), GraphQL использует всего одну точку входа (обычно `/graphql`).
        
    - Все операции выполняются через POST-запросы на этот endpoint. Тип операции (чтение, изменение) определяется не HTTP-методом (GET, POST, PUT, DELETE), а телом запроса.
        
3. **Строгая типизация и схема (Strongly Typed Schema)**:
    
    - **Схема** — это основа любого GraphQL API. Она выступает в роли контракта между клиентом и сервером.
        
    - Схема определяется с помощью SDL (Schema Definition Language). Она четко описывает все типы данных, запросы (Query) и изменения (Mutation).
        
    - Это позволяет использовать мощные инструменты вроде **автодополнения** и **валидации запросов** на стороне клиента (в IDE типа GraphiQL или Apollo Studio) еще до отправки на сервер.
        
4. **Гибкость и быстрота разработки на клиенте**:
    
    - Добавление новых полей на клиенте не требует изменений на сервере (если эти поля уже есть в схеме). Это ускоряет разработку, особенно на мобильных клиентах, где нельзя заставить всех пользователей обновить приложение.

### Недостатки GraphQL (Важно показать, что вы понимаете и минусы)

1. **Проблема N+1**: Классическая проблема. Если запрос клиента включает список элементов и для каждого из них нужно сделать отдельный запрос к БД (например, получить автора для каждой статьи), это может привести к огромному количеству запросов. Решается с помощью **DataLoader** (паттерн batching).
    
2. **Сложность кэширования**: HTTP-кэширование на уровне GET-запросов не работает, так как все операции используют POST. Кэширование необходимо реализовывать на клиенте или с помощью специальных библиотек.
    
3. **Сложность мониторинга и логирования**: В REST легко логировать и ограничивать запросы по URL. В GraphQL все запросы приходят на один endpoint, и их анализ требует парсинга тела запроса.
    
4. **Уязвимости**: Неправильная настройка может привести к уязвимостям, например, слишком глубоким или сложным запросам, которые могут положить сервер (DoS-атаки). Нужны механизмы ограничения сложности запросов (query depth limiting, complexity analysis).
    
5. **Не подходит для простых API**: Для небольших приложений с простыми данными настройка GraphQL может быть избыточной. REST проще и быстрее.
