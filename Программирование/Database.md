## JOINS
### INNER JOIN (просто JOIN)
- Возвращает только строки, где есть совпадения в обеих таблицах

```java
SELECT columns
FROM table1
INNER JOIN table2 ON table1.column = table2.column
```
### LEFT JOIN (LEFT OUTER JOIN)

- Возвращает все строки из левой таблицы и совпадающие из правой    
- Если совпадений нет, справа будет NULL

```JAVA
SELECT columns
FROM table1
LEFT JOIN table2 ON table1.column = table2.column
```

### RIGHT JOIN (RIGHT OUTER JOIN)
- Возвращает все строки из правой таблицы и совпадающие из левой
- Если совпадений нет, слева будет NULL

```JAVA
SELECT columns
FROM table1
RIGHT JOIN table2 ON table1.column = table2.column
```

### FULL JOIN (FULL OUTER JOIN)

- Возвращает все строки из обеих таблиц
- Если совпадений нет, в недостающей части будет NULL

```JAVA
SELECT columns
FROM table1
FULL JOIN table2 ON table1.column = table2.column
```

### CROSS JOIN

- Декартово произведение - каждая строка из первой таблицы соединяется с каждой строкой из второй
- Не требует условия ON

```JAVA
SELECT columns
FROM table1
CROSS JOIN table2
```

### Важные моменты для собеседования

1. **Производительность**: INNER JOIN обычно быстрее, чем OUTER JOIN    
2. **Порядок таблиц**: важен для LEFT/RIGHT JOIN, не важен для INNER JOIN
3. **WHERE vs ON**: условия в ON фильтруются до JOIN, в WHERE - после
4. **Использование**:
    - INNER JOIN - когда нужны только совпадения
    - LEFT JOIN - когда нужно сохранить все записи из основной таблицы
    - FULL JOIN - когда нужно сохранить все записи из обеих таблиц
    - CROSS JOIN - для комбинаторики или когда нужны все возможные пары

## GROUP BY AND HAVING

### GROUP BY

**Назначение**:  
Группирует строки с одинаковыми значениями в указанных столбцах для выполнения агрегатных функций.

**Основные характеристики**:

- Используется с агрегатными функциями (COUNT, SUM, AVG, MAX, MIN)
- Может группировать по одному или нескольким столбцам
- Порядок группировки соответствует порядку столбцов в GROUP BY

```SQL
-- Количество сотрудников в каждом отделе
SELECT department_id, COUNT(*) as employee_count
FROM employees
GROUP BY department_id

-- Средняя зарплата по отделам
SELECT department_id, AVG(salary) as avg_salary
FROM employees
GROUP BY department_id

-- Группировка по нескольким полям
SELECT department_id, job_title, COUNT(*) as count
FROM employees
GROUP BY department_id, job_title
```

### HAVING

**Назначение**:  
Фильтрует результаты группировки (аналогично WHERE, но для агрегированных данных).

**Основные характеристики**:

- Применяется после GROUP BY
    
- Может использовать агрегатные функции в условиях


```SQL
-- Отделы с более чем 5 сотрудниками
SELECT department_id, COUNT(*) as employee_count
FROM employees
GROUP BY department_id
HAVING COUNT(*) > 5

-- Отделы со средней зарплатой выше 50000
SELECT department_id, AVG(salary) as avg_salary
FROM employees
GROUP BY department_id
HAVING AVG(salary) > 50000

-- Комбинация WHERE и HAVING
SELECT department_id, AVG(salary) as avg_salary
FROM employees
WHERE hire_date > '2020-01-01'
GROUP BY department_id
HAVING AVG(salary) > 50000
```

### Важные моменты для собеседования

**Порядок выполнения**:
```SQL
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

1. **Оптимизация**: WHERE обычно эффективнее, чем HAVING, так как фильтрация происходит раньше
    
2. **Использование индексов**: WHERE может использовать индексы, HAVING - нет
    
3. **Практическое правило**:
    
    - Фильтровать отдельные строки → WHERE
    - Фильтровать результаты агрегации → HAVING

## INDEXES
### 1. B-tree индексы

- Сбалансированные деревья, хранят данные в отсортированном порядке.

**Преимущества:**

- Универсальность: поддержка равенства, диапазонных запросов (>, <, BETWEEN), сортировки.
- Эффективность: логарифмическая сложность (O(log n)) для поиска, вставки, удаления.
- Упорядоченность данных.

**Недостатки:**

- Замедление операций вставки/обновления из-за обновления индексов.

**Применение:**

- Широко используются для большинства запросов, особенно с диапазонными операциями и сортировкой.

### 2. Hash индексы

**Описание:**

- Используют хеш-таблицы для хранения ключей и значений.

**Преимущества:**

- Высокая скорость для операций равенства (O(1)).
- Простая реализация.

**Недостатки:**

- Не поддерживают диапазонные запросы.
- Возможны коллизии, требующие разрешения.
- Неупорядоченность данных.

**Применение:**

- Подходят для частых операций поиска по точному совпадению (например, первичные ключи).

### 3. Partial индексы

**Описание:**

- Индексы только для части данных, соответствующих условию (фильтру).

**Преимущества:**

- Экономия места.
- Повышенная производительность за счёт меньшего объёма данных.
- Оптимизация под специфичные запросы.

**Недостатки:**

- Используются только для запросов, соответствующих условию индекса.
- Требуют тщательного проектирования.

**Применение:**

- Таблицы с большим объёмом данных, но часто используемые только их подмножества (например, `WHERE active = true`).

### 4. Covering индексы

**Описание:**

- Индексы, содержащие все столбцы, необходимые для выполнения запроса.

**Преимущества:**

- Улучшенная производительность: запросы выполняются только по индексу без обращения к таблице.
- Сокращение операций ввода-вывода.

**Недостатки:**

- Увеличение размера индекса.
- Необходимость тщательного выбора столбцов для покрытия.

**Применение:**

- Часто используемые запросы с небольшим количеством столбцов, требующие быстрой выборки (например, аналитику и отчётность).

### Сравнение и рекомендации

- **B-tree:** Универсальный выбор для большинства сценариев.
- **Hash:** Оптимален для быстрых операций равенства, но ограничен функционально.
- **Partial:** Эффективен для специфичных запросов и экономии ресурсов при больших таблицах.
- **Covering:** Ускоряет частые запросы, уменьшая необходимость обращения к таблице.

### Дополнительные моменты

- **Комбинированные индексы:** Улучшают производительность при фильтрации/сортировке по нескольким столбцам.
- **Балансировка индексов и нормализации:** Чрезмерное индексирование может замедлить операции вставки/обновления.
- **Уникальные индексы:** Обеспечивают уникальность значений, важны для первичных ключей.
- **Типы данных:** Выбор индекса зависит от типов операций и данных (B-tree для диапазонов, Hash для равенства).

## EXPLAIN ANALYZE и оптимизация

### Ключевые элементы
- **Типы операций**:
  - Sequential Scan - чтение всей таблицы
  - Index Scan - доступ через индекс
  - Bitmap Heap Scan - комбинация индекса и таблицы
  - Nested Loop - вложенные циклы для JOIN
  - Hash Join - соединение через хеш-таблицу
  - Merge Join - соединение по отсортированным данным

- **Выполнение запроса:** `EXPLAIN` не выполняет запрос, тогда как `EXPLAIN ANALYZE` выполняет его.
- **Статистика:** Только `EXPLAIN ANALYZE` предоставляет фактические данные о времени выполнения и количестве обработанных строк.
- **Безопасность:** `EXPLAIN` безопасен для всех типов запросов, включая те, что изменяют данные, тогда как `EXPLAIN ANALYZE` выполняет запрос, что может привести к изменениям данных.

### Основные оптимизации
1. Добавление недостающих индексов
2. Пересмотр порядка JOIN
3. Настройка work_mem
4. Обновление статистики (ANALYZE)

### Полезные команды
- `EXPLAIN (ANALYZE, BUFFERS)`
- `pg_stat_statements`

## ACID

Это свойства системы, которое работает для всех транзакций в sql базах данных

- Atomicity - это свойство гарантирует, что все операция транзакции будут выполнены полностью, либо не будет выполнено ничего. При ошибке на одной из операций произойдет откат транзакции.
- Consistency - это свойство говорит о том, что данные всегда будут находится в правильном, согласованном состоянии. Атомарность это принцип работы. Консистентность - результат всех изменений.
- Isolation -определяющее видимость изменений между параллельными транзакциями
- Durability  - это свойство гарантирует что изменения, сделанные в транзакции будут сохранены навсегда, если транзакция успешна завершена

## Уровни изоляции транзакций

### 2. Уровни изоляции (от слабых к строгим)

#### 2.1 READ UNCOMMITTED
- **Поведение**: разрешает "грязное чтение"
- **Проблемы**:
  - Dirty Read (чтение незакоммиченных данных)
- **Где используется**: аналитика, временные данные

#### 2.2 READ COMMITTED (по умолчанию в PostgreSQL)
- **Поведение**: видит только закоммиченные изменения
- **Проблемы**:
  - Non-repeatable Read( Одна транзакция дважды читает одну и ту же строку, но получает разные значения, потому что между чтениями другая транзакция изменила и закоммитила эту строку)
  - Lost Update(Две транзакции одновременно читают одну строку, изменяют ее на основе прочитанного значения, и последняя транзакция перезаписывает изменения первой.)
- **Решения**:
  - SELECT FOR UPDATE( позволяет выбрать определённые строки из таблицы и установить на них блокировки, предотвращая их изменение другими транзакциями до завершения текущей транзакции. Это механизм реализации **пессимистической блокировки**)

#### 2.3 REPEATABLE READ
- **Поведение**: гарантирует неизменность прочитанных данных
- **Особенности**:
  - В PostgreSQL предотвращает Lost Update и non-repetable-read
- **Проблемы**:
  - Phantom Read( Транзакция повторно выполняет запрос, возвращающий набор строк по некоторому условию, и обнаруживает новые "фантомные" строки, которые были добавлены другими закоммиченными транзакциями в промежутке между выполнениями запроса.)
- **Решения**:
  - SELECT FOR UPDATE с блокировкой диапазона
  - SERIALIZABLE для критичных операций

#### 2.4 SERIALIZABLE
- **Поведение**: полная изоляция, эмуляция последовательного выполнения
- **Реализация**:
  - В PostgreSQL: SSI (Serializable Snapshot Isolation)
- **Проблемы**:
  - False-positive конфликты
  - Высокие накладные расходы
- **Оптимизации**:
  - Короткие транзакции
  - Повтор при Serialization Failure

### 3. Проблемы параллельных транзакций

#### 3.1 Dirty Read
- **Уровни**: READ UNCOMMITTED
- **Решение**: не использовать в production

#### 3.2 Non-repeatable Read
- **Уровни**: READ COMMITTED
- **Решение**: REPEATABLE READ

#### 3.3 Phantom Read
- **Уровни**: REPEATABLE READ
- **Решение**: SERIALIZABLE, блокировка диапазонов

#### 3.4 Lost Update
- **Уровни**: READ COMMITTED
- **Решение**:
  - REPEATABLE READ (в PostgreSQL)
  - SELECT FOR UPDATE

### 4. Практические рекомендации
- **Для 90% случаев**: READ COMMITTED + точечные блокировки
- **Для финансовых операций**: SERIALIZABLE
- **Мониторинг**:
  - Долгие транзакции
  - Deadlocks
  - Конфликты сериализации

## Optimistic and Pessimistic lock
Это два подхода к управлению параллельным доступом к данным в системах с многопоточностью или распределёнными системами. Они используются для предотвращения конфликтов при одновременном изменении одних и тех же данных разными транзакциями.

### Пессимистическая блокировка

**Пессимистическая блокировка** предполагает, что конфликты при одновременном доступе к данным вероятны. Поэтому система блокирует запись данных сразу при их чтении или модификации, предотвращая доступ других транзакций к этим данным до завершения текущей операции.

**Характеристики:**

- **Эксклюзивные блокировки:** Транзакция, получившая блокировку, единственная, кто может изменять данные до её завершения.
- **Предотвращение конфликтов:** Конфликты предотвращаются заранее, так как доступ других транзакций ограничен.
- **Подходит для:** Сценариев с высокой вероятностью конкурентного доступа и частых конфликтов, например, банковские системы.

**Плюсы:**

- Гарантирует отсутствие конфликтов при одновременном доступе.
- Простота понимания и реализации в некоторых системах.

**Минусы:**

- Может привести к снижению производительности из-за блокировок и ожиданий.
- Риск возникновения дедлоков (взаимных блокировок).

### Оптимистическая блокировка

**Оптимистическая блокировка** исходит из предположения, что конфликтов при одновременном доступе к данным происходит редко. Вместо блокировки данных при чтении, система проверяет целостность данных только при записи, чтобы убедиться, что данные не были изменены другой транзакцией.

**Методы реализации:**

- **Версионность:** Каждая запись имеет версию. При обновлении транзакция проверяет, совпадает ли текущая версия с версией при чтении. Если нет — транзакция откатывается или повторяется.
- **Метки времени:** Использование временных меток для отслеживания изменений.

**Плюсы:**

- Высокая производительность при низкой вероятности конфликтов.
- Нет блокировок, что уменьшает вероятность дедлоков.
- Лучшее масштабирование в системах с большим количеством операций чтения.

**Минусы:**

- В случае частых конфликтов может потребоваться много повторных операций, что снизит производительность.
- Сложнее реализовать механизмы проверки версий и отката транзакций.![[Снимок экрана 2025-05-05 в 14.22.20.png]]

## Normalization Denormalization

**Нормализация** — это процесс организации данных в БД для уменьшения избыточности и аномалий через разбиение таблиц и связи между ними.

**Денормализация** — намеренное добавление избыточности для ускорения чтения (например, дублирование данных или объединение таблиц).

**Trade-off:** нормализация улучшает целостность данных, денормализация — производительность чтения.

## BASE
- **Basically Available** — система гарантирует доступность даже при частичных сбоях (например, при потере узла).
- **Soft-state** — данные могут быть временно в не согласованном состоянии, 
- **Eventual consistency** — в конечном счёте данные станут согласованными, но не сразу (например, как в DynamoDB или Cassandra).

**Пример:** Соцсеть может показывать ленту с временными расхождениями между репликами, но через секунду всё синхронизируется.

**Trade-off:** Отказ от строгой согласованности (ACID) ради масштабируемости и отказоустойчивости.


## MVCC

Метод управления параллельным доступом к данным в СУБД, позволяющий нескольким транзакциям одновременно читать и записывать данные без блокировок.

 Ключевые концепции
- **Версии данных:** Каждая запись может иметь несколько версий.
- **Транзакции:** Получают уникальные идентификаторы, определяющие порядок.
- **Видимость версий:** Транзакция видит версии до своего начала.
- **Избежание блокировок:** Чтение и запись не блокируют друг друга.

Как работает
1. **Чтение:** Транзакция считывает последнюю зафиксированную версию данных на момент начала.
2. **Запись:** Создается новая версия записи с новым штампом.
3. **Фиксация:** Изменения становятся видимыми для новых транзакций.
4. **Удаление:** Старые версии удаляются после завершения всех затронутых транзакций.

 Преимущества
- Высокая производительность и параллелизм.
- Обеспечение согласованности данных.
- Лучшая масштабируемость.

Недостатки
- Увеличение объема хранения.
- Сложность управления версиями.
- Возможные задержки на фиксацию.
 Важные понятия
- **Dirty Read:** Избегаются благодаря MVCC.
- **Snapshot Isolation:** Уровень изоляции, реализованный MVCC.
