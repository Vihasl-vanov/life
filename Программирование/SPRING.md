## Inversion of Control (IoC)
— это принцип, который говорит о том, что я как разработчик должен делегировать создание объектов фреймворку  и он будет управлять их жизненным циклом. Spring container берет на себя эту работу(application context) 

- ✔ **Контейнер Spring управляет жизненным циклом объектов** — мы просто указываем, какие классы нужны, а Spring сам их создает и связывает.
    
- ✔ **Гибкость и расширяемость** — можно легко менять зависимости, не лезя в код.
    
- ✔ **Меньше рутины** — можно сосредоточиться на бизнес-логике, а не на инфраструктурных деталях.

В реальной разработке почти все проекты разворачиваются **на нескольких средах**. Например:

- **dev** — для тестирования новой функциональности.
    
- **stage** — для тестирования на приближенной к продакшену системе.
    
- **prod** — реальное окружение, где работают пользователи.

Благодаря IoC, мы можем настроить **разные конфигурации**, и Spring сам выберет нужный бин в зависимости от среды, в которой запущено приложение.![[Снимок экрана 2025-08-31 в 18.03.48.png]]

## Bean and ApplicationContext

**Bean** — это просто обычный объект Java, которым управляет Spring-контейнер. Единственное отличие от привычных объектов в том, что мы **не создаем их вручную** (**new SomeClass()**), а **Spring сам их создает, хранит и управляет ими**.

Все такие бины хранятся в **ApplicationContext** — специальном контейнере, который следит за их созданием, жизненным циклом и внедрением зависимостей.

**ApplicationContext** — это сердце Spring-приложения. Он:

- ✔ Загружает **конфигурацию** (аннотации, XML или Java-код).
    
- ✔ Создает и связывает **бины**.
    
- ✔ Управляет их **жизненным циклом**.
    
- ✔ **Внедряет зависимости** (Dependency Injection).
    
- ✔ Может **управлять транзакциями**.

Каждый бин внутри ApplicationContext имеет **уникальное имя** (по умолчанию — это имя класса с маленькой буквы, но его можно поменять).

### Типы бинов в Spring(scope)

Бины бывают **разных типов**, и от этого зависит, как Spring управляет их жизненным циклом.

#### 📌 **Singleton** (по умолчанию) — **Один объект на все приложение.**

Бин создается **один раз при запуске** и используется **повторно** во всем приложении. Подходит для объектов, которые должны существовать в **единственном экземпляре** (например, сервисы).

#### 📌 **Prototype — Новый объект при каждом запросе.**

Каждый раз, когда мы запрашиваем бин, создается **новый экземпляр**. Подходит, если объект **изменяемый** и **не должен быть общим** (например, объекты с внутренним состоянием). Spring не отвечает за уничтожение таких бинов, нужно самостоятельно все убивать.

#### 📌 **Request — Один бин на каждый HTTP-запрос.**

Новый экземпляр создается для **каждого HTTP-запроса** и уничтожается после завершения запроса. Используется в **Spring MVC** для обработки данных запроса.

#### 📌 **Session — Один бин на сессию пользователя.**

Объект живет **столько же, сколько и сессия пользователя**. Подходит для хранения данных **сессии** (например, информации о пользователе).

**Сессия пользователя** — это временное хранилище данных, которое создается для конкретного пользователя при его первом запросе к серверу и существует, пока пользователь активен. В рамках одной сессии можно хранить информацию, которая должна оставаться неизменной между разными запросами, например, данные о текущем пользователе или настройках. Когда пользователь закрывает браузер или истекает время активности, сессия удаляется.

#### 📌 **Global session — Один бин на всю глобальную сессию.**

Редко используется, но может пригодиться для **распределенных систем**.

**Глобальная сессия пользователя** — это аналог обычной сессии, но с тем отличием, что она едина для всех пользователей, работающих в одном общем контексте (например, в портлет-приложениях). Это значит, что данные глобальной сессии доступны не только конкретному пользователю, но и другим участникам одной и той же группы или системы, где требуется общий доступ к данным на уровне всей платформы.

### **Как получить бин из ApplicationContext?**

Мы можем запросить бин **по типу** или **по имени**:

```java
public class Main {
    public static void main(String[] args) {
        ApplicationContext context = new AnnotationConfigApplicationContext(AppConfig.class);

        // Поиск по типу
        MyBean myBean = context.getBean(MyBean.class);
        System.out.println(myBean.getMessage());

        // Поиск по имени
        MyBean myBeanByName = (MyBean) context.getBean("myBean");
    }
}
```

### Способы конфигурации бинов в Spring

**1. Java-конфигурация (@Configuration + @Bean)**

- Класс помечается `@Configuration`, методы — `@Bean`
    
- Spring создаёт объекты, возвращаемые методами
    
- **Когда использовать**: нужна дополнительная логика при создании, работа со сторонними библиотеками, группировка бинов
    

**2. Аннотации (@Component)**

- Самый простой и популярный способ
    
- Класс помечается `@Component` — Spring сам создаёт бин
    
- **Преимущества**: простота, автоматическое сканирование, не требует конфигурационных классов
    
- Имя бина по умолчанию — название класса с маленькой буквы, можно задать своё: `@Component("myCustomBean")`
    

**3. XML-конфигурация**

- Устаревший способ, используется редко
    
- Конфигурация через XML-файлы с тегом `<bean>`

## Dependecy Injection

В любом приложении объекты не существуют в вакууме — они **взаимодействуют друг с другом**. В **Spring** бины (объекты, которыми управляет контейнер) могут зависеть от других бинов. Эти зависимости нужно **как-то передавать** — с этим помогает **Dependency Injection (DI)**.

**DI позволяет передавать зависимости в объекты автоматически**, без необходимости создавать их вручную. Это делает код **гибким, масштабируемым и удобным в тестировании**.

### **Способы внедрения зависимостей (DI)**

В **Spring** есть три основных способа внедрения зависимостей:

#### **1. Внедрение через конструктор (Constructor DI) — Рекомендуемый способ**

Этот способ **надежный и безопасный**, так как гарантирует, что объект **не создастся без необходимых зависимостей**.

```java
@Service
public class Service {

    private final Repository repository;

    @Autowired
    public Service(Repository repository) {
        this.repository = repository;
    }
}
```

#### **2. Внедрение через сеттер (Setter DI) — Для необязательных зависимостей**

Используется, если зависимость **необязательная** и может изменяться в процессе работы приложения.

```java
@Service
public class Service {
    private Repository repository;

    @Autowired
    public void setRepository(Repository repository) {
        this.repository = repository;
    }
}
```

❌ **Почему не стоит использовать @Autowired на сеттерах?**

- Можно **забыть вызвать сеттер**, и зависимость останется null.
    
- В коде появляется **лишняя изменяемость**, что усложняет поддержку.

#### **3. Внедрение через поле (Field DI) — ❌ НЕ рекомендуется**

Прост в использовании, но **считается плохой практикой**, так как усложняет тестирование и нарушает инкапсуляцию.

```java
@Service
public class Service {
    @Autowired
    private Repository repository;
}
```

 ❌ **Почему не стоит использовать @Autowired на полях?**
- Поля остаются **изменяемыми**, что может привести к ошибкам.
    
- **Сложнее тестировать** (нельзя просто передать mock в конструктор).
    
- **Spring использует рефлексию** для установки значений в поле, что менее эффективно.

### **@RequiredArgsConstructor**

автоматически создаёт конструктор для всех final полей.
✔ **Меньше кода** — не нужно вручную писать конструкторы.

✔ **Автоматическая поддержка DI через Spring**.

✔ **Работает только с final полями**, что делает зависимости **immutable** (что безопаснее).

### **Разрешение конфликтов зависимостей (@Qualifier)**

Что делать, если в **ApplicationContext** есть **несколько бинов одного типа**? Допустим, у нас есть **два репозитория**:

```java
@Repository("userRepository")
public class UserRepository implements Repository { ... }

@Repository("productRepository")
public class ProductRepository implements Repository { ... }
```

![](https://api.faang-school.com/api/storage/file/yg0jjegj.jpeg)

Как сказать Spring'у, какой именно бин нам нужен? Используем **@Qualifier**:

```java
@Service
public class Service {

    private final Repository userRepository;
    private final Repository productRepository;

    @Autowired
    public Service(@Qualifier("userRepository") Repository userRepository,
                   @Qualifier("productRepository") Repository productRepository) {
        this.userRepository = userRepository;
        this.productRepository = productRepository;
    }
}
```

Теперь Spring **точно знает**, какой бин куда вставить.

### @Primary
Как сказать Spring'у, какой бин использовать **по умолчанию**? Используем **@Primary**:

Помечаем основной бин аннотацией `@Primary`. Теперь Spring будет автоматически выбирать этот бин, когда требуется внедрение зависимости, и нет явного указания на конкретный бин.

Когда Spring встречает зависимость типа, для которого существует несколько бинов, он сначала ищет бин с аннотацией `@Primary` и использует его, если не указан конкретный квалификатор.

Это удобно, когда один бин является основным или реализацией по умолчанию, а другие — специализированными вариантами, которые требуются только в особых случаях.

### **DI через конфигурационный класс (@Bean)**

Если мы **не можем пометить класс аннотацией @Component** (например, он из сторонней библиотеки или требуется дополнительная логика при создании объекта), можно описать его в **конфигурации**:

```java
@Configuration
public class AppConfig {

    @Bean
    public Service service(Repository repository) {
        return new Service(repository);
    }

    @Bean
    public Repository repository() {
        return new Repository();
    }
}
```

### **Как Spring понимает, какие зависимости внедрять?**

Spring **использует рефлексию**: он анализирует классы, определяет зависимости и автоматически подставляет нужные бины.

📌 **Важно!**

- ✔ **@Autowired** **можно не писать** в случае одного конструктора — Spring сам догадается, что туда надо внедрять.
    
- ✔ **@Autowired** все же стоит указывать, если хочется **явно показать зависимость**.
    

### **Как не запутаться в зависимостях?**

⚠️ **Много зависимостей — плохо!** Если у вас класс с **10 зависимостями**, это **сигнал, что архитектура приложения неудачная**.

✅ **Советы:**

- ✔ Разбейте **монолитный сервис** на несколько **маленьких**.
    
- ✔ Внедряйте **только нужные зависимости**, не превращая класс в "суперобъект".
    
- ✔ Используйте **интерфейсы** для гибкости.
## Трехслойная архитектура

Она делит код на три независимых слоя, что делает приложение **структурированным, понятным и легко поддерживаемым:**

1. **Контроллеры (Controller)** — принимают запросы, передают их в сервисный слой, а затем формируют и отправляют ответы клиенту.
    
2. **Сервисы (Service)** — содержат **бизнес-логику**: выполняют расчеты, вызывают API, взаимодействуют с базой через репозиторий.
    
3. **Слой доступа к данным (Repository)** — работает с базой данных, управляет запросами и хранением информации.
    

![](https://api.faang-school.com/api/storage/file/08jaamga.jpeg)

Такое разделение позволяет легко **изменять код** в одном слое, не затрагивая другие, что **упрощает разработку, тестирование и поддержку**.

#### **Почему трехслойная архитектура — это топ?**

✅ **Разделение ответственности** – каждый слой выполняет свою задачу.

✅ **Гибкость** – можно менять слои независимо друг от друга.

✅ **Упрощение тестирования** – можно легко тестировать сервисы отдельно от базы и контроллеров.

✅ **Модульность** – можно легко добавлять новые фичи, не затрагивая весь код.

### **Как работает трехслойная архитектура?**

Представим, что у нас есть сайт **фитнес-центра**, где пользователи могут **записываться на тренировки**. Когда клиент **нажимает кнопку "Записаться"**, происходит следующее:

1. **Контроллер** BookingController принимает HTTP-запрос и передает его в сервис.
    
2. **Сервис** BookingService проверяет, есть ли свободные места, создает бронь и вызывает репозиторий для сохранения данных.
    
3. **Репозиторий** BookingRepository сохраняет информацию о бронировании в базе данных.

## @Value

@Value – это аннотация Spring, которая **внедряет значения в бины** из **файлов конфигурации, системных переменных, аргументов командной строки и других источников.

Spring подставляет **значения из application.yaml**

**@Value** применяется для инъекции значений в:

1. **Поля класса** — основной вариант
    
2. **Конструктор** — для immutable-объектов (final-поля)
    
3. **Setter-методы** — если нужна доп. обработка перед установкой
    
4. **Параметры метода** — значение передаётся при вызове метода

## DTO
DTO (Data Transfer Object) - это объект, который используется для передачи данных между слоями приложения.

Он используется для упрощения обмена данными, обеспечивает эффективную передачу данных, снижая избыточность - передавать через такой объект можно не всю сущность целиком, а только те данные, которые необходимы. Это улучшает производительность.

- DTO обычно содержит только необходимые для передачи данные и не содержит бизнес-логики.
    
- DTO позволяют легко адаптировать данные для различных клиентов или для изменений внутренней структуры приложения. Данные, которые хранятся в одной и той же сущности, можно представлять разными ДТО для разных целей.
    
- Использование DTO также позволяет защитить конфиденциальные данные, которые хранятся в сущности. Во "внешний мир" мы отдаем DTO, в котором сами выбираем какие поля отдавать, а какие - нет.

## ComponentScan

**Spring сам находит классы и создает их бины**

Spring сканирует классы **в указанном пакете** и автоматически регистрирует в контексте **все классы с аннотациями @Component, @Service, @Repository, @Controller**.

```java
@Configuration
@ComponentScan("com.faang.school")
public class MainConfig {
    // Конфигурационный класс
}
```

- **@ComponentScan("com.faang.school")** → Spring проверит **все классы внутри com.faang.school**.
    
- **Если найдет @Component или подобные аннотации, то создаст бины**.
    

**Аннотация @ComponentScan нужна, если у вас обычный Spring-проект.**

Spring Boot автоматически **сканирует все классы в текущем пакете и подпакетах**.

```java
@SpringBootApplication
public class MyApp {
    public static void main(String[] args) {
        SpringApplication.run(MyApp.class, args);
    }
}
```

**Почему Spring Boot находит бины сам?**

Потому что **@SpringBootApplication уже включает в себя @ComponentScan!** То есть **Spring сканирует весь пакет, где лежит MyApp, и все его подпакеты**.

### **Можно ли изменить поведение @ComponentScan?**

Да, можно **настроить** поиск компонентов:

#### **1️⃣ Задать несколько пакетов для сканирования**

```java
@ComponentScan({"com.project.services", "com.project.repositories"})
```

#### **2️⃣ Исключить классы из сканирования**

```java
@ComponentScan(
    basePackages = "com.project",
    excludeFilters = @ComponentScan.Filter(type = FilterType.ANNOTATION, classes = Deprecated.class)
)
```

Этот код **исключит все классы с @Deprecated**.


## Жизненный цикл бина
**Bean Lifecycle (Жизненный цикл бина)** — это процесс создания, настройки, использования и уничтожения бина в Spring.

### **Этапы жизненного цикла бина**

1️⃣ **Конфигурация** – Spring находит и регистрирует бин (через аннотации или XML).

2️⃣ **Инстанцирование** – создаётся объект бина.

3️⃣ **Настройка свойств** – внедряются зависимости (через **@Autowired**).

4️⃣ **Инициализация** – вызываются методы, помеченные **@PostConstruct**.

5️⃣ **Использование** – бин выполняет свою работу в приложении.

6️⃣ **Уничтожение** – вызываются методы, помеченные **@PreDestroy**, перед удалением бина.
![](https://api.faang-school.com/api/storage/file/b86jmp8p.jpeg)

### **@PostConstruct — метод выполняется после создания бина**

Используется, чтобы выполнить **дополнительную настройку** бина **после внедрения зависимостей**.

Вызывается после того, как Spring создал бин и внедрил зависимости.

```java
@Repository
@Scope("prototype")
public class D {

    @PostConstruct
    public void openConnection() {
        System.out.println("🔌 Открываем соединение...");
    }

    public void doWork() {
        System.out.println("🛠 Работаем с ресурсом...");
    }
}
```

### **@PreDestroy — метод выполняется перед уничтожением бина**

Используется, чтобы **очистить ресурсы** перед удалением объекта. Вызывается перед тем, как Spring **удалит бин** (например, при завершении работы приложения).

💡 **Важно!** `@PreDestroy` **не вызывается для** `**Prototype**`**-бинов** (их удаляет Garbage Collector).

```java
@Repository
@Scope("prototype")
public class D {

    @PostConstruct
    public void openConnection() {
        System.out.println("🔌 Открываем соединение...");
    }

    @PreDestroy
    public void closeConnection() {
        System.out.println("❌ Закрываем соединение...");
    }
}
```

## Spring Web

Spring Web в стандартной конфигурации является блокирующим фреймворком, что означает, что каждый запрос к серверу блокирует текущий поток выполнения, пока запрос не будет обработан. Это означает, что при большой нагрузке на сервер, когда приходит много запросов одновременно, сервер может столкнуться с проблемой блокировки и обработки запросов с задержкой.

Однако, Spring Web также предоставляет возможность использования неблокирующих операций, что позволяет обрабатывать запросы в асинхронном режиме, не блокируя текущий поток выполнения. Это повышает производительность и уменьшает нагрузку на сервер. Для этого необходимо использовать дополнительные инструменты, такие как Spring WebFlux, который основан на реактивном программировании и позволяет создавать неблокирующие веб-приложения.

## Контроллеры

Контроллеры являются ключевым компонентом Spring Web. Это посредники между пользовательским интерфейсом и приложением и отвечают за обработку запросов от клиента и предоставление необходимой функциональности или данных.

Контроллеры представляют собой классы Java, которые отвечают за обработку HTTP-запросов и возврата HTTP-ответов. Контроллеры обычно содержат несколько методов, каждый из которых обрабатывает определенный тип запроса или URL-адрес.

В Spring Web существует два основных типа контроллеров: `@Controller` и `@RestController`. `@Controller` используется для обработки HTTP-запросов и возврата представлений, таких как HTML-страницы. `@RestController`, с другой стороны, используется для возврата данных в формате JSON, XML или другом формате, который будет интерпретирован как данные. `@RestController` является более простым и эффективным способом создания веб-сервисов, которые работают с данными.

Запрос в Spring Web поступает на `DispatcherServlet` (это Java класс, который представляет из себя центральный контроллер, он знает обо всех остальных контроллерах в нашем приложении) через контейнер сервлетов. Контейнер сервлетов является частью веб-сервера. На всякий случай, вспомним, что такое сервлет.

**Сервлет** (`Servlet`) — это Java-компонент, который выполняет обработку HTTP-запросов и генерирует HTTP-ответы. Он является частью Java Servlet API, который предоставляет среду выполнения для веб-приложений на основе Java.

Сервлеты работают внутри контейнера сервлетов, который обеспечивает среду выполнения для сервлетов. Когда клиент отправляет HTTP-запрос на сервер, сервлет-контейнер принимает этот запрос и передает его соответствующему сервлету для обработки.

Когда запрос приходит на сервер, он сначала обрабатывается веб-сервером, который затем передает его контейнеру сервлетов. Контейнер сервлетов определяет, какой сервлет должен обрабатывать запрос, и запускает его выполнение. Контейнер сервлетов также отвечает за управление жизненным циклом сервлетов, их инициализацию и выгрузку.

Таким образом, процесс отправки HTTP запроса и получения HTTP ответа с помощью контейнера сервлетов и Spring приложения выглядит так:

![](https://api.faang-school.com/api/storage/file/mg7330ge.bin)

Один из самых популярных контейнеров сервлетов сейчас — Apache Tomcat (или просто Tomcat). Tomcat также может выполнять функции балансировки нагрузки и управления сеансами и предоставляет множество дополнительных функций, таких как поддержка SSL-шифрования, аутентификация и авторизация пользователей, логирование и многое другое.

## RequestMapping

`@RequestMapping` — это аннотация в Spring Web, которая используется для привязки URL-адресов к методам контроллера. `@RequestMapping` является более общей аннотацией и может быть использована для обработки запросов любого типа HTTP метода. Она может быть применена к классу контроллера и/или к отдельным методам контроллера. Для методов чаще используются разновидности `@RequestMapping`, как `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`, `@PatchMapping` для обработки запросов соответствующего типа.

Метод `getUsers()` обрабатывает GET запрос по пути `/api/users`. Например: `http://localhost:8080/api/users`

### Обратите внимание:

`/api` в приложении - общий путь для всех методов и всех контроллеров. Поэтому в реализации своего приложения выносите эту часть в конфигурационный файл. Обычно общий путь выглядит так: `/api/v1`, то есть первая версия нашего приложения. В конфиге версию можно будет менять динамично без редеплоя всего приложения в продакшене.

Для конфигурации этого параметра нужно в yaml-файл добавить проперти spring.servlet.mvc.path: + значение.

То есть это именно Spring-конфиг, Spring спринг будет автоматически подтягивать этот путь перед всеми остальными, которые мы прописываем в маппингах.

## ResponseBody

`@ResponseBody` — это аннотация в Spring Web, которая указывает, что возвращаемый из метода контроллера объект должен быть преобразован в тело ответа HTTP. Она облегчает создание RESTful веб-сервисов, предназначенных для работы с данными в формате JSON или XML. Аннотация `@RestController` уже комбинирует функциональность аннотаций `@Controller` и `@ResponseBody`. Поэтому `@ResponseBody` не нужно указывать отдельно в классе с аннотацией `@RestController`.

```java
@RestController
public class MyController {
    private MyService service;
    
    public MyController(MyService service) {
        this.service = service;
    }
    
    @GetMapping("/users")
    public List<User> getUsers() {
        List<User> users = service.getUsers();
        return users;
    }
}
```

В данном примере мы создаём контроллер `MyController`, который связывает путь `/api` с классом контроллера. Далее мы определяем два метода контроллера: `getUsers()` и `createUser()`, которые связываются с путями `/api/users` и `/api/users` соответственно.

```java
@RestController
@RequestMapping("/api")
public class MyController {
    private MyService service;
		
    public MyController(MyService service) {
        this.service = service;
    }
    
    @GetMapping("/users")
    public List<User> getUsers() {
        List<User> users = service.getUsers();
        return users;
    }
    
    @PostMapping("/users")
    public ResponseEntity<User> createUser(@RequestBody UserDto userDto) {
        User user = service.createUser(userDto);
        return ResponseEntity.ok(user);
    }
}
```

Метод `getUsers()` возвращает список пользователей в формате JSON. Возвращаемое значение метода преобразуется в тело ответа HTTP с помощью `@ResponseBody`.

`ResponseEntity` — это класс в Spring Web, который представляет собой полный HTTP-ответ, включая статус ответа, заголовки и тело ответа. Метод `createUser()` создаёт нового пользователя и возвращает `ResponseEntity` с кодом статуса `200 OK` и телом ответа, содержащим созданный объект `User`.

`ResponseEntity` позволяет контролировать полный HTTP-ответ, включая статус ответа, заголовки и тело ответа. Она также предоставляет удобство и простоту в обработке ошибок и обработке запросов. Если вам нужно полное управление над ответом HTTP, вы можете использовать `ResponseEntity`.

## RequestBody

Эту аннотацию вы уже видели в примере выше в аргументах метода `createUser()`. `@RequestBody` позволяет передавать данные запроса в виде **объекта** в метод контроллера.

Например, мы хотим отправить такой запрос:

```java
POST /api/users HTTP/1.1
Host: localhost:8080
Content-Type: application/json

{
    "firstName": "Vlad",
    "lastName": "Mishustin",
    "email": "legend@faang.com"
}
```

Вот как будет выглядеть контроллер:

```java
@RestController
@RequestMapping("/api")
public class MyController {
    private MyService service;

    public MyController(MyService service) {
        this.service = service;
    }

    @PostMapping("/users")
    public ResponseEntity<User> createUser(@RequestBody UserDto userDto) {
        User user = service.createUser(userDto);
        return ResponseEntity.ok(user);
    }
}
```

Аннотация `@RequestBody` указывает, что метод ожидает объект типа `User` в теле запроса. В запросе клиент отправляет объект User в виде JSON, а Spring Web преобразует тело запроса в объект `User` и передает его в метод `createUser()`.

## RequestParam

`@RequestParam` — это аннотация в Spring Web, которая используется для извлечения параметров запроса из строки запроса и передачи их в метод контроллера в качестве параметров.

URL для запроса, использующего `@RequestParam` в качестве аргументов, может выглядеть следующим образом: `GET "<http://localhost:8080/api/users?page=1&size=10”`>

В данном примере мы указываем путь `/api/users` и передаём два параметра запроса — `page` и `size`. Когда клиент отправляет запрос, Spring Web извлекает значения параметров запроса и передаёт их в метод контроллера в качестве параметров.

А вот так выглядит код в контроллере для обработки этого запроса:

```java
@RestController
@RequestMapping("/api")
public class MyController {
    private MyService service;

    public MyController(MyService service) {
        this.service = service;
    }
    
    @GetMapping("/users")
    public List<User> getUsers(@RequestParam("page") int page, @RequestParam("size") int size) {
        List<User> users = service.getUsers(page, size);
        return users;
    }
}
```

Когда клиент отправляет запрос, Spring Web извлекает значения параметров запроса и передает их в метод контроллера в качестве параметров.

## PathVariable

Ещё одна аннотация в Spring Web, которая используется для извлечения переменной из URL-адреса и передачи её в метод контроллера в качестве параметра.

Например, мы отправляем `GET "<http://localhost:8080/api/users/123>"` и хотим получить данные пользователя с id 123.

123 — это и есть path variable, переменная id со значением 123, прописанная в пути запроса.

А так мы напишем нужный нам метод в контроллере:

```
@RestController
@RequestMapping("/api")
public class MyController {
    private MyService service;

    public MyController(MyService service) {
        this.service = service;
    }
    
    @GetMapping("/users/{id}")
    public ResponseEntity<User> getUserById(@PathVariable("id") Long id) {
        User user = service.getById(id);
        return ResponseEntity.ok(user);
    }
}
```

Метод `getUserById()` извлекает переменную `id` из URL-адреса и передает её в метод в качестве параметра. Если операция завершится успешно, метод вернёт объект `User`, который будет отправлен в формате JSON.

## Get-запросы: Post + RequestBody vs. Get + query param
### Как работает Get + query param?

Get-запросы часто передают информацию через **query параметры**. Это такие штуки, которые добавляются в адрес строки, например:

```
<https://mymemes.com/api/memes?type=cat&limit=10>
```

Вот что тут происходит:

URL: **https://mymemes.com/api/memes** — это адрес, куда мы обращаемся.

**Query параметры:**

- **type=cat** — говорит серверу, что мы ищем только котиков.
    
- **limit=10** — просим показать не больше 10 мемов.
    

![](https://api.faang-school.com/api/storage/file/3gva7980.jpg)

**🔧 А как это выглядит в коде на Java?**

```java
@RestController
@RequestMapping("/api/memes")
public class MemeController {

    @GetMapping
    public List<Meme> getMemes(@RequestParam String type, @RequestParam int limit) {
        // Здесь читаем параметры и возвращаем данные
        return memeService.getMemes(type, limit);
    }
}
```

### Get + FilterDto

А еще вместо того, чтобы принимать каждый параметр запроса по отдельности (через **@RequestParam**), можно передавать сразу целый объект (например, **FilterDto**) как query-параметры, не используя аннотацию **@RequestBody**.

Это работает потому что, если у метода-контроллера есть единственный аргумент-POJO (Plain Old Java Object) без **@RequestBody**, Spring автоматически пытается связать поля этого объекта с query-параметрами запроса. То есть достаточно, чтобы названия полей в вашем **FilterDto** совпадали с именами query-параметров, и всё «соберётся» автоматически.

**🔧 Как это выглядит в коде?**

Например, у вас есть **FilterDto** с полями **type** и **limit**:

```java
public class FilterDto {
    private String type;
    private int limit;

    // геттеры и сеттеры
}
```

Тогда в контроллере можно сделать так:

```java
@GetMapping
public List<Meme> getMemes(FilterDto filter) {
    return memeService.getMemes(filter.getType(), filter.getLimit());
}

```

При вызове **/api/memes?type=funny&limit=10** объект **filter** будет проинициализирован полями **type="funny"** и **limit=10**.

Основной нюанс – не добавлять к этому объекту аннотацию **@RequestBody**, иначе Spring попытается искать данные в теле запроса (body), а не в query-параметрах.

### Как работает Post + RequestBody?

Теперь про Post-запросы. Данные в них передаются в теле запроса (RequestBody). Это не видно в строке браузера.

📋 **Пример запроса:**

```java
POST <https://mymemes.com/api/memes/filter>
Content-Type: application/json

{
  "type": "cat",
  "limit": 10
}

```

Сервер читает данные из тела запроса, а не из строки URL. Это удобно, когда данных слишком много или они чувствительные (например, пароль).

![](https://api.faang-school.com/api/storage/file/k8n3m0gj.jpg)

🔧 **А как это выглядит в коде на Java?**

```java
@RestController
@RequestMapping("/api/memes")
public class MemeController {

    @PostMapping("/filter")
    public List<Meme> filterMemes(@RequestBody MemeFilterRequest request) {
        // Здесь читаем данные из тела запроса и фильтруем мемы
        return memeService.filterMemes(request.getType(), request.getLimit());
    }
}
```

### Get vs. Post:

**Когда использовать Get + query param?**

- Когда данные не секретные.
    
- Когда запрос простой и его можно выразить в строке.
    
- Когда вы хотите передать ссылку другому человеку.
    

**Когда использовать Post + RequestBody?**

- Когда данные чувствительные.
    
- Когда данные сложные и их слишком много для query параметров.
    
- Когда сервер ожидает изменения данных.

## RestTemplate
предоставляет удобный способ взаимодействия Spring приложения с внешними REST-сервисами. Он предоставляет удобный API для отправки запросов и получения ответов, а также для десериализации данных из формата JSON или XML.

Т.е. раньше вы сами руками через Postman посылали HTTP запрос в ваше Spring приложение. А теперь можете сделать так, чтобы ваше приложение на Spring могло послать запрос в любое другое web-приложение, используя его REST API. Т.е. послать такой запрос именно программно, а не вручную.

RestTemplate включают в себя:

1. Конфигурация клиента HTTP. Можно настроить RestTemplate для использования специальной реализации клиента HTTP. Это может быть полезно, например, для настройки соединения или поддержки прокси-серверов.
    
2. Настройка таймаутов. Это может быть полезно для обеспечения более высокой производительности приложения и уменьшения риска блокировки приложения при медленном ответе от сервера.
    
3. Добавление интерсепторов. Можно добавить интерсепторы для запросов и ответов, которые будут выполняться перед и после отправки запроса. Это может быть полезно, например, для добавления заголовков авторизации или логирования запросов и ответов.
    
4. Настройка сериализаторов и десериализаторов. Можно настроить RestTemplate для использования различных сериализаторов и десериализаторов для преобразования данных в форматы JSON, XML и другие форматы.

## Валидация данных

**Валидация** — это процесс проверки входных данных на соответствие определённым требованиям. Существует несколько способов проведения валидации данных:

- Проверка на стороне клиента — это проверка входных данных на стороне клиента (например, веб-браузера), с помощью JavaScript. Это позволяет предотвратить отправку некорректных данных на сервер. Однако, такой подход может быть обойдён злоумышленником, поэтому проверка на стороне сервера также является обязательной.
    
- Проверка на стороне сервера позволяет убедиться в корректности данных и предотвращает ошибки ввода и непредвиденное поведение приложения.

Java Bean Validation API предоставляет ряд аннотаций, которые могут быть использованы для определения правил валидации. Некоторые из наиболее распространенных аннотаций включают в себя:

- `@NotNull` — используется для проверки, что значение поля не равно null;
    
- `@Size` — используется для проверки, что длина значения поля находится в заданных границах;
    
- `@Min` и `@Max` — используются для проверки, что значение поля находится в заданных пределах;
    
- `@Email` — используется для проверки, что значение поля соответствует формату email адреса;
    
- `@Pattern` — используется для проверки, что значение поля соответствует заданному регулярному выражению;
    
- `@NotEmpty` — используются для проверки, что значение поля не пустое;
    
- `@NotBlank` — используются для проверки, что значение поля не пустое или не содержит только пробельные символы;
    
- `@Valid` — используется для указания, что нужно провести валидацию вложенного объекта.
    

Кстати, у большинства этих аннотаций есть параметр `message` для того, чтобы можно было добавить своё сообщение в случае ошибки валидации.

##  Обработка исключений
Аннотация `@ExceptionHandler` позволяет определить метод, который будет вызван в случае возникновения исключения определённого типа в контроллере.

Аннотация `@ControllerAdvice` позволяет определить глобальные обработчики исключений для всех контроллеров в приложении.

Использование аннотации `@ControllerAdvice` и методов с аннотацией `@ExceptionHandler` позволяет централизованно управлять обработкой исключений в приложении и предоставлять более информативные сообщения об ошибках для пользователей.

Аннотация `@ControllerAdvice` и методы с аннотацией `@ExceptionHandler` могут быть использованы не только для обработки исключений в контроллерах, но и для других компонентов приложения, например, сервисов.

## MultipartFile

`MultipartFile` — это интерфейс, который представляет загруженный файл, отправленный на сервер в виде HTTP-запроса. Он позволяет получить содержимое файла, его имя, размер, тип содержимого и другую метаинформацию.

```java
@PostMapping("/uploadFiles")
public ResponseEntity<String> uploadMultipleFiles(@RequestPart("files") MultipartFile[] files) {
    String fileNames = "";
    for (MultipartFile file : files) {
        fileNames += file.getOriginalFilename() + ", ";
    }
    return ResponseEntity.ok("Files uploaded: " + fileNames);
}
```

`MultipartFile` также содержит методы для сохранения файла на сервере, проверки размера и типа файла, получения потока содержимого и т.д.

## Sсheduled

Механизм Scheduler в Spring Framework предназначен для автоматического запуска задач в заданные интервалы или в определённые моменты времени. Этот механизм очень полезен в приложениях, где необходимо выполнять определённые операции на регулярной основе, например, обновлять кэш, отправлять email-уведомления, обновлять базу данных и так далее. В реальных приложениях этот механизм используется постоянно.

Чтобы использовать аннотацию `@Scheduled` в Spring Framework, необходимо добавить аннотацию `@EnableScheduling` в вашу конфигурационный класс или в класс, который аннотирован как `@SpringBootApplication`. Вот так:

```java
@SpringBootApplication
@EnableScheduling
public class SpaceShipApplication {
    public static void main(String[] args) {
        SpringApplication.run(SpaceShipApplication.class, args);
    }
}
```

```java
// Запускать метод каждые 30 минут (в миллисекундах)
    @Scheduled(fixedDelay = 1800000) 
```

Аннотация `@Scheduled` — это аннотация уровня метода, то есть вешать её нужно на тот метод, который должен выполняться по расписанию. Только методы с типом возвращаемого значения `void`  и без параметров можно сделать запланированным событием с помощью аннотации `@Scheduled`. Как видно здесь, аннотация принимает ряд параметров, которые позволяют настраивать её поведение:

- `cron` — позволяет задавать расписание выполнения задач с использованием стандартной синтаксиса cron. Например, можно задать запуск задачи каждую секунду: `@Scheduled(cron = "0/1 * * * * *")`;
    
- `fixedDelay` — указывает фиксированную задержку между окончанием выполнения предыдущей задачи и началом выполнения следующей задачи. Например, `@Scheduled(fixedDelay = 1000)` означает, что задача будет запускаться каждую секунду после окончания предыдущего выполнения;
    
- `fixedRate` — указывает фиксированную задержку между началом выполнения двух последовательных задач, независимо от того, сколько времени заняла предыдущая задача. Например, `@Scheduled(fixedRate = 1000)` означает, что задача будет запускаться каждую секунду, независимо от того, сколько времени заняло предыдущее выполнение;
    
- `initialDelay` — позволяет указать задержку перед первым запуском задачи. Например, `@Scheduled(initialDelay = 5000, fixedRate = 1000)` означает, что первый запуск задачи произойдет через 5 секунд после старта приложения, а далее задача будет запускаться каждую секунду;
    
- `zone` — позволяет указать временную зону, в которой будет выполняться задача. По умолчанию используется системная временная зона.
    

Обычно в коде приложения можно ссылаться на значения свойств из нашего файла свойств в качестве значения атрибутов `fixedDelayString` или `fixedRateString` для задания значений интервала:

```java
@Scheduled(fixedDelayString = "${fixedDelay.in.milliseconds}")
```

Здесь мы установили фиксированный интервал задержки как свойство в нашем файле `application.yaml`. То есть, в файле конфигурации теперь содержится что-то такое:

```java
fixedDelay:
	in:
	  milliseconds: 1800000
```

## Async

Аннотация `@Async` в Spring Framework позволяет асинхронно выполнять методы, помеченные этой аннотацией. Асинхронное выполнение означает, что метод будет выполнен в отдельном потоке, и управление будет возвращено вызывающему потоку.

При использовании аннотации `@Async` метод должен возвращать `void` или `Future<T>`, где `T` — тип возвращаемого значения метода. Если метод возвращает `Future<T>`, то результат его работы можно получить позднее с помощью вызова метода `get()`.

Для использования `@Async` необходимо настроить исполнитель (executor), который будет запускать асинхронные методы. По умолчанию Spring создает однопоточный исполнитель, но это можно изменить, настроив свой экземпляр `TaskExecutor`. Можно использовать и стандартный `ThreadPoolTaskExecutor`, который создаёт пул потоков для выполнения методов.

- Асинхронные методы должны вызываться из другого компонента. То есть, если мы вызываем метод с аннотацией `@Async` из того же класса, где он определен, то это не будет работать;
    
- Spring создаёт пул потоков для выполнения асинхронных методов. По умолчанию используется пул из 1 потока, но его можно настроить в файле конфигурации;
    
- Асинхронные методы должны возвращать объект типа `CompletableFuture`. Это нужно для того, чтобы мы могли получить результат выполнения метода в будущем, когда он завершится;
    
- Методы с аннотацией `@Async` могут вызываться только из `public` методов других классов. Если мы попытаемся вызвать асинхронный метод из `private` или `protected` метода, то он не будет выполнен асинхронно;
    
- Асинхронные методы не гарантируют порядок выполнения. То есть, если мы вызываем несколько асинхронных методов, то мы не можем быть уверены в том, что они будут выполнены в том же порядке, в котором мы их вызывали. Если порядок выполнения важен, то нам нужно использовать другие механизмы синхронизации, такие как блокировки или семафоры.

## EventListener
Когда событие генерируется в нашем приложении, Spring ищет методы-обработчики с аннотацией `@EventListener`, которые соответствуют типу события. Если метод-обработчик найден, он будет вызван с параметром, содержащим информацию о событии

- Методы, отмеченные `@EventListener`, должны быть `public`, чтобы Spring мог вызывать их во время обработки событий;
    
- Если методы, отмеченные `@EventListener`, бросают исключение, Spring перехватит их и зарегистрирует как событие ошибки;
    
- Если в вашем приложении есть несколько экземпляров классов, обработчиков событий (`@EventListener`) будут вызываться для каждого экземпляра класса;
    
- Если вы хотите изменить порядок обработки событий, можно использовать аннотацию `@Order`, которая позволяет указать порядок, в котором методы будут вызываться;
    
- `@EventListener` также поддерживает фильтры событий, которые позволяют указать, какие события будут обработаны методом, а какие нет;
    
- Методы, отмеченные `@EventListener`, могут использоваться для обработки не только пользовательских событий, но и событий, связанных с жизненным циклом Spring, таких как события контекста приложения;
    
- `@EventListener` может быть использован в сочетании с другими фреймворками, такими как Kafka и RabbitMQ, например, чтобы обрабатывать сообщения из очередей и обменов;
    

Таким образом, использование `@EventListener` позволяет нам создавать реактивные приложения, которые могут реагировать на различные события и выполнять нужные нам действия в соответствии с ними.

## Spring Data

• `CrudRepository` — это базовый интерфейс, который предоставляет основные операции CRUD (Create, Read, Update, Delete). Он включает методы для сохранения, удаления, поиска и получения всех сущностей. Интерфейс `CrudRepository` предоставляет минимальный набор функций для работы с сущностями;

• `JpaRepository` — это интерфейс, расширяющий `CrudRepository` и предоставляющий дополнительные функции для работы с сущностями. `JpaRepository` включает методы для пагинации, сортировки, выполнения запросов на основе примера (query by example) и другие расширенные функции. Об этом поговорим немного ниже. В целом, он предоставляет более широкий спектр возможностей по сравнению с `CrudRepository`.

```java
@Repository
public interface PersonRepository extends CrudRepository<Person, Long> {
    List<Person> findByFirstName(String firstName);
    List<Person> findByLastName(String lastName);
    // Другие методы репозитория
}
```

Под капотом Spring Data использует механизм рефлексии и анализа метаданных для преобразования именованных методов в соответствующие SQL-запросы. Когда вы вызываете метод репозитория, Spring Data анализирует его имя и параметры, чтобы определить, какой SQL-запрос нужно сгенерировать.

Spring Data предоставляет аннотации, такие как `@Query`, которые позволяют написать пользовательские SQL-запросы

```java
@Repository
public interface PersonRepository extends CrudRepository<Person, Long> {

    @Query(value = "SELECT * FROM person WHERE age > :age", nativeQuery = true)
		List<Person> findByAgeGreaterThan(@Param("age") int age);
}
```
