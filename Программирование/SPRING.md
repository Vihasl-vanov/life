## Inversion of Control (IoC)
— это принцип, который говорит о том, что я как разработчик должен делегировать создание объектов фреймворку  и он будет управлять их жизненным циклом. Spring container берет на себя эту работу(application context) 

- ✔ **Контейнер Spring управляет жизненным циклом объектов** — мы просто указываем, какие классы нужны, а Spring сам их создает и связывает.
    
- ✔ **Гибкость и расширяемость** — можно легко менять зависимости, не лезя в код.
    
- ✔ **Меньше рутины** — можно сосредоточиться на бизнес-логике, а не на инфраструктурных деталях.

В реальной разработке почти все проекты разворачиваются **на нескольких средах**. Например:

- **dev** — для тестирования новой функциональности.
    
- **stage** — для тестирования на приближенной к продакшену системе.
    
- **prod** — реальное окружение, где работают пользователи.

Благодаря IoC, мы можем настроить **разные конфигурации**, и Spring сам выберет нужный бин в зависимости от среды, в которой запущено приложение.![[Снимок экрана 2025-08-31 в 18.03.48.png]]

## Bean and ApplicationContext

**Bean** — это просто обычный объект Java, которым управляет Spring-контейнер. Единственное отличие от привычных объектов в том, что мы **не создаем их вручную** (**new SomeClass()**), а **Spring сам их создает, хранит и управляет ими**.

Все такие бины хранятся в **ApplicationContext** — специальном контейнере, который следит за их созданием, жизненным циклом и внедрением зависимостей.

**ApplicationContext** — это сердце Spring-приложения. Он:

- ✔ Загружает **конфигурацию** (аннотации, XML или Java-код).
    
- ✔ Создает и связывает **бины**.
    
- ✔ Управляет их **жизненным циклом**.
    
- ✔ **Внедряет зависимости** (Dependency Injection).
    
- ✔ Может **управлять транзакциями**.

Каждый бин внутри ApplicationContext имеет **уникальное имя** (по умолчанию — это имя класса с маленькой буквы, но его можно поменять).

### Типы бинов в Spring(scope)

Бины бывают **разных типов**, и от этого зависит, как Spring управляет их жизненным циклом.

#### 📌 **Singleton** (по умолчанию) — **Один объект на все приложение.**

Бин создается **один раз при запуске** и используется **повторно** во всем приложении. Подходит для объектов, которые должны существовать в **единственном экземпляре** (например, сервисы).

#### 📌 **Prototype — Новый объект при каждом запросе.**

Каждый раз, когда мы запрашиваем бин, создается **новый экземпляр**. Подходит, если объект **изменяемый** и **не должен быть общим** (например, объекты с внутренним состоянием). Spring не отвечает за уничтожение таких бинов, нужно самостоятельно все убивать.

#### 📌 **Request — Один бин на каждый HTTP-запрос.**

Новый экземпляр создается для **каждого HTTP-запроса** и уничтожается после завершения запроса. Используется в **Spring MVC** для обработки данных запроса.

#### 📌 **Session — Один бин на сессию пользователя.**

Объект живет **столько же, сколько и сессия пользователя**. Подходит для хранения данных **сессии** (например, информации о пользователе).

**Сессия пользователя** — это временное хранилище данных, которое создается для конкретного пользователя при его первом запросе к серверу и существует, пока пользователь активен. В рамках одной сессии можно хранить информацию, которая должна оставаться неизменной между разными запросами, например, данные о текущем пользователе или настройках. Когда пользователь закрывает браузер или истекает время активности, сессия удаляется.

#### 📌 **Global session — Один бин на всю глобальную сессию.**

Редко используется, но может пригодиться для **распределенных систем**.

**Глобальная сессия пользователя** — это аналог обычной сессии, но с тем отличием, что она едина для всех пользователей, работающих в одном общем контексте (например, в портлет-приложениях). Это значит, что данные глобальной сессии доступны не только конкретному пользователю, но и другим участникам одной и той же группы или системы, где требуется общий доступ к данным на уровне всей платформы.

### **Как получить бин из ApplicationContext?**

Мы можем запросить бин **по типу** или **по имени**:

```java
public class Main {
    public static void main(String[] args) {
        ApplicationContext context = new AnnotationConfigApplicationContext(AppConfig.class);

        // Поиск по типу
        MyBean myBean = context.getBean(MyBean.class);
        System.out.println(myBean.getMessage());

        // Поиск по имени
        MyBean myBeanByName = (MyBean) context.getBean("myBean");
    }
}
```

### Способы конфигурации бинов в Spring

**1. Java-конфигурация (@Configuration + @Bean)**

- Класс помечается `@Configuration`, методы — `@Bean`
    
- Spring создаёт объекты, возвращаемые методами
    
- **Когда использовать**: нужна дополнительная логика при создании, работа со сторонними библиотеками, группировка бинов
    

**2. Аннотации (@Component)**

- Самый простой и популярный способ
    
- Класс помечается `@Component` — Spring сам создаёт бин
    
- **Преимущества**: простота, автоматическое сканирование, не требует конфигурационных классов
    
- Имя бина по умолчанию — название класса с маленькой буквы, можно задать своё: `@Component("myCustomBean")`
    

**3. XML-конфигурация**

- Устаревший способ, используется редко
    
- Конфигурация через XML-файлы с тегом `<bean>`

## Dependecy Injection

В любом приложении объекты не существуют в вакууме — они **взаимодействуют друг с другом**. В **Spring** бины (объекты, которыми управляет контейнер) могут зависеть от других бинов. Эти зависимости нужно **как-то передавать** — с этим помогает **Dependency Injection (DI)**.

**DI позволяет передавать зависимости в объекты автоматически**, без необходимости создавать их вручную. Это делает код **гибким, масштабируемым и удобным в тестировании**.

### **Способы внедрения зависимостей (DI)**

В **Spring** есть три основных способа внедрения зависимостей:

#### **1. Внедрение через конструктор (Constructor DI) — Рекомендуемый способ**

Этот способ **надежный и безопасный**, так как гарантирует, что объект **не создастся без необходимых зависимостей**.

```java
@Service
public class Service {

    private final Repository repository;

    @Autowired
    public Service(Repository repository) {
        this.repository = repository;
    }
}
```

#### **2. Внедрение через сеттер (Setter DI) — Для необязательных зависимостей**

Используется, если зависимость **необязательная** и может изменяться в процессе работы приложения.

```java
@Service
public class Service {
    private Repository repository;

    @Autowired
    public void setRepository(Repository repository) {
        this.repository = repository;
    }
}
```

❌ **Почему не стоит использовать @Autowired на сеттерах?**

- Можно **забыть вызвать сеттер**, и зависимость останется null.
    
- В коде появляется **лишняя изменяемость**, что усложняет поддержку.

#### **3. Внедрение через поле (Field DI) — ❌ НЕ рекомендуется**

Прост в использовании, но **считается плохой практикой**, так как усложняет тестирование и нарушает инкапсуляцию.

```java
@Service
public class Service {
    @Autowired
    private Repository repository;
}
```

 ❌ **Почему не стоит использовать @Autowired на полях?**
- Поля остаются **изменяемыми**, что может привести к ошибкам.
    
- **Сложнее тестировать** (нельзя просто передать mock в конструктор).
    
- **Spring использует рефлексию** для установки значений в поле, что менее эффективно.

### **@RequiredArgsConstructor**

автоматически создаёт конструктор для всех final полей.
✔ **Меньше кода** — не нужно вручную писать конструкторы.

✔ **Автоматическая поддержка DI через Spring**.

✔ **Работает только с final полями**, что делает зависимости **immutable** (что безопаснее).

### **Разрешение конфликтов зависимостей (@Qualifier)**

Что делать, если в **ApplicationContext** есть **несколько бинов одного типа**? Допустим, у нас есть **два репозитория**:

```java
@Repository("userRepository")
public class UserRepository implements Repository { ... }

@Repository("productRepository")
public class ProductRepository implements Repository { ... }
```

![](https://api.faang-school.com/api/storage/file/yg0jjegj.jpeg)

Как сказать Spring'у, какой именно бин нам нужен? Используем **@Qualifier**:

```java
@Service
public class Service {

    private final Repository userRepository;
    private final Repository productRepository;

    @Autowired
    public Service(@Qualifier("userRepository") Repository userRepository,
                   @Qualifier("productRepository") Repository productRepository) {
        this.userRepository = userRepository;
        this.productRepository = productRepository;
    }
}
```

Теперь Spring **точно знает**, какой бин куда вставить.

### @Primary
Как сказать Spring'у, какой бин использовать **по умолчанию**? Используем **@Primary**:

Помечаем основной бин аннотацией `@Primary`. Теперь Spring будет автоматически выбирать этот бин, когда требуется внедрение зависимости, и нет явного указания на конкретный бин.

Когда Spring встречает зависимость типа, для которого существует несколько бинов, он сначала ищет бин с аннотацией `@Primary` и использует его, если не указан конкретный квалификатор.

Это удобно, когда один бин является основным или реализацией по умолчанию, а другие — специализированными вариантами, которые требуются только в особых случаях.

### **DI через конфигурационный класс (@Bean)**

Если мы **не можем пометить класс аннотацией @Component** (например, он из сторонней библиотеки или требуется дополнительная логика при создании объекта), можно описать его в **конфигурации**:

```java
@Configuration
public class AppConfig {

    @Bean
    public Service service(Repository repository) {
        return new Service(repository);
    }

    @Bean
    public Repository repository() {
        return new Repository();
    }
}
```

### **Как Spring понимает, какие зависимости внедрять?**

Spring **использует рефлексию**: он анализирует классы, определяет зависимости и автоматически подставляет нужные бины.

📌 **Важно!**

- ✔ **@Autowired** **можно не писать** в случае одного конструктора — Spring сам догадается, что туда надо внедрять.
    
- ✔ **@Autowired** все же стоит указывать, если хочется **явно показать зависимость**.
    

### **Как не запутаться в зависимостях?**

⚠️ **Много зависимостей — плохо!** Если у вас класс с **10 зависимостями**, это **сигнал, что архитектура приложения неудачная**.

✅ **Советы:**

- ✔ Разбейте **монолитный сервис** на несколько **маленьких**.
    
- ✔ Внедряйте **только нужные зависимости**, не превращая класс в "суперобъект".
    
- ✔ Используйте **интерфейсы** для гибкости.
## Трехслойная архитектура

Она делит код на три независимых слоя, что делает приложение **структурированным, понятным и легко поддерживаемым:**

1. **Контроллеры (Controller)** — принимают запросы, передают их в сервисный слой, а затем формируют и отправляют ответы клиенту.
    
2. **Сервисы (Service)** — содержат **бизнес-логику**: выполняют расчеты, вызывают API, взаимодействуют с базой через репозиторий.
    
3. **Слой доступа к данным (Repository)** — работает с базой данных, управляет запросами и хранением информации.
    

![](https://api.faang-school.com/api/storage/file/08jaamga.jpeg)

Такое разделение позволяет легко **изменять код** в одном слое, не затрагивая другие, что **упрощает разработку, тестирование и поддержку**.

#### **Почему трехслойная архитектура — это топ?**

✅ **Разделение ответственности** – каждый слой выполняет свою задачу.

✅ **Гибкость** – можно менять слои независимо друг от друга.

✅ **Упрощение тестирования** – можно легко тестировать сервисы отдельно от базы и контроллеров.

✅ **Модульность** – можно легко добавлять новые фичи, не затрагивая весь код.

### **Как работает трехслойная архитектура?**

Представим, что у нас есть сайт **фитнес-центра**, где пользователи могут **записываться на тренировки**. Когда клиент **нажимает кнопку "Записаться"**, происходит следующее:

1. **Контроллер** BookingController принимает HTTP-запрос и передает его в сервис.
    
2. **Сервис** BookingService проверяет, есть ли свободные места, создает бронь и вызывает репозиторий для сохранения данных.
    
3. **Репозиторий** BookingRepository сохраняет информацию о бронировании в базе данных.

## @Value

@Value – это аннотация Spring, которая **внедряет значения в бины** из **файлов конфигурации, системных переменных, аргументов командной строки и других источников.

Spring подставляет **значения из application.yaml**

**@Value** применяется для инъекции значений в:

1. **Поля класса** — основной вариант
    
2. **Конструктор** — для immutable-объектов (final-поля)
    
3. **Setter-методы** — если нужна доп. обработка перед установкой
    
4. **Параметры метода** — значение передаётся при вызове метода

## DTO
DTO (Data Transfer Object) - это объект, который используется для передачи данных между слоями приложения.

Он используется для упрощения обмена данными, обеспечивает эффективную передачу данных, снижая избыточность - передавать через такой объект можно не всю сущность целиком, а только те данные, которые необходимы. Это улучшает производительность.

- DTO обычно содержит только необходимые для передачи данные и не содержит бизнес-логики.
    
- DTO позволяют легко адаптировать данные для различных клиентов или для изменений внутренней структуры приложения. Данные, которые хранятся в одной и той же сущности, можно представлять разными ДТО для разных целей.
    
- Использование DTO также позволяет защитить конфиденциальные данные, которые хранятся в сущности. Во "внешний мир" мы отдаем DTO, в котором сами выбираем какие поля отдавать, а какие - нет.

## ComponentScan

**Spring сам находит классы и создает их бины**

Spring сканирует классы **в указанном пакете** и автоматически регистрирует в контексте **все классы с аннотациями @Component, @Service, @Repository, @Controller**.

```java
@Configuration
@ComponentScan("com.faang.school")
public class MainConfig {
    // Конфигурационный класс
}
```

- **@ComponentScan("com.faang.school")** → Spring проверит **все классы внутри com.faang.school**.
    
- **Если найдет @Component или подобные аннотации, то создаст бины**.
    

**Аннотация @ComponentScan нужна, если у вас обычный Spring-проект.**

Spring Boot автоматически **сканирует все классы в текущем пакете и подпакетах**.

```java
@SpringBootApplication
public class MyApp {
    public static void main(String[] args) {
        SpringApplication.run(MyApp.class, args);
    }
}
```

**Почему Spring Boot находит бины сам?**

Потому что **@SpringBootApplication уже включает в себя @ComponentScan!** То есть **Spring сканирует весь пакет, где лежит MyApp, и все его подпакеты**.

### **Можно ли изменить поведение @ComponentScan?**

Да, можно **настроить** поиск компонентов:

#### **1️⃣ Задать несколько пакетов для сканирования**

```java
@ComponentScan({"com.project.services", "com.project.repositories"})
```

#### **2️⃣ Исключить классы из сканирования**

```java
@ComponentScan(
    basePackages = "com.project",
    excludeFilters = @ComponentScan.Filter(type = FilterType.ANNOTATION, classes = Deprecated.class)
)
```

Этот код **исключит все классы с @Deprecated**.


## Жизненный цикл бина
**Bean Lifecycle (Жизненный цикл бина)** — это процесс создания, настройки, использования и уничтожения бина в Spring.

### **Этапы жизненного цикла бина**

1️⃣ **Конфигурация** – Spring находит и регистрирует бин (через аннотации или XML).

2️⃣ **Инстанцирование** – создаётся объект бина.

3️⃣ **Настройка свойств** – внедряются зависимости (через **@Autowired**).

4️⃣ **Инициализация** – вызываются методы, помеченные **@PostConstruct**.

5️⃣ **Использование** – бин выполняет свою работу в приложении.

6️⃣ **Уничтожение** – вызываются методы, помеченные **@PreDestroy**, перед удалением бина.
![](https://api.faang-school.com/api/storage/file/b86jmp8p.jpeg)

### **@PostConstruct — метод выполняется после создания бина**

Используется, чтобы выполнить **дополнительную настройку** бина **после внедрения зависимостей**.

Вызывается после того, как Spring создал бин и внедрил зависимости.

```java
@Repository
@Scope("prototype")
public class D {

    @PostConstruct
    public void openConnection() {
        System.out.println("🔌 Открываем соединение...");
    }

    public void doWork() {
        System.out.println("🛠 Работаем с ресурсом...");
    }
}
```

### **@PreDestroy — метод выполняется перед уничтожением бина**

Используется, чтобы **очистить ресурсы** перед удалением объекта. Вызывается перед тем, как Spring **удалит бин** (например, при завершении работы приложения).

💡 **Важно!** `@PreDestroy` **не вызывается для** `**Prototype**`**-бинов** (их удаляет Garbage Collector).

```java
@Repository
@Scope("prototype")
public class D {

    @PostConstruct
    public void openConnection() {
        System.out.println("🔌 Открываем соединение...");
    }

    @PreDestroy
    public void closeConnection() {
```
