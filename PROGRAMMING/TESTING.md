**Пирамида тестирования: 70/20/10**

В мире разработки существует **концепция пирамиды тестирования**, которая распределяет **разные типы тестов** в проекте:

![](https://api.faang-school.com/api/storage/file/3gv3zb80.jpeg)

- 📌 **70%** — **Unit-тесты** 🏗 (проверяют отдельные классы и методы) — Unit-тесты **должны быть основой**, потому что они **быстрые, стабильные и легко запускаются**.
    
- 📌 **20%** — **Интеграционные тесты** 🔗 (проверяют, как классы взаимодействуют между собой) — Интеграционные тесты **важны**, но их запуск занимает больше времени.
    
- 📌 **10%** — **UI-тесты** 🖥 (проверяют работу интерфейса) — UI-тесты **очень дорогие и медленные**, их используют реже.

## Базовые аннотации JUnit 5

Давайте рассмотрим главные аннотации, которые вы будете чаще всего использовать.

### @Test

Это основная аннотация, которая говорит: «Вот метод – это тест, запусти его!».

### @BeforeAll / @AfterAll

- **@BeforeAll**: метод, помеченный этой аннотацией, запускается один раз **до всех тестов** в классе.
    
- **@AfterAll**: соответственно, запускается один раз **после всех тестов**.
    

**Важно**: по умолчанию методы с **@BeforeAll/@AfterAll** должны быть статическими. Если мы хотим сделать их нестатическими, нужно ставить **@TestInstance(TestInstance.Lifecycle.PER_CLASS)** над классом теста.

### @BeforeEach / @AfterEach

- **@BeforeEach**: запускается перед **каждым** тестовым методом.
    
- **@AfterEach**: запускается после **каждого** тестового метода.
    

Очень полезно, если тебе нужно подготовить какие-то данные для теста или очистить ресурсы (например, файлы, коннекции к базе) после выполнения.

### Assertions: проверки результатов

Чаще всего в тестах мы хотим проверить, что результат работы кода соответствует ожиданиям. Для этого в JUnit 5 есть класс **org.junit.jupiter.api.Assertions.**

Примеры самых популярных методов:

- **assertEquals(expected, actual)** – проверяет, равен ли результат ожиданию.
    
- **assertNotEquals(unexpected, actual)** – проверяет, что два значения не равны.
    
- **assertTrue(condition) / assertFalse(condition)** – проверяют булевские условия.
    
- **assertNotNull(object)** – проверяет, что объект не null.
    
- **assertThrows(Exception.class, () -> { ... })** – проверяет, что при выполнении кода выбрасывается нужное исключение.

### Распространённые ошибки

**🚨 Методы с @BeforeAll и @AfterAll не работают, тесты их не вызывают.**

**Причина**: Эти методы должны быть статическими (если не используется **@TestInstance(TestInstance.Lifecycle.PER_CLASS)**).

**🚨** Использую @Test из **org.junit.Test**, а не из **org.junit.jupiter.api.Test**.

**Причина**: Вы случайно импортировали JUnit 4-аннотацию, а не JUnit 5. Нужно следить за импортами.

**🚨** Тесты не находятся системой сборки.

Нужно, чтобы тесты лежали в папке **src/test/java**, иначе Maven/Gradle их не видит.

**🚨** «Почему несколько методов с **@Test** запускаются не в том порядке, в каком я их написал?»

По спецификации JUnit порядок тестов не гарантируется. Если нужен строгий порядок – есть аннотация @TestMethodOrder, но лучше полагаться на независимость тестов друг от друга.

### Что такое «Arrange-Act-Assert»?

![](https://api.faang-school.com/api/storage/file/xg9w52gw.jpeg)

Подход «Arrange-Act-Assert» (ААА) — это не столько инструмент, сколько способ структурировать тесты. Он помогает сделать тесты более понятными и логичными. Суть проста:

1. **Arrange (Подготовка данных)**: вы настраиваете окружение, готовите нужные объекты, переменные и условия, чтобы тест можно было корректно выполнить.
    
2. **Act (Действие)**: вы вызываете тестируемый метод (или функцию) с подготовленными данными.
    
3. **Assert (Проверка результатов)**: вы проверяете (через Assertions) то, что метод вернул ожидаемый результат или повёл себя так, как вы предполагали.
    

Преимущества:

- Тест становится более читаемым: проще понять, что в нём происходит и где именно происходит сбой.
    
- Логическая структура: всё разбивается на блоки, и глаза «не путаются» в бессвязном наборе переменных и проверок.
    
- Проще поддерживать такой код.

## Mockito basic
**Mockito** — это фреймворк для создания mock-объектов в тестах. Mock-объекты симулируют работу реальных объектов, что позволяет упростить процесс тестирования.

Аннотация **@ExtendWith(MockitoExtension.class)** используется для включения расширения Mockito в JUnit 5. Используя аннотацию **@Mock**, мы создаём мок-объект репозитория UserRepository, который будем использовать для имитации поведения реального репозитория. Аннотация **@InjectMocks** используется для автоматической инжекции объектов, созданных с помощью аннотации **@Mock**, в экземпляр UserService, который затем будет сохранен в тест. Нам его создавать не нужно — всё сделает Mockito.

**ArgumentCaptor** — это класс Mockito, который используется для захвата аргументов, переданных в мок-объект. Он позволяет получить значения аргументов, которые были переданы в метод мок-объекта при его вызове. Это особенно полезно в случаях, когда метод возвращает void, и нет возможности проверить его возвращаемое значение. Таким образом, ArgumentCaptor помогает убедиться, что метод был вызван с корректными аргументами. Метод capture() — для захвата аргумента, метод getValue() — для получения.

**Mock объект** — подменяет реальную зависимость для проверки **взаимодействий** (какие методы были вызваны, с какими аргументами). Используется для верификации поведения.

**Spy объект** — обёртка над реальным объектом, которая **записывает вызовы**, но сохраняет оригинальную логику. Позволяет проверить взаимодействия, не подменяя работу объекта полностью.

Главное отличие: Mock часто создаёт пустой заглушку, а Spy работает с реальным объектом, лишь отслеживая его.

## Parameterized tests
Параметризированные тесты — это тесты, которые выполняются несколько раз с различными наборами входных данных. Это позволяет проверить функцию или метод на разных значениях параметров без написания отдельных тестов для каждого случая, повышая эффективность и покрытие тестированием.

## @SpringBootTest
`@SpringBootTest` — это аннотация из Spring Boot, используемая для интеграционного тестирования. При её применении поднимается полный контекст приложения, включая все бины и конфигурации, что позволяет тестировать взаимодействие различных компонентов в условиях, близких к реальной работе приложения. Это полезно для проверки целостности приложения, но может замедлить выполнение тестов из-за времени, необходимого для инициализации контекста.

## TestContainers
TestContainers — это библиотека для Java, которая предоставляет одноразовые экземпляры баз данных, веб-браузеров или любых других сервисов, запускаемых в Docker-контейнерах.

Используется для написания интеграционных и приемочных тестов, максимально приближенных к реальному окружению.

**Ключевые преимущества:**

- **Изоляция тестов:** Каждый тест работает с чистым экземпляром сервиса.
    
- **Простота:** Не требует ручной настройки тестового окружения.
    
- **Универсальность:** Работает с любым образом Docker (БД, message brokers, Selenium и т.д.).
    
- **Совместимость:** Легко интегрируется с JUnit.

## Как писать тестируемый код
1. **Зависимость от абстракций (DIP):** Код должен зависеть от интерфейсов, а не от конкретных классов. Это позволяет легко подменять реализации с помощью моков и стабов.
    
2. **Внедрение зависимостей (DI):** Все зависимости должны передаваться в класс извне (через конструктор или сеттеры), а не создаваться внутри. Это делает зависимости явными и заменяемыми.
    
3. **Разделение ответственности (SRP):** Класс должен решать только одну задачу. Чем он проще, тем легче его протестировать изолированно.
    
4. **Предпочитайте композицию наследованию:** Наследование часто усложняет тестирование из-за тесной связности.
    
5. **Минимум приватной логики:** Приватные методы сложно протестировать напрямую. Лучше выносить сложную логику в отдельные, публичные классы с интерфейсами, которые можно протестировать по отдельности. Если метод должен быть приватным, его тестируют через публичный контракт класса.
