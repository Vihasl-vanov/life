## Эволюция архитектур

- **Монолит:** Всё в одном. Просто на старте, но с ростом становится громоздким: сложно масштабировать, обновлять и поддерживать.
    
- **SOA (Сервис-ориентированная):** Разбиение на крупные сервисы, но с тяжелыми протоколами (SOAP) и общей шиной (ESB).
    
- **Микросервисы:** Эволюция SOA. Разбиение на **мелкие, слабо связанные** компоненты с легковесными протоколами (REST/JSON). Пик популярности — сер. 2010-х (Netflix, Amazon).
    

## Что это такое?

**Определение:** Подход, при котором приложение состоит из набора небольших, независимых сервисов. Каждый сервис решает одну бизнес-задачу, имеет свой код, свою БД и API.

**Ключевые принципы:**

- **Единичная ответственность:** Сервис делает только "одну вещь, но хорошо".
    
- **Автономность:** У каждого своя БД (Database per service), ресурсы. Изменение одного не ломает другие.
    
- **API First:** Четкие контракты взаимодействия (REST/gRPC).
    
- **Децентрализация:** Можно использовать разные технологии под разные задачи.
    
- **DevOps:** Требует автоматизации (CI/CD, контейнеры, оркестрация).
    

## Преимущества

- **Независимое масштабирование:** Масштабируется только нужный сервис, а не всё приложение.
    
- **Простота поддержки:** Код маленький, его легче понимать и тестировать.
    
- **Гибкость команд:** Команды работают параллельно и независимо ("двух-пиццевые команды").
    
- **Независимый деплой:** Можно выкатывать обновления одного сервиса без остановки всего продукта.
    
- **Отказоустойчивость:** Падение одного сервиса не роняет всю систему (частичная деградация).
    

## Недостатки и сложности

- **Сложность системы:** Управлять роем сервисов сложнее, чем одним монолитом.
    
- **Сетевые издержки:** Вызовы по сети медленнее вызовов в памяти, добавляются риски таймаутов.
    
- **Согласованность данных:** Нет общих транзакций (ACID). Приходится использовать сложные паттерны (Saga) и конечную согласованность.
    
- **DevOps-нагрузка:** Нужны сложный мониторинг, логирование, трейсинг (Jaeger, ELK) и CI/CD.
    
- **Миграция:** Разделить существующий монолит и его БД — долго и больно (паттерн "Strangler Fig").
    

## Когда использовать, а когда нет

- **Нужны микросервисы:** Огромные нагруженные системы (Amazon, Netflix), множество независимых команд, разнородные технологии.
    
- **НЕ нужны микросервисы:** Маленькие проекты, команда 1–3 человека, нет проблем с масштабированием. **Начинать лучше с монолита!**
    

## Проектирование (Основы)

- **DDD (Domain-Driven Design):** Режем систему по **бизнес-доменам** (Заказы, Платежи, Доставка). Каждый домен = один микросервис.
    
- **Database per Service:** У каждого сервиса **своя БД**, к которой другие не имеют прямого доступа (только через API).
    
- **High Cohesion, Low Coupling:** Внутри сервиса всё связано (высокая связность), между сервисами связей минимум (слабая связанность).
    
- **API Contract:** Стабильный и документированный API (OpenAPI).
    

## Пример: Интернет-магазин

- **Схема:** Клиент -> **API Gateway** (единая точка входа) -> Микросервисы (Account, Inventory, Cart, Payment, Shipping).
    
- **Суть:** У каждого сервиса своя БД и логика. Если упадет Payment, Cart все еще работает. Gateway маршрутизирует запросы.
