## Введение: что такое балансировка нагрузки

**Load balancer (LB)** равномерно распределяет входящие запросы между пулом доступных серверов, чтобы:

- не перегружать отдельные узлы (**перфоманс, resource utilization**),
    
- переживать отказ части парка (**availability**),
    
- прозрачно **масштабировать** сервис (добавили/убрали узлы - клиенты не заметили).
    

LB - обычно **первая точка входа** после периметра (FW/WAF). В трехзвенной схеме его ставят:

- между **клиентами и веб-слоем**,
    
- между **веб и приложением**,
    
- между **приложением и БД/кэшом** (реже, но возможно для read-реплик или шардов).
    

### Что еще умеет LB (поверх "раскидать RPS")

- **Health-checks** (active/passive) и connection draining (аккуратно выводит узлы из ротации).
    
- **TLS termination** (offload RSA/ECDSA/TLS1.3, session resumption, SNI).
    
- **HTTP-фичи L7**: маршрутизация по cookie/URL/заголовкам, header-rewriting, rate limiting, компрессия, кэширование статического.
    

- **Service discovery** (через registry/EDS), **outlier detection**, **slow-start**.
    

- **Security**: базовая L3/L4 DDoS-защита (SYN-cookies, conn-limits), интеграция с WAF.
    

- **Наблюдаемость**: метрики (qps, active conns, 5xx, p95/p99), трассировка, логи, предиктивная аналитика.
    

## Глобальная и локальная балансировка

### GSLB (Global Server Load Balancing)

Распределяет трафик м**ежду регионами/ЦОДами**: учитывает близость пользователя (латентность), здоровье регионов, вместимость, планы аварийного переключения (active-active/active-passive). Реализуется:

- **DNS-уровнем**: GeoDNS/latency-based/weighted RR. Плюсы - простота, минусы - **кэширование** (TTL), не видит "упавшие" IP до истечения TTL, перекосы из-за кешей крупных ISP.
    

- **Anycast** (BGP): один и тот же IP анонсируется из разных PoP/регионов - маршрутизаторы доставляют трафик к "ближайшему" анонсу. Плюсы: быстрый **failover** (withdraw BGP), естественная "тяготение к ближнему", хорошее поглощение DDoS на периферии; минусы: тонкими L7-правилами управлять сложнее, требуется аккуратно решать **симметрию трафика** и **сохранность сессий** (делайте сервис stateless либо храните сессии во внешнем сторе).
    

- **Cloud LBaaS/ADC**: глобальные балансировщики провайдеров (GCLB/ALB+GTM/Front Door) с health-сигналами от локальных слоев.
    

### Локальный LB (внутри региона/ЦОДа)

- **L4** (TCP/UDP): быстрый dataplane, баланс по 5-tuple/consistent hash, умеет NAT/DSR/TPROXY.
    

- **L7** (HTTP/HTTP2/gRPC): "понимает" приложение (URI, cookie, headers), умеет TLS offload, sticky-policy, маршрутизацию и rate limit.
    

На практике часто используется **несколько слоев** LB: глобальный (DNS/Anycast) → L4 (ECMP/LVS/NLB) → L7 (Envoy/HAProxy/Nginx) у границы сервиса.

## Алгоритмы распределения

**Статические** (не учитывают текущую загрузку):

- Round-robin,
    
- Weighted RR,
    
- IP-hash,
    
- URL-hash,
    
- **Consistent/Rendezvous hash** (минимальные перемещения ключей при изменении пула).
    

**Динамические** (учитывают состояние):

- Least Connections,
    
- Weighted Least Connections,
    
- Least Response Time,
    
- Power of Two Choices(рандомно 2 узла → выбрать лучший),
    
- EWMA latency.
    

Дополнительно: **slow-start (плавный прогрев новых узлов),** outlier detection(исключение "плохих").

**Когда какие**

- **Короткие запросы, однородные узлы** → RR/Power-of-Two.
    

- **Длительные коннекты/WebSocket** → Least Connections.
    

- **Разный класс узлов** → Weighted.
    

- **Нужна консистентность маршрута** (кэш, шард БД) → Consistent/Rendezvous hash.
    

- **Perf-чувствительные** → Least Response Time/EWMA.
    

## Stateful vs Stateless LB

- **Stateful**: LB хранит **таблицу сессий/привязок** (клиент → бэкенд) и шарит ее между узлами. Плюс - точная "липкость", минус - сложность масштабирования (репликация состояния).
    

- **Stateless**: решение по детерминированной функции (hash), локальное состояние - временное (conn-tracking). Плюс - легкая горизонталка, минус - иногда нужна дополнительная "память" (например, cookie insert) для устойчивой липкости.
    

Для **статического контента** (текст/картинки) чаще выбирают stateless L4/L7 + CDN: дешево, масштабируемо, отказоустойчиво. Sticky не нужен - бэкенды одинаковы.

## Типы LB по уровню OSI

- **L4**: баланс по TCP/UDP, минимальная задержка; сессии направляются на один бэкенд (коннект-пининг). Подходит для gRPC/DB-проксирования, игровых протоколов, стриминга.
    

- **L7**: решения на уровне приложения (HTTP(S)/gRPC): роутинг по пути/хеадерам/куки, TLS-offload, WAF/rate-limit. Медленнее, но умнее.
    

## Трехуровневая архитектура LB

- **Tier-0**: DNS/GSLB/Anycast (раскидывает по регионам/PoP).
    

- **Tier-1**: ECMP/роутеры - делят поток между Tier-2 (по IP-hash/ECMP).
    

- **Tier-2**: L4-LB - обеспечивает "стик" потока к конкретному Tier-3.
    

- **Tier-3**: L7-LB - HTTP-осознанная балансировка к пулам сервисов (health на уровне HTTP/gRPC, TLS, маршрутизация).
    

## Реализации

- **Hardware ADC**: высокая производительность, но дорого, vendor-lock, сложный change-management.
    

- **Software LB**: Envoy/HAProxy/Nginx/Traefik/LVS (IPVS/DSR). Дешево, программируемо, горизонталится.
    

- **Cloud LB (LBaaS)**: управляемые L4/L7/GSLB, оплата по использованию, нативные health-checks, A/B/Canary.
    

- **Client-side LB** (библиотеки/SD-агенты): когда сервисов много, клиенты сами выбирают инстанс из service registry (gRPC pick\_first/round\_robin, Envoy xDS, Ribbon/Resilience4j). Хорошо внутри Mesh.
    

## DDoS и безопасность

LB помогает фильтровать **L3/L4** атаки (SYN flood - SYN-cookies, conn-rate; UDP floods - limiting/filters), абьюз **L7** (HTTP floods - challenge, rate limiting, JA3/UA fingerprint). На периметре/edge лучше всего **Anycast + scrubbing**: трафик "впитывается" ближайшим PoP, не перегружая один ЦОД. Важны **анализ аномалий**, **per-IP/ASN rate**, т**окен-челленджи**, **блок-листы** и "пересадка" на дешевые вычисления.

## Метрики и НФТ для эксплуатации

- **Пропускная способность** (qps, Mbps, packets/s), **active connections**, **estab/sec**.
    

- **Время решения** LB-ветки (p50/p95/p99), **TLS handshake latency**, **resumption rate**.
    

- **Health**: доля healthy бэкендов, время флапов, outlier-ejections.
    

- **Ошибки**: 5xx на LB (connection reset, upstream timeout), retry-rate.
    

- **Согласованность конфигурации** и MTTR при смене пула.
    

- **Failover-цель**: изъятие "плохого" узла ≤ N секунд, без заметного роста 5xx.

## Практический пример (маршрутизация по приложению)

- Tier-1 отдает поток на один из Tier-2 по ECMP.
    

- Tier-2 фиксирует соединение к конкретному Tier-3 (consistent hash).
    

- Tier-3 завершает TLS, читает HTTP/2/gRPC метаданные и отправляет в нужный пул (URI `/slides` → Slides-сервера, `/docs` → Docs-сервера).
    

- Ответ может идти **симметрично назад через те же уровни** (обычно да), либо применяются оптимизации (DSR/кэш на edge).
    

## Вопрос "Anycast vs классический GSLB (DNS)"

**Anycast**: один IP анонсирован из многих PoP (BGP). Пользователь попадает в "ближайший" по маршрутизации PoP.

**Плюсы**: мгновенный failover (withdraw route), естественная близость, DDoS-поглощение на краю, простота для клиента (один VIP).

**Минусы**: тонкая политика маршрутизации сложнее; важно держать сервис **stateless** или вынести сессии наружу; нужны сетевые компетенции (BGP/health-пробы/blackhole).

**DNS-GSLB**: понятные политики, веса, geo-ответы, но TTL/кеши → задержки при отказах, перекосы по крупным кешам ISP.
