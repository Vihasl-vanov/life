
## Проблема

Каждый узел имеет **собственные часы** → дрейф → метки времени несопоставимы → нельзя упорядочить события по физическому времени.

---

## Синхронизация физических часов

### Алгоритм Кристиана

- Клиент запрашивает время у сервера-эталона
- Поправка: `T_new = T_server + RTT/2`
- ✅ Прост, 1 раунд, мало нагрузки
- ❌ Single point of failure, плохо масштабируется, нет отказоустойчивости

### Алгоритм Беркли

- **Внутренняя** синхронизация (без привязки к UTC)
- Координатор опрашивает все узлы → вычисляет среднее отклонение → рассылает **дельты** (не абсолютное время)
- ✅ Не нужен внешний эталон, можно переизбрать координатора
- ❌ Результат может отличаться от реального времени, масштабируемость ограничена частотой опросов

### NTP (Network Time Protocol)

- Иерархия страт: атомные/GPS часы → страта 1 → страта 2 → ... → клиенты
- Клиент опрашивает несколько серверов, фильтрует выбросы, плавно корректирует частоту часов
- Точность: ~10–50 мс в интернете, < 1 мс в LAN
- ✅ Стандарт де-факто, масштабируется до миллионов узлов, аутентификация
- ❌ Нужен хотя бы один эталон, асимметричные маршруты снижают точность

## Логические часы Лэмпорта

> **Идея:** не фиксировать реальное время, а отследить порядок «случилось раньше» (`→`)

### Правила

|Событие|Действие|
|---|---|
|Локальное событие|`C += 1`|
|Отправка сообщения|`C += 1`, вложить `C` в сообщение|
|Получение сообщения|`C = max(C_local, C_msg) + 1`|

### Свойство

`A → B` ⟹ `C(A) < C(B)`

**Обратное неверно:** `C(A) < C(B)` ≠ A причинно предшествует B

### ✅ Плюсы

- 1 число на процесс, 1 число в каждом сообщении
- Нет глобальных часов
- Достаточно для очередей, мьютексов, распределённых логов

### ❌ Минусы

- Не различает конкурентные (независимые) события
- Нельзя определить наличие причинной связи только по меткам

## Векторные часы

> **Идея:** вектор счётчиков `[C1, C2, ..., Cn]` — по одному на каждый процесс

### Правила

|Событие|Действие|
|---|---|
|Локальное событие|`V[i] += 1`|
|Отправка сообщения|`V[i] += 1`, вложить весь вектор|
|Получение сообщения|`V[k] = max(V[k], V_msg[k])` для всех k, затем `V[i] += 1`|

### Сравнение векторов

```
A → B  ⟺  V(A)[k] ≤ V(B)[k] для всех k  И  V(A) ≠ V(B)
A ∥ B  ⟺  ∃k: V(A)[k] > V(B)[k]  И  ∃j: V(A)[j] < V(B)[j]
```

`A ∥ B` — события **конкурентны** (независимы)

### ✅ Плюсы

- Точно отражает причинность
- Позволяет обнаружить конфликты при репликации (DynamoDB, NoSQL)
- Основа версионности данных и snapshot-консистентности

### ❌ Минусы

- Размер вектора = O(N) → накладно при большом кластере
- Динамическое добавление/удаление узлов усложняет управление
- Реализация сложнее, выше риск ошибки
