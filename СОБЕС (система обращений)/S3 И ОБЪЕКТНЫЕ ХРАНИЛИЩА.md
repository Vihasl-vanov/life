# S3 И ОБЪЕКТНЫЕ ХРАНИЛИЩА

> В требованиях: «опыт работы с SQL/noSQL базами данных, **S3 хранилищами**». В хранилище была одна строка: «Объектное хранилище — S3/MinIO c CDN».
> Для системы обращений это вложения: скриншоты, акты, сканы, логи. При 10 млн обращений в год — основной объём данных системы.

Связанные: [[DATABASE]], [[ВЕРТИКАЛЬНОЕ И ГОРИЗОНТАЛЬНОЕ МАСШТАБИРОВАНИЕ]], [[KUBERNETES]]

## Три типа хранения

| Тип | Единица | Доступ | Когда |
|---|---|---|---|
| **Block** | Блок диска | Как диск (EBS, LVM) | БД, файловые системы |
| **File** | Файл в дереве | NFS/SMB, POSIX | Общие папки, легаси |
| **Object** | Объект (данные + метаданные + ключ) | HTTP API | Медиа, документы, бэкапы, логи, вложения |

Объектное хранилище: **плоское пространство ключей**, никаких директорий (папки в консоли — иллюзия, это префиксы в ключе), объект **иммутабелен** (нельзя дописать в середину — только перезаписать целиком), горизонтально масштабируется практически безгранично, стоит дёшево.

Ограничения, о которых спрашивают: нет частичной записи, нет переименования (только copy+delete), листинг по префиксу дорогой на больших бакетах, нет транзакций между объектами.

## Модель S3

- **Bucket** — контейнер верхнего уровня, глобально уникальное имя, привязан к региону.
- **Key** — полный путь-идентификатор: `requests/2026/08/15/req-4821/attachment-1.pdf`.
- **Object** — тело + системные метаданные (Content-Type, размер, ETag) + пользовательские (`x-amz-meta-*`).
- **ETag** — обычно MD5 тела; для multipart — хэш хэшей с суффиксом `-N`, поэтому **не годится как контрольная сумма файла** при multipart.

### Проектирование ключа
```
requests/{yyyy}/{MM}/{dd}/{requestId}/{attachmentId}-{safeFileName}
```
- Дата в начале даёт естественное разделение и упрощает lifecycle-правила.
- `requestId` в ключе позволяет удалить все вложения обращения одним префиксом.
- Имя файла **санировать**: пользовательское имя хранить в метаданных/БД, в ключе — безопасный идентификатор. Иначе кириллица, пробелы и `../` в ключах.
- Историческая рекомендация про случайный префикс ради шардирования устарела (AWS давно масштабирует префиксы автоматически), но для MinIO/Ceph равномерность ключей всё ещё имеет значение.

## Операции, которые надо знать

**Multipart upload** — файл режется на части (5 МБ … 5 ГБ), части грузятся параллельно и независимо ретраятся, затем `CompleteMultipartUpload` собирает объект. Обязателен для файлов больше ~100 МБ, максимум объекта — 5 ТБ. Незавершённые multipart'ы **занимают место и не видны в листинге** — обязательное lifecycle-правило `AbortIncompleteMultipartUpload` через 7 дней, иначе бакет тихо растёт.

**Presigned URL** — временная подписанная ссылка. Ключевой паттерн для вложений:

```
Клиент → [POST /attachments] → Сервис (проверяет права, пишет запись в БД)
Клиент ← presigned PUT URL ←
Клиент → [PUT файл напрямую] → S3
Клиент → [POST /attachments/{id}/confirm] → Сервис (помечает загруженным)
```

Файл **не проходит через ваш JVM-сервис**: не занимает потоки, не ест память и трафик приложения. То же на скачивание — presigned GET. Это правильный ответ на «как загружать вложения в высоконагруженной системе».

Нюансы: срок жизни ссылки минимальный (5–15 мин), в ссылке фиксировать `Content-Type` и `Content-Length`, антивирусная проверка после загрузки — асинхронно по событию, до неё файл в статусе «на проверке».

**Versioning** — каждая перезапись создаёт версию, удаление ставит delete marker. Защита от случайного удаления, но платите за все версии — обязательно lifecycle на удаление старых.

**Lifecycle** — правила по возрасту/префиксу: перевести в холодный класс через 90 дней, удалить через 5 лет, оборвать незавершённые multipart'ы. Для банка со сроками хранения документов это не опция, а требование.

**Storage classes** — Standard / Infrequent Access / Glacier. Экономия в разы, но у холодных есть минимальный срок хранения и плата за извлечение.

**Object Lock / WORM** — запрет на изменение и удаление в течение retention-периода. Прямо ложится на регуляторные требования банка.

## Java: AWS SDK v2

```java
S3Client s3 = S3Client.builder()
    .endpointOverride(URI.create("https://s3.bank.internal"))   // MinIO / Ceph
    .region(Region.of("ru-central-1"))
    .credentialsProvider(...)
    .serviceConfiguration(S3Configuration.builder()
        .pathStyleAccessEnabled(true)    // важно для MinIO
        .build())
    .build();
```

```java
// Загрузка потоком, без чтения файла в память
s3.putObject(PutObjectRequest.builder()
        .bucket("attachments").key(key)
        .contentType("application/pdf")
        .metadata(Map.of("request-id", requestId))
        .build(),
    RequestBody.fromInputStream(in, size));

// Presigned URL
S3Presigner presigner = S3Presigner.create();
PresignedPutObjectRequest presigned = presigner.presignPutObject(
    PutObjectPresignRequest.builder()
        .signatureDuration(Duration.ofMinutes(10))
        .putObjectRequest(b -> b.bucket("attachments").key(key))
        .build());
```

**Грабли:**
- Никогда не читать файл в `byte[]` — на 100 МБ файле и 50 параллельных загрузках это OOM. Только стриминг, и `MultipartFile` в Spring тоже настраивать на диск (`spring.servlet.multipart.max-file-size`, `file-size-threshold`).
- `S3Client` **потокобезопасен и дорог в создании** — один бин на приложение, не создавать на запрос.
- Обязательно закрывать `ResponseInputStream`, иначе утечка соединений из пула.
- Таймауты (`apiCallTimeout`, `apiCallAttemptTimeout`) и ретраи задавать явно — дефолты щедрые.
- `S3TransferManager` (SDK v2, на CRT) — параллельный multipart из коробки.

## S3-совместимые реализации

**MinIO** — самое популярное self-hosted решение, полный S3 API, erasure coding, разворачивается в Kubernetes. **Ceph RGW** — часть Ceph, типичен в крупных корпоративных ЦОД. **Yandex Object Storage / VK Cloud** — облачные в РФ. Плюс внутренние банковские платформы.

## Главное архитектурное решение: файл в БД или в S3

| | BLOB в PostgreSQL | S3 |
|---|---|---|
| Транзакционность | Атомарно с бизнес-данными | Нет, нужен двухшаговый протокол |
| Размер БД | Растёт быстро, бэкап/восстановление деградируют | БД остаётся компактной |
| Стоимость | Дорогое БД-хранилище | Дёшево |
| Раздача | Через приложение | Напрямую по presigned URL / CDN |
| Масштабирование | Ограничено БД | Практически неограниченно |

**Стандартное решение:** метаданные (id, имя, размер, тип, автор, `requestId`, статус, ключ в S3) — в PostgreSQL, тело — в S3.

**Проблема согласованности** между БД и S3 — почти обязательный вопрос:
- Записали в S3, упали до коммита БД → **осиротевший объект**.
- Записали в БД, упали до загрузки в S3 → **битая ссылка**.

Решение — состояние в БД плюс уборка:
1. `INSERT` записи со статусом `PENDING`, генерируем ключ.
2. Клиент грузит по presigned URL.
3. `confirm` → проверяем наличие объекта (`headObject`) → статус `UPLOADED`.
4. Фоновая джоба: `PENDING` старше суток → удалить запись и объект, если он есть.
5. Удаление вложения: сначала `DELETED` в БД, физическое удаление объекта — асинхронно (или lifecycle-правилом).

Это тот же класс задач, что [[DISTRIBUTED SYSTEMS|Outbox]] — атомарности между двумя системами нет, есть согласованность в конечном счёте плюс компенсации.

## Вопросы с собеседования

**1. Почему не хранить вложения в БД?**
Раздувание БД бьёт по времени бэкапа и восстановления, по буферному кэшу, по репликации. При этом БД не даёт ничего взамен, кроме транзакционности, которую можно заменить статусной моделью. Отдача файла через приложение занимает поток на всё время передачи. S3 плюс presigned URL снимает и то, и другое.

**2. Как отдать пользователю файл на 500 МБ?**
Presigned GET со сроком в минуты, скачивание напрямую из хранилища мимо приложения. Приложение только проверяет права и выдаёт ссылку. Поддержка Range-запросов и докачки — со стороны S3 из коробки. Для публичного контента сверху CDN.

**3. Как гарантировать, что файл не подменили?**
Считать SHA-256 на загрузке и хранить в метаданных и в БД, сверять при скачивании критичных документов. ETag для этого не подходит при multipart. Для юридически значимых документов — Object Lock/WORM и версионирование.

**4. Что такое eventual consistency в S3?**
Исторически листинг и чтение после записи могли отдавать устаревшие данные. С декабря 2020 AWS S3 даёт строгую консистентность read-after-write для всех операций. Но **S3-совместимые реализации гарантируют это не всегда** — при работе с MinIO/Ceph нельзя закладываться на немедленную видимость в листинге, отсюда правило: истина о существовании файла живёт в вашей БД, а не в результате `listObjects`.

**5. Как ограничить доступ?**
IAM-политики и bucket policy по принципу минимальных прав, отдельные учётки на сервис, приватный бакет без публичного доступа, доступ только через presigned URL с коротким TTL, шифрование at rest (SSE-S3/SSE-KMS) и in transit (TLS), логирование доступа. Для банка ещё — сетевая изоляция и запрет выхода в интернет.

**6. Как посчитать объём под 10 млн обращений в год?**
Вслух: пусть 30% обращений имеют вложения, в среднем 2 файла по 1,5 МБ → 10 млн × 0,3 × 2 × 1,5 МБ ≈ 9 ТБ в год. С RF/erasure coding — умножить. Отсюда lifecycle: горячие 90 дней в Standard, дальше в холодный класс, удаление по регуляторному сроку. Такой расчёт «на салфетке» на собесе ценят больше, чем перечисление API.
