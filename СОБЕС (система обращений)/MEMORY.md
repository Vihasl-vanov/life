## циклические ссылки
**Ответ на тот вопрос про GC** — скорее всего спрашивали про циклические ссылки. Java GC работает через tracing от GC roots (локальные переменные стека, статические поля, JNI), а не через подсчёт ссылок. Поэтому два объекта, ссылающихся друг на друга, но недостижимые от GC roots — будут удалены. Именно так Java избегает проблемы, из-за которой страдает, например, Python.
## Общая структура памяти JVM (Heap vs Stack)
Какие основные области памяти вы знаете в JVM?
Ответ: Основные области — Heap (куча) и Metaspace, куда попадают классы. Память потоков — Stack (стек) и PC Register. Также есть Native Memory для служебных нужд JVM.

В чём ключевая разница между Heap и Stack? 
Ответ:

- **Heap:** Общая память для всех потоков. Туда попадают все объекты, созданные через `new`. Управляется сборщиком мусора (Garbage Collector).
    
- **Stack:** Память, индивидуальная для каждого потока. Туда попадают примитивные переменные и ссылки на объекты из кучи, а также вызовы методов (стэкфреймы). Управляется автоматически при входе/выходе из методов.

Что хранится в стеке потока (Stack)?
Ответ: Стек состоит из фреймов. В каждом фрейме хранятся: локальные переменные (примитивы и ссылки на объекты), параметры метода и информация о точке возврата (return address).

**Что хранится в куче (Heap)?**  
Ответ: В куче хранятся все объекты Java (экземпляры классов) и массивы. Туда же помещаются строки из пула строк (String Pool).

**Что такое Metaspace? Чем он отличается от PermGen?**  
Ответ: Metaspace — это область памяти для метаданных классов (структуры Class, байт-код, константы пула ). В отличие от PermGen, которая имела фиксированный размер и могла привести к `OutOfMemoryError: PermGen space`, Metaspace по умолчанию автоматически увеличивается (до предела native memory системы).

## Устройство кучи (Heap Structure) и сборка мусора

На какие области делится куча (Heap)?
Ответ: Куча делится на две главные области:

- **Young Generation (молодое поколение):** Куда помещаются новосозданные объекты. Делится на Eden и два Survivor-пространства (S0, S1).
    
- **Old Generation (старое поколение):** Куда перемещаются объекты, пережившие несколько сборок мусора в Young Generation.

**Опишите жизненный цикл объекта в куче.**  
Ответ:

1. Объект создается в **Eden**.
    
2. Когда Eden заполняется, запускается Minor GC. Выжившие объекты перемещаются в один из **Survivor**-пространств (S0 или S1), и их возраст (age counter) увеличивается.
    
3. При следующих Minor GC выжившие объекты из Eden и активного Survivor копируются в другой Survivor. Их возраст снова увеличивается.
    
4. Когда возраст объекта достигает порога (по умолчанию 15), он перемещается в **Old Generation**.
    
5. Когда Old Generation заполняется, запускается Major GC (часто более медленный).

**Что такое Garbage Collection (Сборка мусора)?**  
Ответ: Это автоматический процесс в JVM, который освобождает память в куче, удаляя объекты, которые больше не достижимы из стека (т.е. на них нет ссылок из работающей программы).

**По какому алгоритму JVM определяет, что объект можно удалить?**  
Ответ: Основной алгоритм — **достижимость (reachability)**. Объект считается "живым", если на него есть ссылка из стека (локальная переменная), из статического поля или из другого живого объекта. Все недостижимые объекты считаются мусором.

**Что такое Stop-The-World?**  
Ответ: Это ситуация, когда JVM полностью останавливает выполнение приложения для проведения некоторых операций сборщика мусора. Задача GC — минимизировать эти паузы.

## Сборщики мусора (Garbage Collectors) в JVM

### Serial GC
- **Режим работы:** Single-threaded, Stop-The-World (все потоки останавливаются).
- **Ниша:** Однопроцессорные системы, клиентские приложения с маленькой кучей (например, десктопные приложения на Swing).
- **Цель:** Эффективность в memory-footprint и для малых куч.
- **Алгоритм:** Mark-Sweep-Compact для Old Generation.

### Parallel GC (Throughput Collector)
- **Режим работы:** Multi-threaded, Stop-The-World (использует несколько потоков для ускорения сборки).
- **Ниша:** Многопоточные приложения, где ключевая цель — максимальная пропускная способность (throughput), а не низкая задержка (latency). Бэкенд-системы, пакетная обработка данных.
- **Цель:** Максимизировать общую производительность за счет более долгих, но параллельных пауз.
- **Алгоритм:** Многопоточный Mark-Sweep-Compact.

### G1 GC (Garbage-First)
- **Режим работы:** Multi-threaded, преимущественно concurrent и incremental.
- **Ниша:** Замена CMS; приложения, работающие на multi-core CPU с большой кучей (>4-6 ГБ), где важна предсказуемость пауз.
- **Уникальная черта:** Делит кучу на регионы (regions) и в фоне вычисляет, какие регионы содержат больше всего мусора ("garbage-first"), чтобы собрать их в первую очередь. Старается уложиться в заданное время паузы (`-XX:MaxGCPauseMillis`).
- **Цель:** Баланс между высокой пропускной способностью и низкими задержками.

### ZGC (The Z Garbage Collector)
- **Режим работы:** Concurrent, с ultra-low pause times.
- **Ниша:** Приложения, требующие чрезвычайно низких задержек (пауз < 10 мс) при работе с очень большими кучами (несколько ТБ). Например, high-frequency trading, real-time системы.
- **Уникальная черта:** Выполняет почти всю работу concurrently (указатели с метками — colored pointers, load barriers), что делает паузы STW крайне короткими и не зависящими от размера кучи.
- **Цель:** Предсказуемо низкие задержки (low latency) без компромисса на пропускной способности.

#### Сравнительная таблица
| GC           | Пропускная способность | Задержки (Latency) | Размер кучи  |            Паузы (STW)            |
| ------------ | :--------------------: | :----------------: | :----------: | :-------------------------------: |
| **Serial**   |         Низкая         |      Высокие       |    Малая     |     Длинные, single-threaded      |
| **Parallel** |      **Высокая**       |      Высокие       |   Средняя    |      Длинные, multi-threaded      |
| **G1**       |        Высокая         |       Низкие       |   Большая    | **Предсказуемые**, multi-threaded |
| **ZGC**      |        Высокая         |  **Очень низкие**  | **Огромная** |    **Крайне короткие** (<10ms)    |

## Исключения и ошибки памяти

**Какие исключения, связанные с памятью, вы знаете?**  
Ответ:

- `OutOfMemoryError`: Нехватка места в куче для создания нового объекта или в Metaspace для загрузки классов.
    
- `StackOverflowError`: Переполнение стека потока, обычно из-за бесконечной рекурсии.
    

**В какой области памяти возникает StackOverflowError?**  
Ответ: В стеке потока (Stack), когда исчерпан лимит на глубину вызовов методов (размер стека).

**В какой области памяти возникает OutOfMemoryError?**  
Ответ: Чаще всего в куче (Heap), когда нет места для нового объекта. Также может быть в Metaspace или когда JVM не может выделить native memory.

## Прочее

**Что такое classloader и его роль в памяти?**  
Ответ: Classloader загружает классы в Metaspace. Он отвечает за поиск байт-кода, его загрузку, связывание и инициализацию. Есть иерархия: Bootstrap, Platform/Extension, Application classloader.

Загрузчики классов в Java отвечают за загрузку классов в среду выполнения. Есть три вида загрузчиков: Bootstrap ClassLoader, Extension ClassLoader и System ClassLoader. Когда JVM запрашивает класс, загрузчик классов ищет и загружает его в среду выполнения. Загрузка происходит рекурсивно, начиная с System ClassLoader и передавая запросы к Extension и Bootstrap ClassLoader. Если класс не найден, генерируется исключение ClassNotFoundException

 **Что такое JIT-компилятор и как он влияет на память?**  
Ответ: JIT (Just-In-Time) компилирует "горячий" байт-код в нативный машинный код для ускорения выполнения. Сам нативный код хранится в отдельной области памяти (Code Cache), что потребляет дополнительную память.

**Что такое "утечка памяти" (memory leak) в Java?**  
Ответ: Это ситуация, когда объекты уже не нужны приложению, но остаются достижимыми (на них есть ссылка), и сборщик мусора не может их удалить. Классические примеры: статические коллекции, куда добавляются объекты, но никогда не удаляются, или незакрытые ресурсы (Connection, Stream).

 **Как можно избежать утечек памяти?**  
Ответ:
- Избегать бесконтрольного роста коллекций.
- Использовать слабые ссылки (WeakReference) для кэшей.
- Использовать try-with-resources для закрытия ресурсов.

**Что такое SoftReference, WeakReference, PhantomReference?**  
Ответ: Это виды ссылок разной силы, которые позволяют объектам быть удаленными сборщиком мусора при определенных условиях, даже если на них есть такая ссылка.

- **WeakReference:** Объект будет удален при следующем запуске GC.
- **SoftReference:** Объект будет удален, если JVM не хватает памяти.
- **PhantomReference:** Используется для более точного контроля над финализацией, объект уже финализирован, но еще не удален из памяти.
- Расскажите, в чем разница между WeakReference и SoftReference?

📝Ответ: WeakReference и SoftReference - это два типа ссылок, предоставляемых Java для управления объектами в памяти. Они используются в контексте сборки мусора для указания на то, как долго объект должен оставаться в памяти при отсутствии сильных ссылок на него.

WeakReference создает слабую ссылку на объект. Если на объект есть только слабые ссылки, сборщик мусора может удалить этот объект при следующем проходе сборки мусора. Объект, на который указывает WeakReference, будет удален сразу, как только не останется сильных ссылок на него.

SoftReference также создает слабую ссылку на объект, но сборщик мусора старается сохранить объект в памяти как можно дольше, чем в случае WeakReference. Объект, на который указывает SoftReference, будет удален только в том случае, если JVM испытывает дефицит памяти и необходимо освободить ресурсы. SoftReference часто используется в кэшировании, где объекты могут быть удалены при необходимости, но оставляются в памяти до тех пор, пока это возможно.

И WeakReference, и SoftReference могут использоваться совместно с классом ReferenceQueue, чтобы получить уведомление о том, когда объект, на который указывает ссылка, был удален сборщиком мусора. И WeakReference, и SoftReference находятся в пакете java.lang.ref.

**Что такое finalize() и почему его использование опасно?**  
Ответ: `finalize()` — это метод, который GC может вызвать перед удалением объекта. Опасно, потому что: 1) вызов не гарантирован; 2) может серьезно замедлить сборку мусора; 3) выброшенное в нем исключение проигнорируется. Использовать не рекомендуется, лучше использовать `Cleaner` или `PhantomReference`. Устарел.

**Что такое card table?**  
Ответ: Это механизм оптимизации для минирования долгих пауз при Minor GC. При изменении ссылки на объект в Old Generation, которая указывает на объект в Young Generation, JVM помечает соответствующую "карточку" как "грязную". Это позволяет быстро найти такие ссылки во время Minor GC, не проходя всю Old Generation.

**Что такое TLAB (Thread-Local Allocation Buffer)?**  
Ответ: Это небольшой участок памяти в Eden, выделенный для конкретного потока. Поток может очень быстро (allocate) новые объекты в своем TLAB без необходимости синхронизации с другими потоками. Это значительно ускоряет выделение памяти в многопоточных приложениях.

 **Как вы можете настроить размеры памяти JVM?**  
Ответ: С помощью ключей (options) командной строки:

- `-Xms` — начальный размер кучи (например, `-Xms512m`).
- `-Xmx` — максимальный размер кучи (например, `-Xmx2g`).
- `-Xss` — размер стека потока (например, `-Xss1m`).
- `-XX:MaxMetaspaceSize` — максимальный размер Metaspace.

## Что такое Run-Time Data Areas? 

📝Ответ: Run-Time Data Areas - это области данных среды выполнения JVM.

JVM определяет необходимые области данных во время выполнения программы. Некоторые создаются при запуске JVM, другие - локальные для потоков и создаются при создании потока, уничтожаясь при его завершении.

Области данных включают:

PC Register - регистр ПК, локальный для каждого потока, содержит адрес текущей инструкции JVM.

JVM Stack - хранит локальные переменные и временные результаты для каждого потока, уничтожается при завершении потока.

Native Method Stack - область для выполнения собственных методов, аналогична стеку JVM.

Heap - общее хранилище для объектов, метаданных классов и массивов, создается и уничтожается при запуске и завершении JVM.

Method Area - общая для всех потоков область, содержащая структуры для каждого класса, такие как пул констант и код методов.

## Расскажите о Heap и Stack память в Java. В чем разница между ними? Где хранятся примитивы?

📝Ответ:

Heap (Куча): Объекты, создаваемые во время выполнения программы, хранятся в куче. Память в куче выделяется и освобождается динамически в процессе выполнения программы. Куча является общедоступной областью памяти, доступной для всех потоков в программе. Объекты в куче существуют, пока на них есть хотя бы одна ссылка из других частей программы. Когда объект больше не используется, и на него нет ссылок, он подлежит сборке мусора.

Stack (Стек): Стек используется для хранения локальных переменных и вызовов методов. Каждый поток выполнения программы имеет свой собственный стек. Размер стека фиксирован и определяется при запуске программы. Обычно, стеки имеют ограниченный размер. Переменные в стеке существуют только во время выполнения метода, в котором они были созданы. Когда метод завершает свое выполнение, переменные стека освобождаются.

Примитивные типы данных: Примитивные типы данных (int, float, char и т. д.) хранят свои значения напрямую в стеке, если они являются локальными переменными метода. Если примитивные типы данных встроены в объекты (например, Integer, Double), они будут храниться в куче, так как объекты всегда хранятся в куче.

## Какие принципы работы и области памяти Garbage Collector?

📝Ответ:

Garbage Collector (сборщик мусора) в Java отвечает за автоматическое управление памятью, освобождая память, занятую объектами, которые больше не используются. Работа сборщика мусора базируется на нескольких принципах:

Ссылочные отношения(Reference counting): Сборщик мусора определяет "живые" объекты посредством анализа ссылочных отношений между объектами. Объект считается "живым", если на него есть хотя бы одна активная ссылка из другого объекта или из переменной в стеке выполнения.

Маркировка и освобождение(Tracing): На этапе маркировки все достижимые объекты помечаются как "живые". Затем, на этапе освобождения, освобождаются память и помечаются объекты, которые больше не являются "живыми".

Поколения: Многие реализации сборщиков мусора в Java основаны на концепции поколений, где объекты делятся на несколько "поколений" в зависимости от их времени жизни. Молодые объекты помещаются в "новое поколение", а те, которые переживают один или несколько сборок мусора, переносятся в старшие поколения.

Сборка по требованию: Сборщик мусора работает по требованию, и его вызов происходит, когда система определяет, что необходимо провести сборку. Это может произойти, например, когда куча заполняется определенным процентом.

Области памяти, используемые сборщиком мусора, включают:

Young Generation (Молодое поколение): В этой области создаются новые объекты. Сборщик мусора часто проводит частые, но небольшие сборки в этой области.

Old Generation (Старшее поколение): Здесь переносятся объекты, которые пережили несколько сборок мусора в молодом поколении. Сборщик мусора проводит сборки меньше, но они более трудоемки.

Permanent Generation (Постоянное поколение): В этой области хранятся метаданные классов, строки постоянного пула и другие данные, которые не подлежат сборке в том виде, в котором обычно происходит сборка объектов.
