# BPMN И CAMUNDA

> В задачах вакансии прямым текстом: «разработка … BPMN-процессов». В хранилище темы не было вообще. Для системы управления обращениями это ядро продукта — маршрут обращения (создано → классифицировано → назначено → согласовано → исполнено → закрыто) описывается именно процессом.

Связанные: [[SPRING]], [[DATABASE]], [[KAFKA]], [[МИКРОСЕРВИСНАЯ АРХИТЕКТУРА]]

---

## Зачем вообще process engine

Альтернатива — маршрут обращения зашит в `if/else` и поле `status` в таблице. Работает, пока переходов десяток. Дальше:
- аналитик не может посмотреть схему, не читая код;
- изменение SLA/маршрута = релиз;
- нет истории «почему тикет две недели висел на этом шаге»;
- таймеры, эскалации и параллельные согласования пишутся руками и текут.

Process engine даёт: **исполняемую диаграмму как единственный источник правды**, персистентное состояние процесса, таймеры, историю, инциденты, версионирование.

Расплата: ещё одна инфраструктурная зависимость, свои таблицы в БД, специфичная отладка, и соблазн затащить в схему бизнес-логику, которой там не место.

## BPMN 2.0 — элементы, которые реально спрашивают

### События (Events)
| Тип | Использование |
|---|---|
| **Start / End** | Начало и конец. Start может быть message/timer/signal |
| **Timer** | Boundary timer на задаче = эскалация по SLA. Intermediate = «подождать 3 дня» |
| **Message** | Ждём внешнее событие: ответ смежной системы, действие пользователя. `correlationKey` связывает сообщение с конкретным экземпляром |
| **Signal** | Broadcast — получают все подписанные экземпляры |
| **Error** | Boundary error event ловит бизнес-ошибку (`BpmnError`) и уводит на альтернативную ветку |
| **Escalation** | Как error, но процесс продолжается по основной ветке |
| **Conditional** | Срабатывает при изменении переменной |

**Прерывающее (interrupting) vs непрерывающее (non-interrupting)**: сплошная граница отменяет задачу, пунктирная — запускает параллельную ветку и оставляет задачу жить. Классика: непрерывающий таймер «через 2 дня напомнить исполнителю», прерывающий «через 5 дней снять и эскалировать руководителю».

### Шлюзы (Gateways)
| Шлюз | Смысл |
|---|---|
| **Exclusive (XOR)** | Ровно одна ветка по условию. Обязательно default flow, иначе при невыполнении всех условий — инцидент |
| **Parallel (AND)** | Все ветки одновременно, join ждёт все |
| **Inclusive (OR)** | Все ветки, чьи условия истинны. Join ждёт только реально запущенные. Дорогой в вычислении |
| **Event-based** | Ждём, что произойдёт раньше: пришло сообщение или сработал таймер |

**Ловушка:** AND-split без AND-join оставляет «висящие» токены и процесс не завершается. Симметричность split/join — базовая проверка на код-ревью диаграммы.

### Задачи (Tasks)
- **Service Task** — вызов кода. Основная рабочая лошадка.
- **User Task** — задача человеку, попадает в Task List. Для обращений — работа исполнителя/согласующего.
- **Script Task** — скрипт прямо в диаграмме. Использовать минимально: не тестируется, не ревьюится нормально.
- **Send / Receive Task** — отправка и ожидание сообщения.
- **Business Rule Task** — вызов DMN-таблицы.
- **Call Activity** — вызов другого процесса как подпроцесса. Способ переиспользования.

### Подпроцессы
- **Embedded** — в той же диаграмме, свой scope переменных.
- **Event subprocess** — реагирует на событие внутри родителя (например, «клиент отозвал обращение» отменяет всё).
- **Transaction subprocess + compensation** — откат уже выполненных шагов через compensation handlers. Это BPMN-реализация **Saga**, см. [[DISTRIBUTED SYSTEMS]].

### Multi-instance
Задача выполняется N раз по коллекции: последовательно или параллельно.
- `completionCondition` — досрочный выход. Пример: согласование пятью руководителями с условием «достаточно трёх одобрений».
- Переменные: `nrOfInstances`, `nrOfCompletedInstances`, `loopCounter`.

## Camunda 7 vs Camunda 8

Разница принципиальная, спросят почти наверняка.

| | **Camunda 7** | **Camunda 8 (Zeebe)** |
|---|---|---|
| Движок | Java-библиотека, встраивается в Spring Boot | Отдельный распределённый кластер, gRPC-клиент |
| Состояние | В реляционной БД (`ACT_*` таблицы) | Собственный лог поверх Raft + экспорт в Elasticsearch |
| Транзакции | **Общая транзакция с бизнес-БД** | Транзакции нет, только external tasks (jobs) |
| Масштаб | Ограничен БД | Горизонтальный, партиционирование |
| Лицензия | Community была Apache 2.0, EOL апрель 2025 | Коммерческая (SaaS/Self-Managed) |

**Ключевое следствие для разработчика:** в Camunda 7 embedded-движок пишет своё состояние в ту же БД и ту же транзакцию, что и бизнес-данные — если Service Task упал, откатывается всё вместе. В Camunda 8 такой атомарности нет, нужны идемпотентность и компенсации.

В российских банках чаще всего **Camunda 7 embedded** в Spring Boot либо форк/отечественный аналог. Уточнить на собесе — хороший встречный вопрос.

## Как движок исполняет процесс: транзакции и wait states

Это **самый глубокий вопрос** по теме, отличает «рисовал схемы» от «работал с движком».

Движок выполняет процесс не целиком, а **отрезками между точками сохранения**. Отрезок = одна транзакция БД. Точки сохранения:
1. **Wait state** — User Task, Receive Task, Timer, Message event. Токен останавливается, состояние в БД, транзакция коммитится.
2. **`asyncBefore` / `asyncAfter`** — явно поставленная граница. Движок сохраняет состояние и ставит **job** в таблицу `ACT_RU_JOB`, который подхватит Job Executor.

```xml
<serviceTask id="callExternalSystem"
             camunda:asyncBefore="true"
             camunda:class="ru.bank.RequestDelegate"/>
```

**Почему это важно.** Без `asyncBefore` цепочка из пяти Service Task выполняется в одной транзакции. Пятая упала → откатились все пять, включая уже отправленный REST-запрос в смежную систему (его-то не откатишь). С `asyncBefore` каждая — своя транзакция и свой ретрай.

**Правило:** ставить `asyncBefore` перед любым шагом с внешним побочным эффектом, после параллельных шлюзов (иначе «параллельные» ветки исполняются последовательно в одном потоке) и в начале процесса, если старт вызывается из REST-контроллера и не должен блокировать ответ.

### Job Executor
Пул потоков, который выбирает jobs из БД и исполняет.
- **Retries** — по умолчанию 3. Каждая неудача уменьшает счётчик.
- **Retries = 0 → инцидент** (`ACT_RU_INCIDENT`). Процесс замирает, требуется вмешательство.
- Стратегия ретраев задаётся: `R5/PT10M` — 5 попыток с интервалом 10 минут.
- В кластере несколько нод конкурируют за jobs; блокировка через `LOCK_EXP_TIME_` и `LOCK_OWNER_`.

**Инциденты** — прямая связь с пунктом вакансии «помощь при разборе промышленных инцидентов». Уметь сказать: смотрим Cockpit/таблицу инцидентов, читаем stacktrace, чиним причину, делаем retry job или модифицируем экземпляр процесса.

### BpmnError vs обычное исключение
```java
throw new BpmnError("CLIENT_NOT_FOUND", "Клиент не найден в МДМ");  // бизнес-ветка
throw new RuntimeException("Connection refused");                    // технический сбой → retry → инцидент
```
Бизнес-ошибка ловится Boundary Error Event и ведёт по альтернативной ветке. Техническая — ретраится движком. Путать эти две вещи — типичная ошибка: технический таймаут, брошенный как `BpmnError`, уведёт процесс в ветку «клиент не найден».

## External Task Pattern

Вместо того чтобы движок сам вызывал ваш код, воркер **опрашивает** движок: «дай мне задачи топика `send-notification`».

```
Engine ──[fetchAndLock]──> Worker ──[complete / handleFailure / handleBpmnError]──> Engine
```

Преимущества: воркер на любом языке, независимое масштабирование, движок не держит потоки на медленных операциях, естественная развязка. В Camunda 8 это единственная модель.

`fetchAndLock` с `lockDuration` — если воркер умер, блокировка истечёт и задачу заберёт другой. Отсюда требование: **воркер должен быть идемпотентным**, потому что задача может выполниться повторно.

## DMN — таблицы решений

Отдельный стандарт рядом с BPMN. Таблица «если категория=IT и приоритет=высокий → группа=IT-Support, SLA=4ч».

- **Hit policy**: `UNIQUE` (пересечений быть не должно), `FIRST` (первое совпадение), `COLLECT` (все, с агрегацией SUM/MIN/MAX/COUNT), `PRIORITY`, `ANY`.
- Ценность: правила маршрутизации меняет аналитик, деплой таблицы отдельно от кода.
- Вызывается из Business Rule Task или напрямую через `DecisionService`.

Для системы обращений DMN — очевидный кандидат на матрицу маршрутизации и расчёт SLA. Хороший ответ на «как бы вы спроектировали».

## Версионирование и миграция

- Деплой новой версии диаграммы → новый `version`, старые экземпляры **продолжают идти по старой версии**. Это правильное поведение по умолчанию.
- Долгоживущие процессы (обращение может висеть месяцами) → в БД одновременно живут экземпляры пяти версий.
- **Process Instance Migration** — явный перенос экземпляров на новую версию с маппингом activity. Обязательно при удалении шага, на котором кто-то стоит.
- `versionTag` для человекочитаемой маркировки.
- **Правило совместимости:** не удалять и не переименовывать activity id, пока на них могут стоять живые экземпляры.

## Схема данных

`ACT_RU_*` — runtime (текущие экземпляры, задачи, переменные, jobs). `ACT_HI_*` — история. `ACT_RE_*` — репозиторий (деплойменты, диаграммы). `ACT_GE_*` — общие.

**Главная эксплуатационная проблема: рост истории.** 10 млн обращений в год × десятки шагов × переменные = сотни миллионов строк в `ACT_HI_*`.
- **History Level**: `NONE` / `ACTIVITY` / `AUDIT` (дефолт) / `FULL`. `FULL` пишет ещё и все изменения переменных — на таком объёме неподъёмно.
- **History TTL** обязателен на каждом процессе + включённый **History Cleanup** job по расписанию в окно низкой нагрузки.
- Партиционирование исторических таблиц по дате.
- Переменные процесса — только идентификаторы и минимум скаляров. Класть в переменную сериализованный объект с телом обращения — прямой путь к раздутым `ACT_RU_VARIABLE`/`ACT_GE_BYTEARRAY` и тормозам.

Это отличный ответ на «где узкие места» применительно к 10 млн обращений — см. [[HIGHLOAD]].

## Camunda 7 + Spring Boot

```java
@Component("assignRequestDelegate")
public class AssignRequestDelegate implements JavaDelegate {
    @Override
    public void execute(DelegateExecution execution) {
        Long requestId = (Long) execution.getVariable("requestId");
        String group = routingService.resolveGroup(requestId);
        execution.setVariable("assigneeGroup", group);
    }
}
```
```xml
<serviceTask id="assign" camunda:delegateExpression="${assignRequestDelegate}"
             camunda:asyncBefore="true"/>
```

- `delegateExpression` (бин из контекста) предпочтительнее `class` (движок создаёт инстанс сам, без DI).
- Старт процесса: `runtimeService.startProcessInstanceByKey("request", businessKey, vars)`. **`businessKey` = номер обращения** — по нему потом ищут процесс.
- Корреляция: `runtimeService.createMessageCorrelation("ApprovalReceived").processInstanceBusinessKey(num).correlateWithResult()`.
- Тестирование: `camunda-bpm-assert` + `@Deployment`, in-memory H2, `ProcessEngineRule`. Юнит-тест на маршрут — обязателен, диаграмма это тоже код.

```java
assertThat(processInstance).isWaitingAt("userTaskApprove");
complete(task(), withVariables("approved", true));
assertThat(processInstance).hasPassed("serviceTaskNotify").isEnded();
```

## Вопросы с собеседования

**1. Зачем `asyncBefore` и что будет без него?**
См. раздел про транзакции. Без него отрезок процесса выполняется одной транзакцией; сбой в конце откатывает всё, а внешние побочные эффекты не откатываются. Плюс без async после параллельного шлюза ветки идут последовательно в одном потоке.

**2. Чем отличается BpmnError от RuntimeException?**
Первая — моделируемая бизнес-ситуация, ловится Boundary Error Event, ретраев нет. Вторая — технический сбой, движок ретраит, при исчерпании создаёт инцидент.

**3. Как реализовать SLA и эскалацию?**
Boundary timer event на User Task. Непрерывающий на 80% SLA — напоминание, прерывающий на 100% — переназначение на руководителя и пометка нарушения. Длительность — выражением из переменной (`${slaDuration}`), посчитанной DMN-таблицей, а не константой в диаграмме.

**4. Процессов миллионы, как не утонуть?**
History level понизить до `ACTIVITY`/`AUDIT`, TTL + cleanup, переменные держать тощими, тяжёлые данные — в своих таблицах и в S3, в процессе только ссылки. Разделить runtime и history-БД. Не моделировать высокочастотные технические шаги как отдельные activity.

**5. Как деплоить изменённую схему, когда живы старые экземпляры?**
Новая версия для новых экземпляров, старые идут по своей. При необходимости — миграция с маппингом activity, предварительно проверенная на тестовом слепке. Не удалять activity id, на которых стоят токены.

**6. Где заканчивается зона ответственности BPMN?**
В диаграмме — маршрут, точки ожидания, SLA, ветвление верхнего уровня. В коде — бизнес-логика, валидации, вызовы. Диаграмма с сорока шлюзами и скриптами внутри — антипаттерн: она нечитаема ни аналитиком, ни разработчиком и теряет весь смысл затеи.

**7. Как связать BPMN с Kafka?**
Входящее событие из Kafka → корреляция message event по businessKey. Исходящее — Service Task публикует через Outbox (см. [[KAFKA]]). Прямая публикация из делегата без outbox расходится с транзакцией движка.

## Что сказать, если опыта с Camunda нет

Честно и по делу: «Прямого коммерческого опыта с Camunda нет, тему изучал. Понимаю модель исполнения: токены, wait states, границы транзакций через asyncBefore, job executor и инциденты, разницу embedded-движка Camunda 7 и Zeebe. В текущей системе маршрут обращения реализован через [свою машину состояний / статусы], вижу ограничения такого подхода — изменения маршрута через релиз и отсутствие внятной истории переходов». Такой ответ сильнее, чем натянутый рассказ про несуществующий проект, и его невозможно провалить на уточняющем вопросе.
