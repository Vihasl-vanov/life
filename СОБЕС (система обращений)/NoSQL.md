# NoSQL

> В требованиях: «опыт работы с SQL/**noSQL** базами данных». [[DATABASE]] закрывает реляционную часть полностью, NoSQL встречался только внутри [[CAP]] и [[PACELC_модель]] как пример.

Связанные: [[DATABASE]], [[CAP]], [[МОДЕЛИ СОГЛАСОВАННОСТИ ДАННЫХ]], [[ВЕРТИКАЛЬНОЕ И ГОРИЗОНТАЛЬНОЕ МАСШТАБИРОВАНИЕ]]

## Классификация

| Тип | Модель | Представители | Сильная сторона |
|---|---|---|---|
| **Key-Value** | ключ → значение | Redis, etcd, Aerospike | Скорость, кэш, сессии, счётчики |
| **Document** | JSON-документ | MongoDB, Couchbase | Гибкая схема, вложенные структуры |
| **Wide-column** | строка → семейства колонок | Cassandra, HBase, ScyllaDB | Огромные объёмы записи, time-series |
| **Search** | инвертированный индекс | Elasticsearch, OpenSearch | Полнотекстовый поиск, аналитика по логам |
| **Graph** | вершины и рёбра | Neo4j, JanusGraph | Связи, обход графа |
| **Time-series** | метрики по времени | Prometheus, ClickHouse*, InfluxDB | Метрики, агрегаты по окнам |

\* ClickHouse формально колоночная аналитическая СУБД с SQL, но в разговоре о «не-OLTP» хранилищах упоминается в том же ряду.

**Главный тезис:** NoSQL — не «база без SQL», а **отказ от части гарантий и универсальности ради конкретного профиля нагрузки**. Универсального выигрыша нет, есть размен.

## Redis

Самое вероятное «noSQL» в вакансии такого профиля.

### Структуры данных
| Тип | Применение в системе обращений |
|---|---|
| String | Кэш DTO, счётчики (`INCR`), флаги |
| Hash | Объект по полям, частичное обновление |
| List | Простая очередь (`LPUSH`/`BRPOP`) |
| Set | Уникальные множества, теги |
| Sorted Set | Рейтинги, отложенные задачи по timestamp, скользящее окно rate limiter |
| Bitmap / HyperLogLog | Уникальные посетители за день с копеечной памятью |
| Stream | Лог событий с consumer groups — облегчённая Kafka |

### Что спрашивают
**Однопоточность.** Команды исполняются одним потоком в цикле событий — отсюда атомарность каждой команды без блокировок и предсказуемая латентность. Побочный эффект: **одна тяжёлая команда блокирует весь инстанс**. `KEYS *` на проде — классическая ошибка, вместо неё `SCAN` с курсором. Тяжёлые `HGETALL` по огромным хэшам и `SORT` — туда же. В Redis 6+ многопоточным сделан только сетевой I/O, исполнение по-прежнему однопоточное.

**Персистентность.** `RDB` — периодический снапшот, быстрый рестарт, потеря последних минут. `AOF` — журнал команд, `appendfsync everysec` как компромисс. Оба вместе — обычная конфигурация. Важно: **Redis не является надёжным хранилищем истины**, это ускоритель.

**Eviction.** `maxmemory` + политика: `allkeys-lru`, `volatile-ttl`, `noeviction` (ошибки на запись при заполнении). Для кэша — `allkeys-lru`; для очередей и сессий `noeviction` с мониторингом.

**Кластеризация.** Sentinel — HA с автоматическим failover одного мастера. Cluster — шардирование по 16384 хэш-слотам, транзакции и мультиключевые операции только внутри одного слота (`{hash tag}` в ключе, чтобы связанные ключи легли в один слот).

**Транзакции.** `MULTI/EXEC` — просто пакетное выполнение, **отката нет**: ошибка в середине не откатывает предыдущие команды. Настоящая атомарность сложной логики — Lua-скрипт (`EVAL`), он выполняется целиком без вклинивания.

**Распределённая блокировка.** `SET key value NX PX 30000` + удаление по проверке владельца через Lua. Redlock на нескольких мастерах спорен (критика Клеппмана: без fencing token корректность не гарантируется при паузах GC и рассинхроне часов). Честный ответ: для взаимного исключения «на удачу» годится, для корректности критичных операций нужен fencing token или блокировка в БД.

### Паттерны кэширования
- **Cache-aside (lazy loading)** — читаем кэш, промах → БД → положили в кэш. Основной паттерн.
- **Write-through** — пишем сразу в кэш и БД. **Write-behind** — в кэш, в БД асинхронно (риск потери).
- **Инвалидация:** по TTL, явная на изменении, версионирование ключа. «Две сложные вещи в информатике» — именно про это.
- **Cache stampede** — TTL истёк, тысяча запросов одновременно пошли в БД. Лечение: probabilistic early expiration, блокировка на перестроение, `Cache.get` с single-flight.
- **Cache penetration** — запросы по несуществующим ключам минуют кэш всегда. Лечение: кэшировать «пусто» с коротким TTL, Bloom filter.

Spring: `@Cacheable`/`@CacheEvict` + `RedisCacheManager`. Помнить, что аннотации работают через прокси — вызов метода изнутри того же бина кэш не задействует (та же природа, что у `@Transactional`, см. [[SPRING]]).

## MongoDB

**Модель.** База → коллекция → документ (BSON, до 16 МБ). Схемы нет, но есть валидация схемы на уровне коллекции — в продакшене её включают.

**Проектирование — главное отличие от реляционного:**
- **Embedding** (вложение) против **referencing** (ссылка). Правило: вкладывать то, что читается вместе и растёт ограниченно; ссылаться на то, что большое, растёт неограниченно или используется независимо.
- Комментарии к обращению вкладывать нельзя — их могут быть тысячи, документ упрётся в 16 МБ (**unbounded array** — классический антипаттерн).
- Данные проектируются **под запросы**, а не под нормализацию. Дублирование — норма.

**Индексы.** Single, compound (важен порядок полей — правило ESR: Equality, Sort, Range), multikey (по массивам), text, TTL (авто-удаление по времени — удобно для сессий и логов), partial. `explain("executionStats")` — смотреть `COLLSCAN` против `IXSCAN`.

**Aggregation pipeline** — `$match` → `$group` → `$sort` → `$project` → `$lookup`. `$match` ставить первым, чтобы отработал индекс. `$lookup` — аналог left join, но дорогой; его наличие в пайплайне часто признак того, что модель спроектирована реляционно.

**Репликация.** Replica set: primary + secondaries, автоматические выборы, oplog. `writeConcern` (`w:1`, `w:majority`, `j:true`) и `readConcern`/`readPreference` — ровно тот размен из [[PACELC_модель]]: `w:majority` надёжнее и медленнее, чтение с secondary быстрее и может быть устаревшим.

**Шардирование.** Ключ шардирования выбирается один раз и определяет всё. Монотонно растущий ключ (timestamp, ObjectId) → все записи в один шард (hot shard). Хэшированный ключ распределяет равномерно, но убивает range-запросы.

**Транзакции.** Многодокументные ACID-транзакции есть с версии 4.0 (replica set) и 4.2 (sharded). Но они дороги и это признак того, что модель, возможно, стоило спроектировать иначе — в Mongo атомарность на уровне одного документа бесплатна.

## Elasticsearch

Прямо релевантен вакансии: поиск по 10 млн обращений — реляционный `LIKE '%текст%'` этого не выдержит.

- **Инвертированный индекс**: терм → список документов. Анализатор разбивает текст на токены, приводит к нормальной форме (для русского — стемминг/лемматизация, `russian` analyzer).
- **Индекс → шарды → реплики.** Число primary-шардов фиксируется при создании.
- **Near real-time**: документ виден после refresh (по умолчанию 1 с), не мгновенно.
- **Релевантность** BM25, `должно/обязано/не должно` через bool query, boosting полей.
- **Агрегации** — фасеты и аналитика (сколько обращений по категориям за месяц).
- **Не источник истины.** Истина в PostgreSQL, в Elasticsearch — проекция, наполняемая событиями из Kafka или CDC. Индекс должен переживать полную перестройку из источника.
- Псевдоним (alias) + переиндексация в новый индекс + переключение alias — стандартный способ менять маппинг без даунтайма.

## Когда что выбирать

| Задача в системе обращений | Хранилище | Почему |
|---|---|---|
| Обращения, пользователи, справочники, аудит | PostgreSQL | Транзакции, связи, отчётность |
| Кэш справочников и профилей, сессии, rate limiting | Redis | Латентность в микросекундах |
| Полнотекстовый поиск по обращениям и переписке | Elasticsearch | Инвертированный индекс, релевантность |
| Вложения | S3 | См. [[S3 И ОБЪЕКТНЫЕ ХРАНИЛИЩА]] |
| Лента событий, интеграции | Kafka | См. [[KAFKA]] |
| Метрики и аналитика по SLA | ClickHouse / витрина | Колоночное хранение, агрегаты |

Это и есть **polyglot persistence**. Обратная сторона, которую надо назвать самому: каждое хранилище — отдельная эксплуатация, отдельная экспертиза, отдельный источник рассогласования. Начинать надо с PostgreSQL и добавлять хранилище только под доказанную проблему.

## Вопросы с собеседования

**1. Когда NoSQL, а когда реляционка?**
Реляционка по умолчанию: транзакции, связи, произвольные запросы, зрелая экспертиза. NoSQL — под конкретный профиль: объём, не влезающий в один узел; профиль запросов, известный заранее и плохо ложащийся на индексы; гибкая схема; экстремальная латентность. Формулировка «взяли Mongo, потому что схема ещё не устоялась» — слабая: `jsonb` в PostgreSQL закрывает это без второго хранилища.

**2. Что такое eventual consistency и как с ней жить?**
Реплики сходятся к одному состоянию через время, между записью и чтением возможно устаревшее значение. Практика: read-your-writes для автора изменения (читать с primary или из кэша своей сессии), UI, не обещающий мгновенности, идемпотентные операции, версии/CAS вместо слепой перезаписи. См. [[МОДЕЛИ СОГЛАСОВАННОСТИ ДАННЫХ]].

**3. Как обеспечить согласованность между PostgreSQL и Redis/Elasticsearch?**
Односторонний поток: источник истины один, остальные — производные. Обновление производных через события (Outbox → Kafka → индексатор) плюс возможность полной перестройки из источника. Двусторонняя синхронизация — источник неразрешимых расхождений.

**4. Redis отдаёт таймауты, приложение легло. Почему кэш уронил систему?**
Скорее всего кэш стал критическим путём: нет таймаутов на обращение к Redis, нет фолбэка на БД, либо БД физически не выдержит нагрузку без кэша. Правильно: короткие таймауты, circuit breaker, деградация на прямое чтение из БД, а если БД без кэша не живёт — это не кэш, а полноценная зависимость, и её надо резервировать соответственно.

**5. Что выберете для хранения истории изменений обращения?**
Если нужны запросы и отчётность — таблица в PostgreSQL с партиционированием по дате. Если объём огромный и запросы аналитические — колоночное хранилище. Ключевой аргумент: история пишется много, читается редко и почти всегда по конкретному обращению или по диапазону дат — этот профиль определяет выбор, а не мода.
