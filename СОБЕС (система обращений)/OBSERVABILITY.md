## Основные концепции наблюдаемости
### 🎯 Основная концепция и подходы

**Observability-as-Code (OaC)** — подход, при котором элементы наблюдаемости (метрики, логи, трассировки) описываются и проверяются как код приложения, хранятся в VCS и имеют строгие требования.

**Наблюдаемость** обеспечивает внутреннюю информацию о состоянии системы и причинно-следственных связях без изменения кода. Это крайне важно для понимания сложных взаимодействий между микросервисами, брокерами сообщений, API-шлюзами, базами данных и кешами в производственных средах.

### 📊 Модели и источники данных

**MELT (Метрики, События, Логи, Трейсинг)** представляет четыре ключевых источника данных для полной наблюдаемости.

**Модели контракта наблюдаемости:**

- **RED-модель (эндпоинтов)**: Rate (количество запросов), Errors (частота ошибок), Duration (время выполнения)
    
- **USE-модель (ресурсов)**: Utilization (использование), Saturation (насыщение), Errors (ошибки ресурса)
    

### ⚙️ Методы сбора данных

**Push vs Pull методы:**

- **Метод push**: сервисы отправляют данные сборщикам (Prometheus Push Gateway)
    
- **Метод scrape**: сборщики опрашивают эндпоинты сервисов через интервалы (15 секунд по умолчанию)
    

## Архитектурные решения

### Prometheus и модель данных

**Хранение данных**: TSDB (база данных временных рядов) на диске с моделью данных на основе имен метрик, меток (labels) и временных меток.

**Модель данных**: Каждая уникальная комбинация меток создает отдельный временной ряд. Метки позволяют фильтровать и группировать метрики, но требуют контроля кардинальности.

**Типы метрик:**

- Счетчики (монотонно возрастающие)
    
- Измерители (произвольные значения)
    
- Гистограммы (корзины для распределений)
    
- Сводки (измерения квантилей)
    

**Настройка целей**: Статически в YAML или динамически через service discovery.

### Экспортеры и интеграция

**Основные экспортеры:**

- Node Exporter — системные метрики Linux
    
- Специализированные экспортеры (Postgres, Micrometer для Spring)
    
- Spring Boot Actuator (`/actuator/prometheus`)
    

**Конфигурация**: Правила оповещений в YAML, монтируемые как Docker volume.

## Реализация в Spring Boot

### Инструменты и контракты

**Инструментарий:**

- **Micrometer** — API для метрик, встроенный в Spring Boot Actuator
    
- **OpenTelemetry** — трассировка
    
- **Spring Boot Actuator** — готовая инфраструктура
    

**Элементы контракта OaC:**

1. **Метрики**:
    
    - Обязательный набор для всех сервисов
        
    - Требования к тегам (low-cardinality)
        
    - Инварианты (например, success_count + error_count = total_count)
        
2. **Логирование**:
    
    - Структурированные логи (JSON)
        
    - Корреляция через traceId/spanId
        
    - Обязательное логирование ошибок и ключевых событий
        
3. **Трассировки**:
    
    - Автоматические спаны для HTTP-запросов
        
    - Кастомные спаны для бизнес-операций
        
    - Контроль кардинальности атрибутов
        

**Пример контракта:**

java

public final class MetricsContract {
    public static final String METRIC_REQUEST_COUNT = "api.requests";
    public static final String TAG_ENDPOINT = "endpoint";
}

### Сбор метрик с приложений

**Micrometer** собирает детальные метрики:

- Статистика HTTP-запросов (количество, длительность, статус)
    
- Метрики пула соединений с БД
    
- Метрики выполнения методов, использование памяти
    
- Пользовательские метрики через MeterRegistry (счетчики, измерители, гистограммы, таймеры)
    

**Без Micrometer**: только базовые системные метрики (время работы процесса, CPU, JVM информация).

## Полный стек наблюдаемости

### Унифицированная архитектура

**Пример системы**: 3 Spring Boot сервиса (производитель, потребитель, API) с:

- PostgreSQL для хранения событий
    
- Kafka кластер с 3 брокерами + Zookeeper + Schema Registry
    
- Prometheus + Grafana для мониторинга
    

**Сбор данных**: Prometheus собирает метрики с экспортеров PostgreSQL, Kafka кластера и Spring Boot сервисов через Actuator.

### Централизованное логирование

**Проблема**: Разрозненные логи в микросервисной архитектуре затрудняют диагностику.

**Grafana Loki**: Система хранения логов с индексацией по меткам (дешевле и проще, чем полнотекстовое индексирование).

**Grafana Alloy**: Универсальный агент на Rust, заменяющий несколько агентов (Promtail, Node Exporter). Собирает метрики, логи и трейсы, маршрутизируя в Loki, Prometheus, Tempo.

### Распределенный трейсинг

**Grafana Tempo**: Хранилище распределенных трейсов, получает данные через OpenTelemetry Protocol.

**Принципы трейсинга**:

- Уникальный Trace ID для каждого запроса
    
- Спаны содержат время начала/окончания, операцию, сервис/метод, теги ошибок
    
- OpenTelemetry SDK автоматически настраивается в Spring Boot для HTTP, Kafka, БД
    

**Преимущества**: Упрощает выявление узких мест по сравнению с логами, обеспечивает сквозную видимость.

## Визуализация и анализ

### Grafana как единый интерфейс

**Возможности**:

- Визуализация метрик, логов и трейсов из Prometheus, Loki, Tempo
    
- Сложные запросы (PromQL, TraceQL)
    
- Шаблонизация и переменные для динамических дашбордов
    
- Детализация и анализ структуры сервисов
    

**Интеграция с Prometheus**: Добавление как источника данных с указанием URL, импорт готовых дашбордов по ID.

**Дашборды**:

- "Node Exporter Full" (ID 1860) — системные метрики
    
- "Quick CPU" — использование CPU по режимам, память, диск, сеть
    
- Пользовательские дашборды для Kafka, PostgreSQL, Spring Boot метрик
    

## Тестирование и качество

### Тестирование наблюдаемости

**Unit-тесты метрик:**

java

@Test
void testMetricIncrement() {
    MeterRegistry registry = new SimpleMeterRegistry();
    service.doSomething();
    assertThat(registry.get("operation.count").counter().count()).isEqualTo(1);
}

**Тестирование логов**: Использование `ListAppender` в Logback, проверка структуры и обязательных сообщений.

**Архитектурные проверки** с ArchUnit:

java

@ArchTest
static final ArchRule noInfoLoggingWithoutContext = 
    noClasses().should(callMethodWhere(...));

### Интеграция в CI/CD

**Автоматизация**:

- Запуск тестов наблюдаемости в пайплайне
    
- Проверка покрытия контракта
    
- Отслеживание изменений метрик
    
- Code review с чек-листами по наблюдаемости
    

## Хранение и масштабируемость

### Хранение данных

**Tempo**: Сохраняет блоки трейсов как файлы parquet в MinIO (S3-совместимое хранилище).

**MinIO**: Высокопроизводительное объектное хранилище, развертываемое локально или в облаке.

**Loki**: Эффективное хранение логов с индексацией по меткам.

### Оповещения и мониторинг

**Алерты**: Автоматические уведомления о сбоях, аномалиях, нарушениях SLA (Slack, Telegram, Email, PagerDuty).

**Grafana Alerts**: Интерфейс для создания, редактирования, мониторинга алертов с поддержкой истории и политик заглушения.

**Prometheus Alerting Rules**: Определение правил на основе метрик для проактивного обнаружения проблем.

## Лучшие практики и преимущества OaC

### Практики реализации

1. **Явное определение контракта** — документация требований как кода
    
2. **Максимальное использование Spring Boot** — активация Actuator
    
3. **Комплексное тестирование** — unit + интеграционные тесты
    
4. **Архитектурные ограничения** — статические проверки
    
5. **Управление инфраструктурой как код** — дашборды и алерты в VCS
    
6. **Обучение команды** — понимание важности наблюдаемости
    

### Ключевые преимущества

- **Предсказуемость** — единые стандарты для всех сервисов
    
- **Раннее обнаружение проблем** — проверки на этапе разработки
    
- **Документирование** — контракт как живая документация
    
- **Качество** — автоматические проверки как gate в CI/CD
    
- **Проактивность** — обнаружение проблем до влияния на пользователей
