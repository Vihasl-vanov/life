# CAP-теорема

> **Суть:** В распределённой системе невозможно одновременно гарантировать все три свойства — при network partition приходится выбирать между **C** и **A**.

---

## Три свойства

|Свойство|Суть|Ключевая деталь|
|---|---|---|
|**C** — Consistency|Все узлы видят одинаковые данные|Чтение всегда возвращает последнюю запись или ошибку|
|**A** — Availability|Каждый запрос получает ответ|Без гарантии актуальности данных|
|**P** — Partition Tolerance|Система работает при разрыве сети|Обязательное свойство большинства реальных систем|

> **P на практике всегда включён** — в реальных сетях сбои неизбежны. Выбор фактически идёт между **CP** и **AP**.

---

## Поведение при network partition

```
Разрыв сети ──► Система выбирает:

  CP (жертвуем A)          AP (жертвуем C)
  ┌─────────────────┐      ┌─────────────────┐
  │ Отклоняем запрос│      │ Принимаем запрос│
  │ если нет кворума│      │ на любом узле   │
  │ → данные чистые │      │ → eventual sync │
  └─────────────────┘      └─────────────────┘
```

### Пример split-brain

Узел A удалил запись R, узел B обновил запись R — нет связи между ними.  
После восстановления: **конфликт**, который нужно разрешать вручную или через стратегию (last-write-wins, MVCC и т.д.)

---

## Классы систем

### CA — Consistent + Available

- Нет устойчивости к partition
- Реальны только при надёжной сети (один ДЦ, резервные каналы)
- **Примеры:** PostgreSQL, MySQL, Oracle (одиночный узел)

### CP — Consistent + Partition Tolerant

- При partition → останавливают операции, ждут кворума
- Применяют алгоритмы консенсуса: **Paxos**, **Raft**
- **Примеры:** HBase, MongoDB (replica set), ZooKeeper, Redis

### AP — Available + Partition Tolerant

- При partition → продолжают работу, данные расходятся
- Eventual consistency — сходимость со временем
- **Примеры:** Cassandra, DynamoDB, CouchDB, Riak, **DNS**

---

## Компромиссы каждого подхода

||Плюсы|Минусы|
|---|---|---|
|**CA**|Простота, нет конфликтов|Не масштабируется, нет P-устойчивости|
|**CP**|Чистые данные, нет рассинхрона|Простои при сбоях, высокая latency|
|**AP**|Максимальная живучесть, низкая latency|Конфликты, устаревшие данные, сложная логика|

---

## Расширение: PACELC

CAP не учитывает **производительность** в штатном режиме.

```
PACELC:
  If Partition → trade-off [A vs C]
  Else (нормальная работа) → trade-off [Latency vs C]
```

Даже без сбоев: синхронная запись в N реплик = выше консистентность, но выше задержка.

---

## Критика CAP

- **Слишком бинарно** — C и A не 0/1, между ними есть градации
- **Упрощение «2 из 3»** — Брюер сам уточнил в 2012: правильнее читать как «при partition — выбор C или A»
- **Нет учёта latency** — решает PACELC
- **Мифологизация** — большинство систем настраиваемые, не «чисто CP» или «чисто AP»

> Хорошая статья: _"Please stop calling databases CP or AP"_ — Martin Kleppmann

---

## Альтернативные модели

|Модель|Суть|
|---|---|
|**BASE**|Basically Available, Soft state, Eventually consistent — антипод ACID|
|**CRDT**|Конвергентные реплицируемые типы данных — математически сходятся без координатора|
|**Eventual consistency**|Данные расходятся, но в конечном итоге выравниваются|
