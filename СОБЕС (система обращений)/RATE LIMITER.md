## Что такое rate limiter

**Rate limiter** ограничивает частоту операций: сколько запросов/сообщений может выполнить субъект (IP, пользователь, API-ключ, сервис) за единицу времени. При превышении порога запрос **замедляется** или **отклоняется** (обычно `HTTP 429 Too Many Requests` + `Retry-After`).

**Пример.** Если для API задано "500 запросов в минуту на ключ", то после 500-го лимитер начнет блокировать (или ставить в очередь) последующие запросы этого клиента до конца окна.

## Требования к системе лимитирования

### Функциональные

- Ограничивать число запросов клиента к API в пределах окна времени.
    

- Конфигурируемые лимиты: пороги и окна (секунда/минута/час/день), разные правила на маршруты/клиентов/тарифы.
    

- Возвращать клиенту понятный сигнал при превышении порога (`429` + заголовки `X-RateLimit-*`/`Retry-After`) - независимо от того, попадает запрос на один сервер или распределен по кластеру.
    

### Нефункциональные

- **Высокая доступность.** Лимитер - "защитный слой" для всей платформы, поэтому SPOF исключен.
    

- **Низкая задержка.** Все запросы проходят через лимитер → дополнительная p99-задержка должна быть минимальной (единицы миллисекунд).
    

- **Масштабируемость.** Поддержка роста числа клиентов/ключей/правил без деградации.
    

## Типы троттлинга

- **Жесткий (hard):** при достижении порога - *немедленный отказ*.
    

- **Мягкий (soft):** допустимо превышение на фиксированный процент (напр., лимит 500 rpm + 5% → 525 rpm).
    

- **Эластичный (dynamic):** разрешать превышение, если есть запас ресурсов (без фиксированного апера). При ложной тревоге - быстро "схлопывать" до базового лимита.
    

## Где размещать лимитер

- **Клиент (SDK).**Ранний отбой лишнего трафика, но небезопасно: легко обойти, трудно централизованно конфигурировать.
    

- **На сервере (в сервисе).** Встроенный мидлвар - низкая задержка, тонкая доменная политика; нужна консистентность счетчиков между инстансами.
    

- **Как промежуточный слой (gateway/middleware).** Единая точка применения политик, защита всего бэкенда, простота оперирования.
    

> Примечание: есть и **OS-уровень** (traffic shaping - `tc`, приоритезация/квоты сокетов), но в продуктовой логике лимиты обычно внедряют на уровне API.

## Модели хранения состояния (счетчиков)

- * **Централизованная БД/кэш (обычно Redis, реже Postgres).**
    

* Единый источник истины → нельзя "перескочить" лимит, идя на разные узлы.

- При огромном трафике возрастает латентность и contention; нужны атомарные операции/Lua, шардинг/репликация.

- **Распределенная БД/локальные счетчики на узлах.**
    

- Меньше задержки/нагрузки на общий стор.  
 - Временные перелимиты при обходе разных узлов (пока состояние не согласовано). Обычно лечится sticky sessions на балансировщике (клиент привязан к одному rate-узлу) - но это бьет по отказоустойчивости и масштабируемости.

- **Глобальный счетчик vs per-user/per-key.**
    

Общий "ведро" для всего трафика - просто, но несправедливо. На практике используют для каждого субъекта счетчики (или иерархические: организация → пользователь → маршрут).

## High-level дизайн

1. **Правила** (Rule DB) описывают, *кто/куда/сколько* может.

2. **Retriever** периодически подтягивает правила в к**эш правил** (горячее состояние).

3. **Identifier** строит ключ квоты (например: `org:{orgId}:user:{userId}:route:{path}`).

4. **Decision-maker** по алгоритму (token/leaky/sliding/…):

- атомарно читает/обновляет счетчик,
    

- решает: *allow / delay / reject*,
    

- пишет метрики/логи.
    

5. **Ответ клиенту**: `200/…` либо `429`, при soft/elastic - возможна **очередь**.

## Detailed дизайн: компоненты

- **Rule DB.** Персистентное хранилище правил (роль/клиент/маршрут → лимит/окно/политика). **Rules Retriever.** Периодический фетч/инвалидация; warm-кэш уменьшает обращения к БД.
    
- **Throttle Rules Cache.** Горячие правила (in-memory/Redis).
    
- **Client Identifier Builder.** Конструирует ключ (IP, userId, apiKey, orgId, path, метод, регион и т.п.).
    
- **Decision-maker.** Реализация алгоритма; атомарные обновления счетчиков; учет soft/elastic-политик.
    
- **Handling 429.** Возвращаем `429`, `Retry-After`, `X-RateLimit-Limit/Remaining/Reset`. Для overload-кейсов - **очередь** и отложенная обработка.
    
- **Failure mode**. Стратегия при сбое стора: *fail-closed* (строгая защита) или *fail-open* (сохраняем доступность) - **пер-роут/пер-роль**.
    
- **Race conditions & contention.** - Избегаем "get-then-set" при высокой конкуренции - используем Lua (атомарный `INCRBY` + `EXPIRE`). - Для экстремального RPS - sharded counters (несколько ключей на одну квоту) → снижение write-contention; чтение агрегирует шардовые значения.
    
- **Не класть всю тяжелую работу в критический путь.** Быстрый r**ead-allow**, а обновление счетчика - асинхронно (batched/pipe) при допустимой погрешности. Это снижает латентность под миллионами RPS.
    

## Алгоритмы лимитирования (когда что выбирать)

|Алгоритм|Ключевая идея|Плюсы|Минусы / эффекты|
|---|---|---|---|
|Token Bucket|"Корзина токенов" пополняется с фиксированной скоростью; запрос “тратит” токен|Разрешает короткие bursts, простая модель|Нужно подобрать параметры (rate/capacity), синхронизация/консистентность в кластере|
|Leaky Bucket|Очередь с ровным оттоком (обработка с фиксированной скоростью)|Сглаживает поток, предсказуемая нагрузка|Bursts почти не проходят; может накапливать очередь и рост latency|
|Fixed Window Counter|Счетчик на фиксированное окно времени|Быстро и дешево (`INCR + EXPIRE`)|Перелимит на границах окон (“edge burst”)|
|Sliding Window Log|Храним лог временных меток запросов за окно|Точная “скользящая” оценка|Дорого по памяти и операциям (сортировка/удаление старых меток)|
|Sliding Window Counter|Взвешивание двух соседних окон (текущее + предыдущее)|Хороший баланс точности/стоимости|Приближение, не идеальная точность; возможны погрешности на границах|

## Практические вопросы

- **Гранулярность ключа:** `tenant:plan:user:route:region` - ровный шард-распределитель.
    

- **Политики при превышении:** `reject`, `delay/backpressure`, `enqueue`, `degrade (убрать тяжелые фичи)`.
    

- **Документирование:** публичные API → описать лимиты в контракте; внутренние - в runbook.
    

- **Наблюдаемость:** метрики отклонений, top offenders, saturation хранилища, latency RL-пути.
