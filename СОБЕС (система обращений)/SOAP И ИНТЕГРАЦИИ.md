# SOAP И ИНТЕГРАЦИИ

> В требованиях: «разработка интеграционных решений с использованием REST API, **SOAP**, брокеров сообщений». Плюс «интеграция более чем с 20 другими автоматизированными системами Банка» — это и есть суть работы.
> SOAP в хранилище встречался один раз, в перечислении «тяжёлые протоколы SOA».

Связанные: [[МИКРОСЕРВИСНАЯ АРХИТЕКТУРА]], [[API GATEWAY]], [[KAFKA]], [[DISTRIBUTED SYSTEMS]], [[OBSERVABILITY]]

## Почему SOAP всё ещё жив в банках

Легаси-системы 2000-х (в том числе Microfocus Service Manager, который вы будете заменять), корпоративные шины (ESB), интеграции с государственными сервисами. SOAP даёт формальный контракт (WSDL+XSD), встроенные стандарты безопасности (WS-Security) и подписи — то, что в REST собирается вручную.

При 20+ интеграциях реалистичная картина: часть по REST, часть по SOAP, часть через Kafka, часть через файловый обмен и БД-линки.

## SOAP vs REST

| | SOAP | REST |
|---|---|---|
| Контракт | WSDL + XSD, машиночитаемый, строгий | OpenAPI (опционален), договорённость |
| Формат | Только XML | JSON, XML, что угодно |
| Транспорт | HTTP, JMS, SMTP | HTTP |
| Модель | RPC — вызов операции | Ресурсы + HTTP-глаголы |
| Ошибки | SOAP Fault в теле, HTTP 500 | HTTP-коды + тело |
| Безопасность | WS-Security: подпись, шифрование на уровне сообщения | TLS + OAuth2/JWT на уровне транспорта |
| Транзакции | WS-AtomicTransaction | Нет |
| Вес | Многословно, парсинг XML дороже | Легче |

**Ключевое отличие по сути:** SOAP подписывает и шифрует **само сообщение**, поэтому оно остаётся защищённым, проходя через посредников (шину, гейтвей). TLS защищает только участок канала — на шине сообщение расшифровано. Для банковских цепочек через ESB это иногда принципиально.

### Структура конверта
```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Header>
    <wsse:Security>...подпись, токен...</wsse:Security>
  </soap:Header>
  <soap:Body>
    <GetEmployeeRequest><personnelNumber>12345</personnelNumber></GetEmployeeRequest>
  </soap:Body>
</soap:Envelope>
```

**SOAP Fault** — `faultcode` (`Client` / `Server`), `faultstring`, `detail` с бизнес-кодом. `Client` повторять бессмысленно, `Server` — можно ретраить. Эта классификация напрямую определяет политику ретраев.

**Стили binding:** `document/literal wrapped` — практический стандарт. `rpc/encoded` — устаревший, но встречается в старых системах и плохо переваривается современными тулзами.

## Java: как работать

### Contract-first (единственно правильный подход)
Есть WSDL от смежной системы → генерируем классы.

```xml
<plugin>
  <groupId>org.apache.cxf</groupId>
  <artifactId>cxf-codegen-plugin</artifactId>
  <executions><execution>
    <goals><goal>wsdl2java</goal></goals>
    <configuration>
      <wsdlOptions><wsdlOption>
        <wsdl>${basedir}/src/main/resources/wsdl/hr-service.wsdl</wsdl>
        <extraargs><extraarg>-xjc-Xts</extraarg></extraargs>
      </wsdlOption></wsdlOptions>
    </configuration>
  </execution></executions>
</plugin>
```

WSDL кладём **в репозиторий и версионируем**, не тянем по URL при сборке — иначе сборка ломается, когда смежная система недоступна или молча поменяла контракт.

### Spring WS (клиент)
```java
@Bean
public Jaxb2Marshaller marshaller() {
    Jaxb2Marshaller m = new Jaxb2Marshaller();
    m.setContextPath("ru.bank.hr.gen");
    return m;
}

@Bean
public WebServiceTemplate hrClient(Jaxb2Marshaller marshaller) {
    WebServiceTemplate t = new WebServiceTemplate(marshaller);
    t.setDefaultUri("https://hr.bank.internal/ws");
    t.setMessageSender(httpComponentsMessageSender());  // таймауты, пул, mTLS
    t.setInterceptors(new ClientInterceptor[]{ securityInterceptor(), loggingInterceptor() });
    return t;
}
```
Таймауты задавать **обязательно и явно** — дефолт у некоторых sender'ов бесконечный, и одна зависшая интеграция кладёт пул потоков всего приложения.

### Spring WS (сервер, contract-first)
XSD → `DefaultWsdl11Definition` генерирует WSDL, эндпоинт:
```java
@Endpoint
public class RequestEndpoint {
    @PayloadRoot(namespace = NS, localPart = "CreateRequestRequest")
    @ResponsePayload
    public CreateRequestResponse create(@RequestPayload CreateRequestRequest req) { ... }
}
```

### WS-Security
`Wss4jSecurityInterceptor`: `UsernameToken` (в банке — редко и только внутри контура), подпись и шифрование по X.509 из JKS/PKCS12, `Timestamp` против replay-атак. Отдельно — mTLS на транспортном уровне. Ротация сертификатов — эксплуатационная боль, о которой полезно упомянуть: истёкший сертификат интеграции это классический инцидент.

**MTOM** — передача бинарных вложений отдельной частью MIME вместо base64 внутри XML. Без MTOM файл на 10 МБ превращается в 13 МБ base64 внутри DOM — и это OOM.

**XXE.** Парсинг чужого XML без отключённых внешних сущностей — уязвимость на чтение файлов сервера. Всегда `disallow-doctype-decl`, отключить `external-general-entities`. Обязательный пункт на код-ревью интеграции.

## Общие правила интеграции (важнее, чем синтаксис SOAP)

На собеседовании ценнее не знание тегов, а понимание, как не уронить систему через чужую.

### 1. Таймауты
Каждый внешний вызов — connect timeout и read timeout, выставленные явно и меньше, чем таймаут вызывающего. Бюджет времени распределяется сверху вниз: если пользователю обещан ответ за 2 с, интеграция не может ждать 30 с.

### 2. Ретраи
Только для идемпотентных операций и retryable-ошибок (таймаут, 5xx, connection reset). **Экспоненциальный backoff с джиттером** — синхронный ретрай всех клиентов добивает и без того больной сервис. Ограниченное число попыток.

### 3. Circuit Breaker
Смежная система лежит — перестаём её звать, отдаём деградированный ответ, периодически пробуем. Resilience4j:
```java
@CircuitBreaker(name = "hrService", fallbackMethod = "fallback")
@Retry(name = "hrService")
@TimeLimiter(name = "hrService")
@Bulkhead(name = "hrService")
public Employee find(String id) { ... }
```
Порядок аннотаций Resilience4j: Bulkhead → TimeLimiter → RateLimiter → CircuitBreaker → Retry.

### 4. Bulkhead
Отдельный пул потоков/семафор на каждую интеграцию. Без этого одна медленная система выедает общий пул и роняет **все** остальные функции. При 20 интеграциях это не опция.

### 5. Идемпотентность
Клиент передаёт `X-Request-Id` / `messageId`, сервер хранит результат по нему и на повтор возвращает тот же ответ без повторного выполнения. Без этого любой ретрай на таймауте порождает дубли обращений.

### 6. Асинхрон вместо синхрона
Если смежная система не нужна для ответа пользователю — не звать её в цепочке запроса. Событие в Kafka, отдельный потребитель, ретраи и DLT. Синхронная цепочка из пяти вызовов имеет доступность как произведение доступностей: пять систем по 99,9% дают 99,5%.

### 7. Anti-corruption layer
Модель смежной системы не протекает в вашу доменную модель. Отдельный слой адаптеров с маппингом. При 20 интеграциях без этого домен превращается в свалку чужих DTO.

### 8. Наблюдаемость
По каждой интеграции: количество вызовов, ошибок, латентность по перцентилям, состояние circuit breaker. Сквозной `traceId` пробрасывается в SOAP-заголовок / HTTP-заголовок. Логирование конвертов — с маскированием персональных данных. См. [[OBSERVABILITY]].

## Выбор протокола под задачу

| Ситуация | Чем |
|---|---|
| Нужен синхронный ответ пользователю | REST (JSON) |
| Смежная система даёт только WSDL | SOAP |
| Событие, ответ не нужен | Kafka |
| Высокочастотный внутренний вызов между сервисами | gRPC |
| Массовая выгрузка/загрузка | Batch-файлы, Kafka Connect, CDC |
| Клиенту нужны разные срезы данных одним запросом | GraphQL |

Формулировка для собеса: «Синхронно зову только то, без чего не могу ответить пользователю. Всё остальное — событием. Это и латентность, и доступность».

## Вопросы с собеседования

**1. Когда выбрали бы SOAP, а не REST?**
Когда смежная система его уже предоставляет и альтернативы нет; когда требуется подпись и шифрование на уровне сообщения, переживающие промежуточные узлы; когда нужен строгий машиночитаемый контракт с генерацией клиента и валидацией по XSD. Для новых внутренних API выбрал бы REST или gRPC.

**2. Как версионировать интеграционный контракт?**
Обратно совместимые изменения — добавление опциональных элементов, новые операции. Ломающие — новый namespace/новая версия эндпоинта и параллельная работа старой версии на период миграции. В XSD помогает `minOccurs="0"` и осторожность с `sequence`. Для REST — версия в пути (`/api/v2`), для Kafka — Schema Registry с BACKWARD-совместимостью, см. [[KAFKA]].

**3. Смежная система отвечает по 30 секунд, у нас всё встало. Что делать?**
Немедленно: жёсткий read timeout, bulkhead под эту интеграцию, circuit breaker. Дальше: убрать вызов из синхронной цепочки, если он не нужен для ответа; кэшировать редко меняющиеся данные; при массовых операциях — батчить. Организационно — SLA со смежной командой и алерт на его нарушение.

**4. Как тестировать интеграции?**
Юнит-тесты на маппинг. Контрактные тесты по WSDL/XSD и OpenAPI. Заглушки: WireMock для HTTP/SOAP, `MockWebServiceServer` в Spring WS. Интеграционные — Testcontainers. Отдельно — тесты на сценарии деградации: таймаут, 500, битый XML, срабатывание circuit breaker. Тесты, которые ходят в реальный тестовый контур смежной системы, — не в CI, они нестабильны.

**5. Как разбирать инцидент в интеграции?**
Сквозной traceId в логах обеих систем, сохранённые конверты запроса/ответа (с маскированием), метрики по кодам ошибок и латентности, состояние circuit breaker. Первым делом определить сторону: наши таймауты или их ошибки. Типовые причины: истёкший сертификат, смена контракта без предупреждения, исчерпание пула соединений, всплеск нагрузки.

**6. Что такое ESB и почему от него уходят?**
Единая шина с маршрутизацией, трансформацией и оркестрацией внутри себя. Проблемы: единая точка отказа, бизнес-логика размазана по конфигурации шины, релизный цикл общий на все системы, одна команда — узкое место. Микросервисный подход выносит логику в сервисы, а шину сводит к «тупому» транспорту (Kafka) плюс API Gateway. См. [[МИКРОСЕРВИСНАЯ АРХИТЕКТУРА]], [[API GATEWAY]].
