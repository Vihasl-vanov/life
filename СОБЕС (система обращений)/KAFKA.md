# KAFKA

> Главный пробел под вакансию: в требованиях стоит «глубокое знание Kafka и смежных технологий». В остальных заметках Kafka упоминается только вскользь.

Связанные: [[DISTRIBUTED SYSTEMS]], [[BACKPREASURE]], [[МОДЕЛИ СОГЛАСОВАННОСТИ ДАННЫХ]], [[SPRING]], [[OBSERVABILITY]]

## Архитектура: из чего состоит

| Термин | Что это |
|---|---|
| **Broker** | Один сервер Kafka. Кластер = несколько брокеров |
| **Topic** | Именованный лог сообщений. Логическая сущность |
| **Partition** | Физическая единица параллелизма. Топик = N партиций. Внутри партиции — строгий порядок |
| **Offset** | Порядковый номер записи внутри партиции. Монотонно растёт, никогда не переиспользуется |
| **Segment** | Файл на диске, из которых состоит партиция. Ретенция удаляет сегменты целиком |
| **Replica** | Копия партиции на другом брокере. Одна — leader, остальные — followers |
| **ISR** (In-Sync Replicas) | Реплики, догнавшие лидера. Только они могут стать лидером при штатном failover |
| **Controller** | Брокер, управляющий метаданными и выбором лидеров |
| **Consumer group** | Набор консьюмеров, делящих партиции между собой |

**Ключевая идея:** Kafka — это не очередь, а **распределённый упорядоченный лог с ретенцией**. Сообщение не удаляется после чтения. Консьюмер просто двигает свой offset. Поэтому можно перечитать историю, подключить нового потребителя к старым данным, переиграть события.

### Zookeeper vs KRaft
- До 2.8 метаданные жили в Zookeeper — отдельный кластер, отдельная боль.
- **KRaft** (Kafka Raft) — метаданные внутри самой Kafka, кворум контроллеров. Дефолт с 3.3+, Zookeeper удалён в 4.0.
- На собесе: «мы на KRaft / у нас ещё ZK, планировали миграцию» — знать, что это такое, обязательно.

### Почему Kafka быстрая
1. **Последовательная запись на диск** — append-only лог, диск линейно быстрее случайного доступа в разы.
2. **Page cache ОС** — Kafka не держит свой кэш, отдаёт это ядру. Поэтому JVM heap у брокера маленький (6–8 ГБ), а машина с большой RAM.
3. **Zero-copy** (`sendfile`) — данные идут с диска в сокет минуя user space.
4. **Батчинг и сжатие** — продюсер копит записи, жмёт батч целиком, брокер хранит его в сжатом виде и отдаёт консьюмеру тоже сжатым.

## Producer

```properties
acks=all
enable.idempotence=true
max.in.flight.requests.per.connection=5
retries=Integer.MAX_VALUE
delivery.timeout.ms=120000
linger.ms=10
batch.size=32768
compression.type=zstd
```

### acks — самый частый вопрос
| Значение | Смысл | Риск |
|---|---|---|
| `acks=0` | Не ждём подтверждения вообще | Теряем данные молча. Только метрики/логи |
| `acks=1` | Ждём запись на лидера | Лидер упал до репликации → сообщение потеряно |
| `acks=all` (`-1`) | Ждём запись на все ISR | Медленнее, но не теряем. **Дефолт для банка** |

`acks=all` работает только в паре с **`min.insync.replicas`** на топике. При RF=3 и `min.insync.replicas=2` кластер переживает падение одного брокера; если живых ISR меньше 2 — продюсер получает `NotEnoughReplicasException` и **лучше упасть, чем потерять**.

### Идемпотентный продюсер
Без него ретрай после таймаута сети даёт дубль: брокер записал, ответ потерялся, продюсер повторил.

`enable.idempotence=true` → брокер выдаёт продюсеру **PID** (producer id), каждое сообщение несёт **sequence number** по партиции. Брокер отбрасывает дубли и ловит нарушения порядка. С Kafka 3.0 включено по умолчанию.

Гарантия действует **в рамках сессии продюсера и одной партиции**. Перезапуск приложения → новый PID → защиты нет. Поэтому дедупликация на стороне консьюмера всё равно нужна.

### Порядок сообщений
- Порядок гарантирован **только внутри партиции**.
- Партиция выбирается по ключу: `hash(key) % partitions`. Один ключ → всегда одна партиция.
- Практика: ключ = `requestId` / `userId`. Все события одного обращения обрабатываются по порядку, разные обращения — параллельно.
- Без ключа — sticky partitioner: продюсер набивает один батч в одну партицию, потом переключается.
- **Если увеличить число партиций — маппинг ключей сломается.** Старые ключи уедут в другие партиции, порядок нарушится. Партиции только добавляются и никогда не уменьшаются, поэтому число закладывают с запасом.

### Транзакции продюсера
```java
producer.initTransactions();
producer.beginTransaction();
producer.send(rec1);
producer.send(rec2);
producer.sendOffsetsToTransaction(offsets, groupMetadata);
producer.commitTransaction();
```
Атомарная запись в несколько партиций/топиков + коммит offset'ов входного топика. Это и есть **exactly-once в паттерне consume-process-produce**. Консьюмер должен читать с `isolation.level=read_committed`, иначе увидит незакоммиченные записи.

Требует `transactional.id` — стабильный, переживающий рестарт, иначе zombie-инстанс не отфенсится.

## Consumer

### Consumer group и распределение
- Партиция в конкретный момент читается **ровно одним** консьюмером группы.
- Консьюмеров больше, чем партиций → лишние простаивают. **Партиции — потолок параллелизма.**
- Разные группы читают один топик независимо, каждая со своим offset'ом.

### Rebalance
Происходит при: подключении/отключении консьюмера, падении heartbeat, изменении числа партиций, `max.poll.interval.ms` превышен.

| Стратегия | Поведение |
|---|---|
| **Eager** (Range, RoundRobin) | Stop-the-world: все отдают все партиции, потом заново раздаются |
| **CooperativeSticky** | Инкрементальный: перекидываются только нужные партиции, остальные продолжают работать |

`partition.assignment.strategy=CooperativeSticky` — правильный выбор для прода.

**Static membership** (`group.instance.id`) — при рестарте пода консьюмер возвращает себе те же партиции без ребаланса, если уложился в `session.timeout.ms`. Спасает от шторма ребалансов при rolling update в Kubernetes.

### Тайминги — классический вопрос «почему у нас бесконечный ребаланс»
| Параметр | Смысл | Типовое |
|---|---|---|
| `heartbeat.interval.ms` | Как часто шлём heartbeat | 3s |
| `session.timeout.ms` | Нет heartbeat дольше — считаемся мёртвыми | 45s |
| `max.poll.interval.ms` | Максимум между двумя `poll()`. Превысили — выкидывают из группы | 5 min |
| `max.poll.records` | Сколько записей отдаёт один `poll()` | 500 |

**Типичный инцидент:** обработка одной пачки занимает больше `max.poll.interval.ms` (например, ходим в медленный внешний сервис). Консьюмера выкидывают, партиции уезжают другому, тот тоже не успевает → группа крутится в вечном ребалансе и лаг растёт. Лечение: уменьшить `max.poll.records`, вынести обработку в свой пул, увеличить таймаут.

### Коммит offset'ов
- `enable.auto.commit=true` — коммитит раз в `auto.commit.interval.ms` **независимо от того, обработал ты или нет**. Упал после коммита, но до обработки → потеря. Для бизнес-логики выключать.
- Ручной: `commitSync()` (надёжно, блокирует) / `commitAsync()` (быстро, без ретраев). Практика: `commitAsync` в цикле + `commitSync` в `finally` при закрытии.
- Коммитится **offset следующей записи**, не текущей.

### Гарантии доставки
| Гарантия | Как получить | Цена |
|---|---|---|
| **At most once** | Коммит offset ДО обработки | Потери |
| **At least once** | Коммит ПОСЛЕ обработки | Дубли → нужна идемпотентность потребителя |
| **Exactly once** | Транзакции + `read_committed`, либо at-least-once + дедуп по ключу в БД | Сложность, латентность |

**Честный ответ на собесе:** «End-to-end exactly-once в Kafka существует только внутри Kafka (consume-process-produce через транзакции). Как только в цепочке появляется внешняя система — БД, REST-вызов — это at-least-once плюс идемпотентный потребитель. Мы делаем дедуп по `messageId` в таблице обработанных сообщений в той же транзакции, что и бизнес-запись».

## Ретенция и compaction

```properties
cleanup.policy=delete        # по умолчанию
retention.ms=604800000       # 7 дней
retention.bytes=-1
```

**Log compaction** (`cleanup.policy=compact`) — Kafka хранит **последнее значение для каждого ключа**, старые версии подчищает. Получается «снимок текущего состояния» в виде топика.
- Применение: справочники, конфигурации, `__consumer_offsets` (он именно compacted).
- **Tombstone** — запись с `value=null`. Означает удаление ключа; после `delete.retention.ms` уходит совсем.
- Можно комбинировать: `cleanup.policy=compact,delete`.

## Надёжность

- **RF (replication factor) = 3** — стандарт для прода.
- **`min.insync.replicas=2`** + `acks=all` — переживаем падение одного брокера без потерь.
- **`unclean.leader.election.enable=false`** — если включить, лидером может стать отставшая реплика → **тихая потеря данных**. В банке всегда `false`.
- **Rack awareness** — реплики раскладываются по разным стойкам/AZ.

**Задача на собес:** RF=3, `min.insync.replicas=3`, один брокер на обслуживании. Что будет? — Продюсер с `acks=all` начнёт получать `NotEnoughReplicasException`, запись встанет. Именно поэтому `min.insync.replicas` ставят на единицу меньше RF.

## Spring for Apache Kafka

```java
@KafkaListener(topics = "requests.created", groupId = "request-processor",
               concurrency = "3")
public void handle(ConsumerRecord<String, RequestEvent> record, Acknowledgment ack) {
    processor.process(record.value());
    ack.acknowledge();
}
```

**Что знать:**
- `ConcurrentKafkaListenerContainerFactory` — `concurrency` = число потоков-консьюмеров в поде. Больше числа партиций смысла не имеет.
- **`AckMode`**: `RECORD`, `BATCH` (дефолт), `MANUAL`, `MANUAL_IMMEDIATE`, `TIME`, `COUNT`. Для бизнес-логики — `MANUAL_IMMEDIATE`.
- **`DefaultErrorHandler`** + `DeadLetterPublishingRecoverer` — N ретраев с backoff, потом в DLT (`<topic>.DLT`).
- **`@RetryableTopic`** — неблокирующие ретраи: неудачное сообщение уезжает в `topic-retry-0`, `topic-retry-1` с растущей задержкой, потом в DLT. Не блокирует партицию, в отличие от блокирующего retry.
- **`KafkaTemplate`** + `@Transactional` с `KafkaTransactionManager`.
- Классификация ошибок: **retryable** (сеть, таймаут БД) — повторяем; **non-retryable** (десериализация, валидация) — сразу в DLT. Иначе poison pill встанет колом в партиции и заблокирует всё за собой.
- `ErrorHandlingDeserializer` — оборачивает десериализатор, чтобы битое сообщение не роняло контейнер.

### Kafka + БД: транзакции не общие
Нельзя атомарно записать в PostgreSQL и отправить в Kafka. Варианты:
1. **Transactional Outbox** — пишем событие в таблицу `outbox` в той же транзакции, отдельный процесс/Debezium читает и публикует. См. [[DISTRIBUTED SYSTEMS]].
2. **Idempotent consumer** — публикуем сразу, на приёме дедуплицируем.
3. **Listen to yourself** — сначала в Kafka, потом сам себя слушаем и пишем в БД.

Outbox — стандартный ответ для банковского контура.

## Смежные технологии

| Что | Зачем | Где всплывает в вакансии |
|---|---|---|
| **Schema Registry** | Хранит Avro/Protobuf/JSON-схемы, проверяет совместимость (BACKWARD/FORWARD/FULL) при эволюции контракта | 20+ интеграций — контракты обязаны версионироваться |
| **Kafka Connect** | Готовые коннекторы source/sink без своего кода (JDBC, S3, Elastic) | Выгрузка обращений в аналитику/S3 |
| **Debezium (CDC)** | Читает WAL PostgreSQL, льёт изменения в Kafka | Миграция со старой системы Microfocus без её переписывания |
| **Kafka Streams** | Библиотека stream-processing внутри JVM-приложения: KStream/KTable, join, windowing, state store | Агрегаты по SLA обращений |
| **ksqlDB** | SQL поверх стримов | — |
| **MirrorMaker 2** | Репликация между кластерами/ЦОД | DR-контур |

**Compatibility в Schema Registry** — частый вопрос:
- `BACKWARD` — новый консьюмер читает старые данные (можно удалять поля и добавлять с default). Дефолт.
- `FORWARD` — старый консьюмер читает новые данные.
- `FULL` — и то, и другое.

## Мониторинг

- **Consumer lag** — метрика №1. `records-lag-max`, Burrow / kafka-lag-exporter. Растёт → консьюмер не успевает.
- **Under-replicated partitions** — > 0 значит проблема с репликацией.
- **Offline partitions** — > 0 значит часть топика недоступна.
- **Request latency**, **network processor idle %**.
- Трассировка: заголовки Kafka несут `traceparent`, Micrometer Tracing / Sleuth пробрасывают контекст сквозь брокера. См. [[OBSERVABILITY]].

```bash
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group request-processor
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic requests.created
kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic requests.created --from-beginning --max-messages 5
```

## Вопросы с собеседования

**1. Чем Kafka отличается от RabbitMQ?**
RabbitMQ — брокер очередей с push-моделью, роутингом через exchange, сообщение удаляется после ack. Сильные стороны: сложный роутинг, приоритеты, per-message TTL, отложенная доставка. Kafka — распределённый лог с pull-моделью, сообщение живёт по ретенции, потребители независимы и могут перечитывать. Kafka выигрывает на пропускной способности и на сценарии «много потребителей одного потока событий»; RabbitMQ — на классических задачах очереди задач с хитрой маршрутизацией.

**2. Сколько партиций делать?**
Отталкиваемся от целевого параллелизма консьюмеров и пропускной способности. Партиция — потолок параллелизма, поэтому берём с запасом (уменьшить нельзя). Но каждая партиция — файлы, память, время выборов лидера при отказе; десятки тысяч партиций на кластер деградируют его. Практика: считаем целевой throughput / throughput на партицию, округляем вверх, кратно ожидаемому числу инстансов.

**3. Гарантирует ли Kafka порядок?**
Только внутри партиции. Глобального порядка по топику нет. Порядок для бизнес-сущности обеспечивается ключом партиционирования. Плюс: при `max.in.flight.requests.per.connection > 1` и **выключенной** идемпотентности ретрай может переставить сообщения местами — с `enable.idempotence=true` брокер это отслеживает по sequence number и порядок сохраняется до 5 in-flight.

**4. Что происходит при ребалансе и как его пережить без потерь?**
Партиции переназначаются. Опасность — обработанное, но не закоммиченное сообщение достанется другому консьюмеру (дубль), либо закоммиченное, но не обработанное потеряется. Решения: `ConsumerRebalanceListener` с коммитом в `onPartitionsRevoked`, CooperativeSticky, static membership, идемпотентная обработка.

**5. Как обрабатывать «ядовитое» сообщение?**
`ErrorHandlingDeserializer` чтобы не падать на десериализации, классификация retryable/non-retryable, ограниченное число ретраев с экспоненциальным backoff, затем DLT с исходными заголовками и причиной. Отдельно — процесс разбора DLT: алерт, ручной или автоматический reprocess. Без DLT poison pill блокирует партицию навсегда.

**6. Консьюмер отстал на 10 млн сообщений. Действия?**
Понять природу: всплеск нагрузки или деградация обработки. Смотрим на время обработки записи, GC, внешние вызовы. Быстрые рычаги: поднять `concurrency`/число подов до числа партиций, увеличить `max.poll.records` и батчить работу с БД, вынести медленные внешние вызовы в асинхрон. Если упёрлись в число партиций — добавлять партиции (с оглядкой на порядок). Крайний случай при неактуальных данных — сдвинуть offset.

**7. Как перенести обработку на новую версию схемы без даунтайма?**
Через Schema Registry с BACKWARD-совместимостью: новые поля только опциональные с default. Сначала выкатываем консьюмеров, умеющих обе версии, потом продюсера. Ломающее изменение — новый топик `v2` и двойная публикация на время миграции.

**8. Зачем `__consumer_offsets` и что будет, если группа исчезнет?**
Внутренний compacted-топик с offset'ами групп. Если группа не коммитила дольше `offsets.retention.minutes` (7 дней по умолчанию), её offset'ы удаляются, и при старте применяется `auto.offset.reset`: `latest` — пропустим накопленное, `earliest` — перечитаем всё с начала. Классическая причина «после новогодних праздников сервис переобработал весь топик».

## Как это ложится на вакансию

Система обращений: 10 млн обращений/год ≈ 320 сообщений/сек в пике на событиях жизненного цикла (создано, назначено, эскалировано, закрыто) при 20+ интеграциях. Формулировка для собеса:

> «Kafka у нас — шина событий между модулем обращений и смежными системами. Топики по доменным событиям, ключ — идентификатор обращения, чтобы события одного тикета шли строго по порядку. Публикация через Outbox, чтобы не расходиться с БД. Потребители идемпотентны по `eventId`. `acks=all`, RF=3, `min.insync.replicas=2`. Ошибки — неблокирующие ретраи через `@RetryableTopic` и DLT с алертом на лаг и на объём DLT.»
