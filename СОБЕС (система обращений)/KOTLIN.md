# KOTLIN

> В требованиях: «уверенное знание Java/**Kotlin**». В хранилище слова «Kotlin» не было ни разу.
> Реалистичная цель — не «выучить Kotlin», а уметь читать чужой код и внятно ответить на вопросы. Если проект на Java, Kotlin спросят поверхностно; если на Kotlin — спросят про корутины и null safety всерьёз.

## Что даёт Kotlin поверх Java

Тот же байткод, та же JVM, полная двусторонняя совместимость. Разница — в языке:

| Проблема Java | Ответ Kotlin |
|---|---|
| NPE | Nullability в системе типов, проверка на компиляции |
| Boilerplate DTO | `data class` — equals/hashCode/toString/copy бесплатно |
| Перегрузки ради опциональных параметров | Дефолтные и именованные аргументы |
| Утилитные классы `StringUtils` | Функции-расширения |
| Иерархии без исчерпывающего разбора | `sealed class` + `when` с проверкой полноты компилятором |
| Потоки под блокирующий I/O | Корутины |
| Изменяемость по умолчанию | `val`, неизменяемые интерфейсы коллекций |

## Null safety — вопрос номер один

```kotlin
var a: String = "x"     // не может быть null
var b: String? = null   // может

b?.length              // safe call → null, если b == null
b?.length ?: 0         // элвис: значение по умолчанию
b!!.length             // NPE, если null. Признак того, что что-то спроектировано неверно
b?.let { println(it) } // выполнить только если не null
```

**Platform types.** Java-код не несёт информации о nullability, поэтому Kotlin видит его тип как `String!` — «не знаю». Компилятор не проверяет, и NPE прилетает в момент присваивания. Отсюда практика: на границе с Java-библиотеками объявлять тип явно nullable, а в самом Java-коде расставлять `@Nullable`/`@NotNull` (Kotlin их читает).

**`lateinit var`** — для полей, инициализируемых после конструктора (внедрение зависимостей, `@BeforeEach`). Обращение до инициализации даёт `UninitializedPropertyAccessException`. Не работает с примитивами.

**`by lazy`** — потокобезопасная ленивая инициализация `val` при первом обращении.

## Конструкции, которые встретятся в любом коде

```kotlin
data class Request(val id: Long, val title: String, val status: Status = Status.NEW)
val closed = request.copy(status = Status.CLOSED)   // иммутабельное обновление
val (id, title) = request                            // деструктуризация

sealed interface Result
data class Ok(val value: String) : Result
data class Fail(val error: String) : Result

// when по sealed — компилятор требует покрыть все ветки, else не нужен
val msg = when (result) {
    is Ok   -> "ок: ${result.value}"     // smart cast, без приведения типа
    is Fail -> "ошибка: ${result.error}"
}

// функция-расширение — добавляет метод к чужому типу без наследования
fun String.toSafeKey(): String = trim().lowercase().replace(' ', '-')

// дефолтные и именованные аргументы вместо цепочки перегрузок
fun search(query: String, page: Int = 0, size: Int = 20, sort: String = "createdAt")
search("сеть", size = 50)
```

**Scope-функции** — источник половины вопросов на собесе:

| Функция | Объект внутри | Возвращает | Типичное применение |
|---|---|---|---|
| `let` | `it` | результат лямбды | null-safe преобразование |
| `run` | `this` | результат лямбды | вычисление на объекте |
| `apply` | `this` | сам объект | конфигурирование билдера |
| `also` | `it` | сам объект | побочный эффект (лог) в цепочке |
| `with` | `this` | результат лямбды | группировка вызовов на объекте |

**Классы по умолчанию `final`.** Наследование требует `open`. Отсюда плагины `all-open`/`kotlin-spring` — Spring нужны не-final классы для CGLIB-прокси. Аналогично `no-arg`/`kotlin-jpa` для JPA-сущностей, которым нужен конструктор без аргументов.

**Коллекции.** `listOf` возвращает `List` — интерфейс **только для чтения**, не иммутабельную коллекцию: под капотом может лежать изменяемый список, а из Java его можно изменить. `mutableListOf` даёт `MutableList`. Функции `map`/`filter`/`groupBy` работают жадно, без промежуточных Stream; `asSequence()` — ленивый аналог Stream API, оправдан на длинных цепочках и больших коллекциях.

## Корутины — главный технический вопрос

**Что это.** Способ писать асинхронный код последовательно. `suspend`-функция при приостановке **не блокирует поток**: компилятор превращает её в конечный автомат (CPS-трансформация), состояние живёт в объекте `Continuation`, а поток уходит выполнять другую работу.

```kotlin
suspend fun loadRequest(id: Long): RequestDto = coroutineScope {
    val request = async { repository.find(id) }      // параллельно
    val history = async { historyClient.fetch(id) }
    RequestDto(request.await(), history.await())
}
```

**Отличие от потоков.** Поток — ресурс ОС, ~1 МБ стека, переключение через ядро. Корутина — объект в heap, сотни байт, переключение в user space. Миллион корутин — нормально, миллион потоков — нет. Но корутина **не даёт параллелизма сама по себе**, она даёт дешёвую конкурентность: параллелизм всё равно ограничен потоками диспетчера.

**Диспетчеры:** `Dispatchers.Default` (CPU-bound, пул по числу ядер), `Dispatchers.IO` (блокирующий I/O, пул расширяемый до 64+), `Dispatchers.Main` (UI, в бэкенде не нужен). Блокирующий вызов на `Default` — заблокированное ядро.

**Structured concurrency** — корутина всегда живёт в scope; scope не завершится, пока не завершатся дочерние; отмена родителя отменяет детей; исключение ребёнка отменяет родителя (кроме `SupervisorJob`). Это то, чего нет в голых `Future`: там ошибка легко теряется, а задача продолжает жить.

- `coroutineScope { }` — ошибка ребёнка валит весь блок.
- `supervisorScope { }` — дети падают независимо.
- Отмена **кооперативная**: код должен её проверять (`isActive`, `ensureActive()`, вызовы suspend-функций). Бесконечный CPU-цикл без проверок не отменится.
- `CancellationException` **нельзя глотать** в `catch (e: Exception)` — это ломает отмену. Ловить точечно или пробрасывать дальше.

**Flow** — холодный асинхронный поток значений: `flow { emit(...) }`, операторы `map`/`filter`/`buffer`/`flatMapMerge`, терминальный `collect`. Холодный — код запускается на каждый `collect`. `StateFlow`/`SharedFlow` — горячие. Backpressure решается `buffer`/`conflate`, см. [[BACKPREASURE]].

**Виртуальные потоки vs корутины.** С Java 21 виртуальные потоки решают ту же задачу — дешёвая конкурентность на блокирующем I/O — но на уровне JVM и без окраски функций (`suspend`). Честный ответ: для нового Java-проекта чаще проще виртуальные потоки; корутины дают больше — structured concurrency, Flow, встроенную отмену — и оправданы, если проект уже на Kotlin.

## Kotlin в Spring Boot

```kotlin
@RestController
class RequestController(private val service: RequestService) {   // конструкторное внедрение без аннотаций

    @GetMapping("/requests/{id}")
    suspend fun get(@PathVariable id: Long): RequestDto = service.load(id)
}

@Entity
class RequestEntity(
    @Id @GeneratedValue val id: Long? = null,
    var title: String,
    @Enumerated(EnumType.STRING) var status: Status
)
```

Что знать:
- Плагины `kotlin-spring` (all-open) и `kotlin-jpa` (no-arg) — без них не заведётся.
- `jackson-module-kotlin` — иначе десериализация в data class с непустым конструктором ломается.
- **`data class` для JPA-сущности — антипаттерн**: сгенерированные `equals`/`hashCode` по всем полям ломают контракт для сущностей с ленивыми связями и порождают инициализацию прокси; `toString` тянет всю связь. См. [[HIBERNATE]].
- `@ConfigurationProperties` отлично ложится на data class с дефолтами.
- Spring WebFlux нативно понимает `suspend`-контроллеры и `Flow`.
- Тесты: JUnit 5 + `runTest { }` для корутин, MockK вместо Mockito (умеет final-классы и корутины).

## Вопросы с собеседования

**1. Чем `val` отличается от `const val` и от `final` в Java?**
`val` — ссылка не переприсваивается, но объект внутри может меняться (как `final` в Java). `const val` — константа времени компиляции, только примитивы и String, только на верхнем уровне или в `object`, инлайнится в место использования.

**2. Что такое `inline` и `reified`?**
`inline`-функция подставляется в место вызова вместе с телом лямбды — исчезают аллокация объекта-лямбды и вызов. Побочно позволяет `return` из вызывающей функции (non-local return). `reified` работает только в inline-функциях: тип-параметр доступен в рантайме, поэтому можно писать `T::class` и `is T` — обход стирания типов. Инлайнить большие функции вредно: раздувается байткод.

**3. Как Kotlin спасает от NPE и где не спасает?**
Спасает: nullable-типы проверяются компилятором. Не спасает: `!!`, platform types с Java-стороны, `lateinit` до инициализации, неинициализированное поле, к которому обратились из конструктора базового класса.

**4. Чем `object` отличается от `companion object`?**
`object` — синглтон-объявление, инстанс создаётся лениво и потокобезопасно. `companion object` — объект-компаньон внутри класса, замена статике; чтобы вызывать из Java как статику, нужен `@JvmStatic`.

**5. Extension-функция переопределяет метод класса?**
Нет. Расширения разрешаются **статически**, по объявленному типу, а не по фактическому. Если у класса есть метод с той же сигнатурой — всегда выиграет метод класса. Полиморфизма у расширений нет.

**6. Корутина против потока — когда что?**
Массовый блокирующий или сетевой I/O с высокой конкурентностью — корутины (или виртуальные потоки). CPU-bound работа — обычный пул потоков по числу ядер, корутины здесь ничего не выигрывают. Смешивать нельзя: блокирующий вызов внутри корутины на `Dispatchers.Default` блокирует поток пула.

**7. Стоит ли переводить существующий Java-проект на Kotlin?**
Не целиком и не разом. Совместимость позволяет писать новые модули и тесты на Kotlin рядом с Java. Цена: обучение команды, время сборки, инструменты. Выигрыш заметнее всего на DTO-heavy и на асинхронном коде.
