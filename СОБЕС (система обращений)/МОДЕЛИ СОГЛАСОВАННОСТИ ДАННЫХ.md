# Модели согласованности данных

> Распределённая система не может обеспечить мгновенную согласованность без компромиссов в производительности и доступности. Вместо единой модели используется спектр — от строгой до итоговой.

---

## Спектр моделей

```
Строже / медленнее
        ▲
        │  Strong Consistency (Linearizability)
        │  Sequential Consistency
        │  Causal Consistency
        │  Eventual Consistency
        ▼
Слабее / быстрее
```

Каждая более сильная модель включает гарантии более слабой.

---

## Строгая согласованность (Strong / Linearizability)

**Гарантия:** каждое чтение возвращает результат последней завершённой записи. Система ведёт себя как единственная копия данных.

**Как реализуется:** синхронная репликация + консенсус (Paxos, Raft). Запись подтверждается только после кворума узлов.

**Поведение при записи:**

1. Клиент пишет X=5 на узел A
2. A синхронно реплицирует на B, C — ждёт подтверждения
3. Только после кворума отвечает клиенту: OK
4. Любое последующее чтение с любого узла вернёт X=5

|||
|---|---|
|✅|Нет устаревших данных, нет аномалий|
|✅|Простая логика приложения — система как единая БД|
|❌|Высокая latency — ждём кворума на каждую запись|
|❌|При partition часть узлов недоступна для записи|
|❌|Плохо масштабируется горизонтально|

**Где применяется:** банки, биржи, распределённые блокировки, ZooKeeper, конфигурационные реестры.

---

## Последовательная согласованность (Sequential Consistency)

**Гарантия:** все узлы видят операции в одном и том же порядке, при этом порядок операций каждого отдельного узла сохраняется. Реального времени не требует — операции могут применяться с задержкой.

**Пример:** P1 сделал A → B. Другой узел увидит A раньше B — всегда. Но где именно вклинится операция C от P2 — не определено, главное что все видят это одинаково.

|||
|---|---|
|✅|Нет «разнобоя» в порядке событий между узлами|
|✅|Меньше накладных расходов, чем у Strong|
|❌|Нет гарантии актуальности — данные могут быть устаревшими|
|❌|Глобальное упорядочивание — узкое место при масштабировании|

**Где применяется:** многопользовательские игры, совместное редактирование — где порядок действий важнее свежести.

---

## Причинно-следственная согласованность (Causal Consistency)

**Гарантия:** если операция B зависит от A (A → B), все узлы увидят A раньше B. Независимые (конкурентные) операции могут наблюдаться в разном порядке на разных узлах.

**Как реализуется:** векторные часы / логические метки версий. Узел задерживает применение обновления, пока не применены все его «причины».

**Пример аномалии, которую предотвращает:** комментарий к посту не появится раньше самого поста.

|||
|---|---|
|✅|Интуитивный порядок для связанных событий|
|✅|Выше производительность, чем у Sequential — нет глобального порядка|
|✅|Баланс: eventual + учёт зависимостей|
|❌|Сложная реализация — нужно хранить векторные метки|
|❌|Параллельные конфликтующие записи всё равно нужно разрешать отдельно|

**Где применяется:** мессенджеры (порядок реплик), соцсети (ответ после поста), совместные документы.

---

## Итоговая согласованность (Eventual Consistency)

**Гарантия:** при отсутствии новых записей все реплики **в конечном счёте** придут к одному состоянию. В любой момент данные могут расходиться.

**Связанная концепция:** BASE — Basically Available, Soft state, Eventually consistent. Антипод ACID.

**Поведение при записи:**

1. Клиент пишет X=5 на узел A
2. A сразу отвечает: OK (локальная запись)
3. Репликация на B, C идёт асинхронно в фоне
4. Клиент на узле C может временно прочитать X=3 (старое)
5. Через некоторое время C тоже обновится до X=5

|||
|---|---|
|✅|Высокая доступность — узлы работают автономно|
|✅|Низкая latency — ответ сразу, без ожидания кворума|
|✅|Горизонтальное масштабирование без сложной синхронизации|
|❌|Временная нецелостность — разные пользователи видят разные данные|
|❌|Нет гарантий порядка — возможны аномалии|
|❌|Нужно явно обрабатывать конфликты (LWW, CRDT, слияние)|

**Где применяется:** CDN, DNS, счётчики лайков/просмотров, Cassandra, DynamoDB (по умолчанию), Riak.

## Сессионные гарантии (Client/Session Guarantees)

Не отдельная модель, а дополнительные гарантии для конкретного клиента поверх eventual consistency. Улучшают UX без потери глобальной масштабируемости.

|Гарантия|Суть|Пример|
|---|---|---|
|**Read Your Writes (RYW)**|После своей записи клиент всегда видит её результат|Добавил товар в корзину — сразу его видишь|
|**Monotonic Reads**|Чтения не «прыгают назад» — никогда не получишь более старую версию|Баланс не может вернуться от $100 к $90|
|**Monotonic Writes**|Записи одного клиента применяются в порядке отправки|Операции A → B не могут применяться как B → A|
|**Writes Follow Reads**|Твоя запись не обгонит данные, которые ты уже читал|Твой комментарий не появится раньше поста, который ты видел|

**Реализация:** sticky session (все запросы сессии на один узел) или routing с учётом версий. Поддерживается в Cosmos DB, DynamoDB (session consistency).

## Сравнительная таблица

|Модель|Актуальность|Порядок|Latency|Доступность|
|---|---|---|---|---|
|Strong|Всегда свежие|Глобальный реального времени|Высокая|Низкая при сбоях|
|Sequential|Может отставать|Глобальный, но без времени|Средняя|Средняя|
|Causal|Может отставать|Частичный (по зависимостям)|Низкая|Высокая|
|Eventual|Временно устарело|Нет гарантий|Минимальная|Максимальная|

## Модели в микросервисах

**Принцип:** внутри сервиса — Strong/ACID; между сервисами — Eventual через события.

**Паттерны:**

- **Saga** — цепочка локальных транзакций с компенсациями при откате. Вместо глобального лока — разруливаем постфактум
- **Outbox pattern** — гарантированная доставка событий через таблицу в той же БД
- **Idempotent operations** — повторная обработка события не ломает данные

**Пример — оформление заказа:**

```
Order создан (Strong внутри Order-сервиса)
    ↓ async event
Inventory резервирует товар
    ↓ async event
Payment списывает деньги
    ↓ async event (или компенсация если failed)
Notification отправляет письмо
```

Пользователь сразу видит «Заказ принят» — eventual consistency между сервисами. Если Payment упал — Saga откатывает резерв.

**Правило выбора:**

|Данные|Модель|
|---|---|
|Финансы, инвентарь|Strong / Sequential (внутри сервиса)|
|Профили, настройки|Causal или Session guarantees|
|Ленты, счётчики, кэши|Eventual|

> 83% компаний с микросервисами комбинируют несколько моделей для разных доменов данных.
